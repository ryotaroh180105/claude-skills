# sidejob/SETUP.md — Phase 0 ユーザー準備手順

出典: `docs/designs/22-side-job-automation.md` §6.7 Phase 0。各操作の意図・内容・確認方法を明記する（CLAUDE.md「操作を依頼する時の説明義務」準拠）。この手順が完了して初めて Phase 1（Lane A 出品＋Lane B intake ループ稼働）を開始する。

## P0-1: プラットフォームアカウントの確認・開設

- **意図**: Lane A（ココナラ出品）・Lane B（クラウドワークス/ランサーズ応募）を動かすには、あなた自身のアカウントが必要（Claude は代理登録できない — 規約の本人操作原則）。
- **内容**: クラウドワークス・ランサーズ・ココナラのアカウントを確認する。未開設なら各サイトで新規登録する（本人確認が必要な場合あり）。
- **確認方法**: 各サイトにログインでき、マイページが表示される。

## P0-2: 新着案件の通知メールをON にする

- **意図**: Lane B の intake ループは Gmail 経由でメール通知をパースする設計（規約でスクレイピング・API直叩きが禁止されているため、公式のメール通知だけを情報源にする）。
- **内容**: クラウドワークス・ランサーズのマイページ→通知設定で「新着案件のメール通知」を有効化する（検索条件の保存が必要な場合あり）。
- **確認方法**: 数分〜1日以内に、登録した Gmail アドレスへ新着案件メールが届く。

## P0-3: Gmail MCP の疎通確認

- **意図**: intake ループがメールを検索できるか、実装前に確認する。
- **内容**: このセッション（Claude）側で Gmail MCP 経由の検索を試す（あなたの操作は不要。P0-2 の通知メールが届いていることが前提）。
- **確認方法**: Claude が「◯件のメールが見つかった」と報告する。0件の場合は P0-2 の通知設定を再確認する。

## P0-4: 実物の通知メール1通の取得（レッドチーム指摘2対策）

- **意図**: `sidejob/fixtures/` の3ファイルは現状「創作サンプル」（実物の通知メール形式を模した想像）であり、実際のメール書式（HTML構造・トラッキングURL・ダイジェスト形式等）と異なる可能性がある。実物なしで検証すると「テストは通るが実運用で抽出0件」という静かな失敗（設計書§8-7）が起こり得る。
- **内容**: P0-2 で受信した実際の通知メール（クラウドワークスかランサーズ、どちらか1通で可）を、個人情報（本名・住所等が含まれていれば）マスクした上でこのセッションに共有する。**メール本文をそのままチャットに貼って問題ない**（案件情報のみで機密情報ではない想定。心配な場合は差出人・件名・本文の案件詳細部分だけで良い）。
- **確認方法**: Claude が `sidejob/fixtures/` を実物ベースに置換し、intake dry-run を再実行して結果を報告する。

## P0-5: Routine（自動実行）登録の可否確認

- **意図**: intake ループ（毎朝1回）・weekly-review ループ（週次1回）を自動実行すると、継続的なセッション実行コストが発生する。設計書§12-4のとおり、登録には明示的な承認が必要。
- **内容**: P0-1〜P0-4 が完了し、実際に運用を始める段になったら、Claude が改めて登録可否を確認する（本SETUP.mdの完了だけでは自動登録しない）。
- **確認方法**: `loops/sidejob-intake/schedule.md` の状態欄が「未登録」から「登録済み（trigger_id: ...）」に変わる。

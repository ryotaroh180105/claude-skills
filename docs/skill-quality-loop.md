# スキル品質ループ（Skill Quality Loop）

「いろんなユースケースでテストして改善する」ためのループ定義。`skill-creator` の
[練度向上ワークフロー](../plugins/skill-creator/skills/skill-creator/SKILL.md)（症状特定→修正→version up、の内側のループ）を
**いつ・何を素材にして回すか**を決める、外側のループ。両者は役割分担であり、内容を重複させない：

- **このドキュメント**: テストケースをどう作り、どう採点し、いつ次に回すか
- **skill-creator**: 見つかった症状をどう SKILL.md の修正に落とすか

## 参考にした知見（出典）

- Anthropic は eval を「決定的チェック＋LLM-as-judge＋人間」の3層で組み合わせ、
  失敗事例をそのまま次の評価データセットに繰り込むことを推奨している。
  LLM-as-judge には「わからなければ分からないと言わせる」逃げ道を必ず用意し、
  無理な採点による捏造を防ぐ。
  ([Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))
- Agent Loop（知覚→推論→実行→評価→内省→更新）の実践では、**1回のループのスコープと
  コストに上限を必ず設ける**。フィードバックのロジック自体が間違っていると
  「一貫して間違った出力」を量産するループになるのが一番のリスク。
  ([How Agent Loop Works, Gleecus 2026](https://gleecus.com/blogs/agent-loop-adaptive-ai-agents-complete-guide-2026/))
- 日本語コミュニティでの Claude Skills 運用知見: スキルは「作って終わり」ではなく
  「70点のドラフトを作る→実際に使ってアウトプットを確認する→フィードバックする→
  80点に引き上げる」を繰り返す「育てる運用」が定着している。
  ([Claude Codeスキル活用術, 01lab](https://01lab.co.jp/ai/claude-code-skills-guide))
- skill-creator コミュニティでは「勘で直す」から「テストで検証する」への移行が
  評価されている。スキル開発は「プロンプト設計」から「評価駆動開発」に変わる。
  ([「勘で直す」が終わる, note.com/renkon40](https://note.com/renkon40/n/n2b3dc4740430))

## ループの全体像

```
Phase 0 スコープ選定 → 1 ケース生成 → 2 実行 → 3 採点 → 4 診断
   ↑                                                    ↓
   └────────────── 6 記録・卒業判定 ← 5 回帰確認 ←──────┘
```

1回のループは **対象スキル 1〜2個・所要 30〜60分** を上限にする（Agent Loopの安全弁に対応）。
一気に21個全部を回そうとしない。

## Phase 0: スコープ選定

- 対象は ROADMAP.md の優先順位（Tier1→2→3）か、直近で実際に使ったスキルを優先する。
- 「このスキルを壁打ちしたい」と Ryo が言ったとき、または `skill-creator` 側で
  version を上げた直後の確認として起動する。

## Phase 1: テストケース生成（4軸で多様化する）

SKILL.md 作成時に列挙した5個以上のユースケースをベースに、以下の4軸で足りない
角度を補う。各ケースには **「何が出れば合格か」を1文で明文化**する
（Anthropicの「unambiguous, robust success criteria」）。

| 軸 | 内容 | 例 |
|---|---|---|
| 定型（happy path） | 主目的にドンピシャな依頼 | 「議事録にして」に音声ファイルを渡す |
| 境界・異常系 | 入力なし/巨大/形式不正/キー未設定/権限不足 | APIキー未設定でvoicememo-pipelineを呼ぶ |
| トリガー境界 | 発動すべきか微妙、または誤発動しそうな紛らわしい依頼 | 「レビューして」だけで pr-review と code-review-adr のどちらが発動すべきか |
| 実運用データ | Ryo の実際のインターン/副業/学習の生々しい状況 | 本物の商談録音、本物の仕様書の抜粋 |

「実運用データ」軸が最も信頼できる（本番のfailureがそのままテストケースになる、
というAnthropicの知見に対応）。実際に使っていて違和感があった場面は、
そのまま次回ループのテストケースとして残す。

## Phase 2: 実行

各ケースを実際に Claude Code 上でスキルを発動させて走らせる（またはドライラン）。
出力と、どのステップで詰まったかを記録する。

## Phase 3: 採点（3層グレーダー）

1. **決定的チェック**: `validate_skills.py` 通過、スクリプトの構文・実行可否、
   参照ファイルパスの実在性など機械的に判定できるもの。
2. **LLM-as-judge（Claudeの自己批評）**: SKILL.md 記載の「出力フォーマット」
   「注意点」と実際の出力を突き合わせ、ルーブリック的に採点する。
   **わからない場合は「不明」と答えさせ、無理に合格/不合格を決めつけない。**
3. **Ryo の最終判定**: 実務で使ったときの納得感。3層の中で最も優先される。
   Ryo の一言フィードバック（「発動しなかった」「微妙」「良い」）で十分。

## Phase 4: 診断 → skill-creator へ

不合格・違和感のあったケースは、**原因を1つに特定してから**
`skill-creator` の練度向上ワークフロー（4パターン: 発動しない/手順曖昧/
出力違い/誤発動）に渡して修正する。「勘で直さない」— 原因不明のまま
SKILL.md をいじらない。

## Phase 5: 回帰確認

修正後、**今回失敗したケースだけでなく、過去に合格していたケースも再実行**し、
デグレがないか確認する。CI が新しい変更で既存テストを壊していないか見るのと同じ考え方。

## Phase 6: 記録・卒業判定

- テストケースと結果は `plugins/<skill>/skills/<skill>/test-log.md` に蓄積する
  （初回ループ時に作成。フォーマットは自由だが、日付・ケース内容・結果・
  対応したversionを含める）。
- **卒業基準**: 直近10ケース連続合格 かつ Ryo からのポジティブな実運用
  フィードバックが2回以上 → そのスキルは「安定運用フェーズ」に移行し、
  積極的なテストケース生成の頻度を落とし、実運用中の違和感ベースの
  フィードバックだけで回すようにする。

## 将来の自動化について

`/loop` スキルや Routine（`create_trigger`）を使えば Phase 1〜3 の一部
（決定的チェックの実行や、Claude自身によるユースケースのウォークスルー）は
定期実行できる。ただし多くのスキルは「Ryo の実際の業務」が最良のテスト
データなので、**完全自動化はしない**。人間の判断が伴わないループは
「一貫して間違った合格判定」を出し続けるリスクがある（Agent Loopの安全弁の教訓）。
自動化するのは Phase 0〜3 の下ごしらえまでとし、Phase 3c・Phase 4 の最終判断は
必ず Ryo を経由する。

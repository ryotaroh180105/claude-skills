## 1. 目的・背景（Why）

未知の、または引き継ぐコードベース／エージェント開発プロジェクトに素早くキャッチアップし、
**固定スキーマの「引き継ぎサマリー」Markdown を1本生成する**スキル。次の4状況を想定する。

1. 他人が作った開発を巻き取る（前任者不在で仕様書がない）
2. 中断した自分の作業を数週間後に再開する（当時の文脈を失っている）
3. 後任インターンに渡す引き継ぎ資料を作る
4. エージェント開発（本リポジトリのような SKILL/plugin/agent 構成）の全体像を掴む

既存スキルでは足りない理由: requirements-definition は「これから作るもの」を定義する未来向き、
本スキルは「既にあるもの」を読む過去・現在向きで方向が逆。work-approach-playbook は
仕事の進め方の型（着手前チェック・報連相）で対象コードの中身は読まない。code-review-adr は
diff/PR の品質判定で全体像把握はしない。task-management はタスクの管理で、抽出はしない。
「コードベースを読んで構造化された引き継ぎ資料を出す」担当が現状どこにも無い。

## 2. スコープ

### 2.1 やること

- リポジトリ構造の把握（ディレクトリツリー・言語構成・規模の概算）
- 読む優先順位付け（§6 Step 2 の固定順序。巨大リポジトリで「何を先に読むか」を確定）
- 抽出: エントリポイント／主要モジュール／データフロー（テキスト記述）／外部依存／未完了作業（TODO・FIXME・未実装スタブ）
- git 履歴の活用（直近コミット・変更頻度の高いファイル・未マージブランチから「今どこまで/直近何を触っていたか」を推定）
- 固定7セクションの「引き継ぎサマリー」Markdown を `docs/handoffs/` に生成
- エージェント開発リポジトリ（SKILL.md / plugin.json / marketplace.json / agents 構成）を認識した場合の専用チェック項目（§6 Step 4b）

### 2.2 やらないこと（明示的スコープ外）

- **フロー図・シーケンス図の作画** → 08-code-flow-visualizer の担当。本スキルはデータフローを箇条書きテキストで記述するに留め、図が要る場合は「08 を呼べ」と促すだけ（YAGNI＋別設計書の担当）
- **コードの品質評価・バグ指摘・レビューコメント** → code-review-adr の担当。本スキルは「何があるか」を記述し「良し悪し」は判定しない（別スキルの担当）
- **これから何を作るかの要件定義** → requirements-definition の担当（方向が逆）
- **抽出した「次にやること」のタスク管理・優先順位付け・進捗追跡** → task-management の担当。本スキルは候補を列挙して渡すのみ（別スキルの担当）
- **依存パッケージの脆弱性スキャン・ライセンス監査**（YAGNI。依頼があれば別スキル）
- **コードの自動修正・リファクタリング実行**（読むだけ。書き換えない）
- **サマリーの多言語出力**（日本語固定。YAGNI）
- **静的解析ツール／AST パーサの新規導入**（ripgrep + git + ファイル読みで足りる。YAGNI）

## 5. データ構造

### 5.1 引き継ぎサマリー固定スキーマ（確定・見出し文字列も確定）

出力 Markdown は次の7セクションを**この順・この見出しで**必ず持つ。該当情報が無いセクションは
削除せず「該当なし（理由）」と書く（空欄は「未調査」と区別できないため）。

```markdown
# 引き継ぎサマリー: <リポジトリ名>

| 項目 | 値 |
|---|---|
| 調査日 | YYYY-MM-DD |
| 対象 | <パス or リポジトリURL> / <調査時点のコミットハッシュ> |
| 調査者 | <名前 or セッション> |
| 規模 | 約 N ファイル / 主要言語 <lang>（M%） |

## 1. 概要（3行で何のプロジェクトか）
<何をするものか・誰のためか・現在の成熟度（PoC/開発中/運用中）を3〜5行>

## 2. アーキテクチャ
- エントリポイント: <ファイル:行 or コマンド>
- 主要モジュール: <ディレクトリ/ファイル → 役割> を表で3〜10件
- データフロー: <入力→処理→出力を箇条書き。図が要るなら「08-code-flow-visualizer を実行」と明記>
- 外部依存: <API/DB/MCP/SaaS/主要ライブラリ → 用途> を表で
- 設定・秘密情報: <env / 設定ファイルの場所と必要キー名（値は載せない）>

## 3. 現在地（どこまで出来ているか）
- 動くもの: <確認できた稼働機能>
- 未完成・スタブ: <未実装・TODO・FIXME・空関数を file:line 付きで>
- 直近の作業: <git log 直近10件から推定した「最後に何を触っていたか」>

## 4. 次にやるべきこと
- [ ] <着手候補。根拠（どの TODO / どの中断点か）を1行添える>
（task-management へ渡す場合はこの節をそのまま Backlog に転記できる粒度で書く）

## 5. 詰まりどころ・落とし穴
- <ビルド/起動の非自明な前提、壊れやすい箇所、暗黙の依存、危険な操作>

## 6. 用語集
| 用語 | 意味 | 出典 file:line |
|---|---|---|
| | | |

## 7. 情報源メタ
- 読んだ主要ファイル: <パス列挙>
- 未読・不明で確認が必要: <時間切れ/権限で読めなかった箇所。無ければ「なし」>
```

### 5.2 生成ファイル命名（確定）

- パス: `docs/handoffs/YYYY-MM-DD-<repo-slug>.md`
- `<repo-slug>`: リポジトリのディレクトリ名を小文字化しスペースを `-` に置換したもの
- `docs/handoffs/` が無ければ作成してよい（handoffs は本スキル専用ディレクトリのため、code-review-adr の adr ディレクトリと違い確認不要）
- 既存の同名ファイルがある場合は上書きせず、末尾に `-2`, `-3` を付す

## 6. 処理フロー

**Step 0（受付・規模判定）**: 対象パス／URL を確認。対象が単一ファイルかつ100行未満なら
サマリーを作らず「小規模のため直接読めば足りる」と返して終了（§7）。曖昧なら着手前に確認。

**Step 1（メタ把握）**: 次を順に取得 —
`git log --oneline -20`、`git shortlog -sn -20`（貢献者）、
`git log --pretty=format: --name-only -50 | sort | uniq -c | sort -rn | head`（変更頻度＝churn 上位）、
`git branch -a`（未マージブランチ）。git 管理外なら本 Step をスキップし「情報源メタ」に記載。

**Step 2（読む優先順位＝固定順）**: 巨大リポジトリでは上から順に読み、時間切れなら途中で打ち切って
「情報源メタ」に未読を記録する。
1. `README*` / `CLAUDE.md` / `docs/`（プロジェクトの自己申告）
2. パッケージ manifest（`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` 等）＝依存とエントリの宣言
3. ディレクトリツリー（`git ls-files | head -200` 相当。ツリー構造で全体量を掴む）
4. Step 1 churn 上位ファイル（＝プロジェクトの重心。最近触られている＝重要かつ流動的）
5. エントリポイント（manifest の `main`/`scripts`/`bin`、`if __name__`、`func main`、CI 定義）から呼び出しを1〜2段辿る
6. `rg -n "TODO|FIXME|XXX|HACK|not implemented|未実装|後で"` で未完了作業を全抽出

**Step 3（抽出）**: Step 2 の読解から、5.1 の各セクション素材を埋める。データフローは箇条書きテキストで書く。

**Step 4a（判定・委譲）**: 以下に該当したら本スキルでは扱わず委譲先を案内する（§11）。
- データフローの図が必要 → 08-code-flow-visualizer
- コードの良し悪し/バグ指摘が欲しい → code-review-adr
- これから作る機能の要件が欲しい → requirements-definition

**Step 4b（エージェント開発リポジトリ検出時の追加チェック）**: `**/SKILL.md` または
`marketplace.json` または `.claude-plugin/plugin.json` を検出したら、通常の抽出に加えて —
各 plugin の SKILL.md の `name`/`description`（発動トリガー）一覧、marketplace.json 登録済み/未登録の差分、
ROADMAP.md のステータス（未着手/実装中/完了）、`.claude/agents/` のサブエージェント定義 — をサマリー2・3節に含める。

**Step 5（出力）**: 5.2 の命名で `docs/handoffs/` に書き出し、ユーザーに要約提示。
「次にやるべきこと」を task-management の Backlog に載せるか尋ねる（載せる操作自体は task-management に委ねる）。

## 7. エッジケース

| ケース | 期待挙動 |
|---|---|
| 対象が単一ファイル・100行未満 | サマリーを作らず「小規模のため直接読めば足りる」と返す |
| git 管理外のディレクトリ | Step 1 をスキップ。「情報源メタ」に「git 履歴なし」と明記し、ファイル mtime で直近作業を代替推定 |
| 巨大リポジトリ（目安 1,000 ファイル超）で時間切れ | Step 2 の優先順で読めた範囲までで7セクションを埋め、未読を「情報源メタ」に列挙。作りかけでも必ず出力する |
| README も manifest も無い | Step 3・4・5（churn とエントリ探索）に依存度を上げ、「概要」は推定と明記する |
| TODO/FIXME が0件 | 「未完成・スタブ」に「明示マーカーなし。未マージブランチ／空関数から推定」と書く。空欄にしない |
| リモートのみ（未 clone）でローカルに無い | GitHub MCP があれば `get_file_contents` 等で主要ファイルのみ取得。無ければ clone を促す |
| 対象が曖昧（パス未指定） | 着手前に対象を確認。カレントリポジトリを既定候補として提示 |

## 8. 失敗シナリオとレッドチーム所見

| # | 失敗シナリオ | 早期警報サイン | 設計上の対策 |
|---|---|---|---|
| 1 | 巨大リポジトリで全ファイルを読もうとして時間切れ・出力なしで終わる | 30分読んでもサマリーが1文字も出ない | §6 Step 2 で読み順を固定し、時間切れでも「読めた範囲＋未読リスト」で必ず出力する設計（作りかけ出力を許容） |
| 2 | サマリーが表層的（README の言い換えだけ）で引き継ぎに使えない | 「現在地」「詰まりどころ」が README に書ける内容しかない | churn 上位・git 履歴・TODO 抽出・未マージブランチという「README に書かれない情報源」を必須ステップ化。特に3節「直近の作業」は git log 由来を強制 |
| 3 | code-flow-visualizer(08) / code-review-adr との責務が曖昧で、図やレビューまで抱え込み肥大化 | サマリーにフロー図やバグ指摘が混入する | §2.2 で作画・品質評価を明示的にスコープ外化。§6 Step 4a で委譲を分岐として固定。データフローは箇条書きテキスト限定 |

## 11. 実装時判断ルール

- **SKILL.md の文体・構成**は既存 `code-review-adr` / `requirements-definition` の SKILL.md に合わせる（「いつ使うか」「ワークフロー」「出力フォーマット」「注意点」構成）。強度レベル（lite/full）区分は設けない。
- **08-code-flow-visualizer が未実装の場合**: 本スキルは単独で完結する。データフローは §5.1 の箇条書きテキストで記述し、図が必要なユーザーには「08 が実装され次第それを使う」と案内する。08 の実装完了を本スキルの完成条件にしない。
- **git コマンド失敗時**（git 未インストール等）: エラーで止めず、その Step をスキップして「情報源メタ」に記録し続行する。
- **書き換えは一切しない**: 対象コードの修正・フォーマット・リファクタは本スキルの責務外。読み取り専用。
- **委譲は案内のみ**: 08 / code-review-adr / requirements-definition / task-management へは「このスキルを使ってください」と案内し、本スキルが代行実行しない。
- **秘密情報**: env・設定ファイルにキーの実値を見つけてもサマリーに転記しない。キー名と場所のみ記す。
- 判断に迷い本ルールに無いものは AskUserQuestion で確認する。

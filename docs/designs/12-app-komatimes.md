## 1. 目的・背景（Why）

fable5-design-assets.md §4.2 に「作りたいアプリ」として名前だけ挙がっている「コマtimes」を、動作設計から実装まで一気通貫で成立させたい、というのが元要求。
ただし**名前以外の情報がゼロ**。「コマ」「times」という2語から機能を推定するしかない。

このリポジトリのユーザー像（既存スキル群から読み取れる文脈）:
- SNS発信・自己記録・タスク管理系スキルを多数運用（article-writer, sns-ops-team, twitter-intel, task-management, voicememo-pipeline）。
- 副業・就活実績づくり（G3）とプロダクト成立性（biz-ops-guard）を重視。
- 無料枠・個人運営・別リポジトリ・1アプリ1リポジトリが既定（04 設計書）。

この文脈は解釈Aの「個人の作業/生活を時間のコマ単位で記録する times（分報）アプリ」と最も整合する（§12 で詳述）。既存の task-management スキルは Markdown TODO であり「時間軸の記録・タイムライン閲覧」は持たないため、代替では埋まらない余地はある。

## 5. データ構造

**解釈依存・§12参照。** 確定前に本物のスキーマは書けない。以下は解釈Aを採った場合の骨格（確定時に「コマ」の意味に合わせて差し替える）。

解釈A（個人times＝時間コマ単位の分報）の最小スキーマ:

```
Koma（1投稿 = 1コマの記録）
- id: string（uuid）
- created_at: ISO8601 datetime
- slot: string        # 「コマ」の識別。解釈依存: 時間ブロック名（例 "09:00-09:25"）/ 通し番号 / 自由ラベル
- body: string        # 本文（分報テキスト）
- tags: string[]      # 任意
```

- 表示は `created_at` 降順のタイムライン、`slot` でグルーピング。
- 解釈B（漫画コマ日記）なら `body` に加え `image_url`／`panel_order` が要る。解釈C（時間割）なら `weekday`・`period`・`subject`・`room` が要る。**どの追加フィールドが要るかは解釈で分岐**するため、確定前にスキーマ確定はしない。

## 6. 処理フロー

**解釈依存・§12参照。** 解釈Aを主線とした最小フロー（他解釈でも「入力→保存→タイムライン表示」の骨格は共通、単位と追加項目のみ変わる）:

1. 入力: ユーザーがフォームに本文（＋解釈依存の項目）を入力し送信。
2. 処理: バリデーション（本文必須・空文字禁止・長さ上限）→ 永続化層に1レコード保存。
3. 出力: 当日ぶんのコマを時系列で一覧表示。保存直後は楽観的にリスト先頭へ追加。
4. 再訪: ページ再読み込み時、永続化層から当日（または選択日）のコマを取得して描画。

分岐:
- 本文が空／空白のみ → 保存せずフォームにエラー表示（§7）。
- 永続化層が応答しない → 保存失敗を明示表示し、入力内容は消さない（§7）。

### 12.3 最有力仮説（A）とその根拠

- 語の自然さ: 「times」は日本のIT/SNS文脈で **Slackの個人分報チャンネル（times-○○）** を強く想起させる。「コマ」を時間の区切りと読むと「時間コマごとの分報」で意味が一貫する。
- リポジトリ文脈: ユーザーは自己記録・SNS発信・タスク管理系スキルを多数運用（article-writer / sns-ops-team / task-management / twitter-intel / voicememo-pipeline）。**個人の記録・発信ツール**という系譜に解釈Aが最も乗る。
- 既存資産との非重複: task-management は Markdown TODO で「時間軸タイムライン閲覧」を持たない。解釈Aは既存で埋まらない余地がある（biz-ops-guard の差別化＝乗り換え理由が立てやすい）。

### 12.4 各解釈に共通で確認すべき点（解釈選択と同時に聞く）

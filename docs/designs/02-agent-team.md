## 0. 計画ゲート回答（00設計書 §5.1）

1. **最も確率の高い失敗パターン（3つ）**: ①規約の形骸化（AGENT_TEAM.md を誰も参照せずに Agent を起動する）②レッドチームの儀式化（指摘が採択されずノイズ扱いになる）③並列実装エージェントの共有ファイル書込競合。→ §8 に早期警報サインと対策を記載。
2. **スコープ境界**: Agent SDK（Python）による常駐・定期無人稼働の実装、sns-ops-team の SKILL.md 改修、hooks による規約の機械的強制、はやらない（§2.2）。
3. **完成条件の真偽判定可能性**: 全項目を grep / ファイル存在 / Agent 起動の出力観察で判定できる形にした（§3）。
4. **実装者が最初に詰まる箇所**: 所有権表の初期行の粒度と、red-team の model 指定。→ §5.2 で初期行を確定値で与え、§11 に判断ルールを記載。
5. **本当に必要か**: 既存 sns-ops-team は SNS 業務限定のロール分担で、リポジトリ横断のファイル所有権・書込権限・レッドチーム強制の規約は存在しない。loop-engineering は時間軸の自動化設計でロール間権限を扱わない。代替不可のため必要。

### 5.3 共有ファイル変更の宣言プロトコル（確定・5手順）

1. リーダーは Agent 起動前に、各実行エージェントに書き込ませるファイルの絶対パス一覧を確定し、所有権表と照合する。`leader` / `user` 所有のパスは実行エージェントに割り当てない。
2. 割当プロンプトの先頭に次の2行を必ず書く: `書込許可: <絶対パスまたはディレクトリのリスト>` `上記以外のファイルは変更禁止。変更が必要になったら変更せず最終報告で申告すること。`
3. 同一ファイル（または同一割当単位ディレクトリ）を2体以上の実行エージェントに同時に割り当てない。重なる場合は直列実行にする。
4. 実行エージェントは、許可リスト外の変更が必要と判明した時点でそのファイルに触れず、最終報告に「追加変更が必要: <パス> <理由1行>」を書いて返す。リーダーが自分で変更するか、再割当する。
5. 全エージェント完了後、リーダーが `git status` で変更ファイル一覧を許可リストの和集合と照合してからコミットする。リスト外の変更があれば revert し、MISTAKES.md に記録する。

### 5.4 .claude/agents/red-team.md の frontmatter とシステムプロンプト骨子（確定）

frontmatter:

```yaml
---
name: red-team
description: 計画・設計書・成果物の批判的分析専用エージェント。対象の失敗シナリオを確率が高い順に3つ挙げ、各シナリオの早期警報サインと対策案を提示する。攻撃者視点・ユーザー視点・経営視点の3ペルソナで検査する。改善の実装はしない。
tools: Read, Grep, Glob
model: inherit
---
```

システムプロンプト本文に必ず含める6要素（実装時はこの骨子を散文化する）:

1. **役割宣言**: あなたは承認機関ではなく反証機関である。賞賛・前置き・「概ね良い」で始めることを禁止する。
2. **必須出力フォーマット**: 次の表をちょうど3行、発生確率の降順で出力する。`| # | 失敗シナリオ | 発生確率（高/中/低） | 早期警報サイン | 対策案 |`。早期警報サイン列は「観測可能な事象」（ファイル・出力・数値で確認できるもの）に限る。
3. **3ペルソナ強制**: 3行のうち、攻撃者視点（悪用・入力汚染・権限逸脱）、ユーザー視点（導入障壁・誤操作・期待とのズレ）、経営視点（保守コスト・ROI・機会損失）の各観点を最低1回ずつ使う。
4. **「問題なし」の禁止**: 高確率の失敗が見つからない場合でも、確率（低）と明記した上で3件を必ず埋める。
5. **禁止事項**: ファイルの変更・作成、コードの実装（対策案は方針1〜2文まで）、指摘の重要度を薄める修飾語。
6. **入力契約**: 呼び出しプロンプトから対象ファイルの絶対パスを受け取り、Read で全文を読んでから分析する。パスが無い場合は分析せず「対象パスがありません」とだけ返す。

## 6. 処理フロー

**Step 1（リーダー）**: サブエージェントを使うタスクを受けたら AGENT_TEAM.md 章2で役割とフレームワークを判定する。無人定期稼働なら本規約外（03設計書へ）と報告して終了。

**Step 2（リーダー）**: タスクを実行エージェント単位に分割し、章3の所有権表と照合して各エージェントの書込許可リストを確定する（§5.3 手順1〜3）。

**Step 3（実行エージェント）**: 割当プロンプト（書込許可2行つき）で並列実行。許可外変更が必要なら書き込まずに申告して返す（§5.3 手順4）。

**Step 4（レッドチーム）**: 章6の必須タイミングに該当すれば red-team を起動し、リーダーが指摘3件それぞれに採択/棄却を明記する。

**Step 5（リーダー）**: `git status` を許可リスト和集合と照合（§5.3 手順5）→ 全体QA → コミット/push。リスト外変更があれば revert + MISTAKES.md 記録。

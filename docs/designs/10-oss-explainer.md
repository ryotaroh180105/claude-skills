## 計画ゲート5項目（設計前に回答・skill-design-rigor §5.1）

1. **失敗する最も確率の高いパターン（3つ）**:
   ① article-writer と執筆工程が重複実装され、二重メンテになる。
   ② Claude がリポジトリを読まず／浅く読み、README の受け売り・技術的誤断定を記事にする（信頼失墜・G3価値の毀損）。
   ③ 「読解」と「執筆」の境界が曖昧で、どちらのスキルを呼ぶか実行時に毎回迷う。
2. **スコープ境界（ついでにやりそうで、やらないこと）**: 実際の note 本文執筆・タイトル生成・推敲・文体メモ運用（全部 article-writer）、OSS候補のトレンド収集（github-trends）、SEO最適化（owned-media）、リポジトリの clone 自動化やコード実行、記事のnote自動投稿。
3. **完成条件を実装者が単独で真偽判定できるか**: できる。ファイル存在・validate_skills.py・marketplace.json エントリ・ウォークスルー3件（§3）で判定。
4. **実装者が最初に詰まる箇所**: 「読解骨子（本スキル）」と「記事化（article-writer）」の受け渡しフォーマット。→ §5 で骨子の確定スキーマ（explainer-brief）を定義し、§6 で article-writer へ渡す定型プロンプトを確定。
5. **本当に必要か（既存で代替できないか）**: article-writer 単体では「OSSを正確に読解し・事実裏取りし・解説骨子を組む」前段がない。github-trends は候補を出すだけで読解しない。この前段（OSS読解 → 解説骨子抽出 → 事実裏取り）が本スキルの独自価値。代替不可。

## 1. 目的・背景（Why）

GitHub でバズっている OSS（または Ryo 指定のリポジトリ）の仕様・設計思想を、中級IT理解者（Ryo と同程度）向けに噛み砕いた **note 解説記事**にする。目的は副業の発信・実績づくり（G2/G3）。

既存では不足する点:
- **article-writer** は note 記事の企画・執筆・推敲の本体だが、「OSS を正確に読み解く」前段を持たない。専門外テーマの断定回避ルール（工程1・エッジケース）はあるが、リポジトリ読解の手順はない。
- **github-trends** は候補を ROADMAP に積むだけで、リポジトリの中身は読まない。

本スキルは **「OSS読解 → 解説骨子（explainer-brief）の抽出 → 事実裏取り」までを担い、記事化は article-writer に委譲する**。読解と執筆の責務を分離し、事実確認を hermes-relay/WebFetch で裏取りして Claude の憶測断定を防ぐ。

## 2. スコープ

### 2.1 やること

- 対象OSS選定の補助: github-trends の候補リスト or Ryo 指定リポジトリを受け取り、解説対象1本を確定する。
- リポジトリ読解: README・アーキテクチャドキュメント・主要ソース・ライセンス・スター数を GitHub MCP / WebFetch で読む。
- 解説骨子（explainer-brief）の抽出: 「何が新しいか／なぜバズったか／どう動くか／自分の仕事にどう活かすか」の4軸 + 事実台帳（要裏取り項目のリスト）を確定スキーマで書き出す。
- 事実裏取り: ライセンス・スター数・技術的主張など「断定に根拠が要る項目」を hermes-relay（notebooklm エンジン）または WebFetch で裏取りし、確認済み/未確認を分離する。
- article-writer への引き継ぎ: explainer-brief を渡す定型プロンプトで article-writer を呼び、記事化・タイトル・推敲・公開設定・ハッシュタグを委譲する。
- 対象リポジトリがカレントに無い場合の add 判断フロー（§11）。

### 2.2 やらないこと（明示的スコープ外）

- note 本文の執筆・タイトル生成・推敲・文体メモ運用 → **article-writer の担当**（重複実装禁止）。
- ハッシュタグ・公開設定（無料/有料）・導線提案 → **article-writer 工程6 の担当**。
- SEO キーワード設計・検索流入狙いの構成 → **owned-media の担当**（本スキルは検索流入を狙わない発信記事）。
- OSSトレンドの定期収集・候補リストへの追記 → **github-trends の担当**。
- リポジトリの clone 自動化・依存インストール・コードのローカル実行・ビルド（YAGNI。読解は静的閲覧で足りる。動かす必要が出たら都度Ryoに相談）。
- note への自動投稿（article-writer と同じく投稿は手動）。
- Claude 自身の WebSearch による事実裏取り（CLAUDE.md 方針。裏取りは hermes-relay 経由、WebFetch は個別ファイル取得のみ可）。
- 複数OSSの一括記事化・連載自動生成（1回1本。連載は article-writer の導線機能に任せる）。

## 5. データ構造

### 5.1 explainer-brief（解説骨子・確定スキーマ）

読解完了後にチャット出力する。article-writer にそのまま渡す入力。

```markdown
# explainer-brief: <owner/repo>

## 対象メタ（要裏取り）
- リポジトリ: <owner/repo>（URL）
- スター数: <N>（取得日 YYYY-MM-DD / 裏取り: 確認済み|未確認）
- ライセンス: <SPDX識別子>（裏取り: 確認済み|未確認）
- 主要言語 / 直近リリース: <lang> / <vX.Y.Z, 日付>

## 4軸の骨子
1. 何が新しいか: <1-3行。既存手段との差分>
2. なぜバズったか: <1-3行。話題化の理由。要裏取り項目は印>
3. どう動くか: <3-6行。アーキテクチャ・主要コンポーネント・データフロー>
4. 自分の仕事にどう活かすか: <1-3行。G1/G2/G3 のどれにどう効くか>

## 読んだ根拠（ファイル/URL）
- <README / docs/xxx / src/yyy のパス or URL を列挙。読んだ範囲を明示>

## 事実台帳（断定に根拠が要る項目）
| 主張 | 種別(license/stars/技術主張) | 裏取り手段 | 状態(確認済み/未確認) | 根拠URL |
|---|---|---|---|---|

## 未確認・断定できない点
- <裏取りできなかった/しなかった項目。記事で断定しないよう article-writer に申し送る>
```

### 5.2 対象確定の入力バリエーション

| 入力 | 扱い |
|---|---|
| Ryo が repo URL / owner/repo を明示 | その1本を対象確定 |
| github-trends の候補リスト（ROADMAP 表 or チャット）を渡された | 候補を提示し Ryo に1本選ばせる（勝手に選ばない） |
| 「最近バズってるOSSを解説して」（対象未指定） | github-trends を先に呼ぶよう案内 or Ryo に候補を1つ確認。本スキルはトレンド収集をしない |

## 6. 処理フロー

**Step 0 — 対象確定**: §5.2 で対象1本を確定。未指定なら github-trends に振るか Ryo に確認（本スキルは収集しない）。

**Step 1 — 読解可能性の確保（add 判断）**: 対象リポジトリがカレントに無い場合、§11 の add 判断フローに従う。読むだけなら GitHub MCP（`mcp__github__get_file_contents` 等）/ WebFetch で足り、セッションへの add は原則不要。

**Step 2 — 読解**: README → アーキテクチャ/docs → 主要ソース（エントリポイント・コア module）→ LICENSE の順に読む。GitHub MCP 優先、無ければ WebFetch（raw.githubusercontent.com / github.com のファイルビュー）。読んだファイル/URL を全て控える（brief の「読んだ根拠」に入れる）。

**Step 3 — brief 抽出**: §5.1 スキーマで4軸 + 事実台帳を埋める。断定に根拠が要る項目（ライセンス・スター数・「業界初」等の技術主張）は事実台帳に「未確認」で登録する。

**Step 4 — 事実裏取り**: 事実台帳の「未確認」項目を裏取りする。
- 技術主張・比較・「なぜバズったか」の外部評価 → **hermes-relay（`engine: notebooklm` + `topic:`）** に1本 enqueue。手順は hermes-x-search SKILL.md が正。必須セクション: 根拠URL（主張ごと1本）・未確認点。
- ライセンス・スター数・リリースなど GitHub 上の一次情報 → **WebFetch で当該ページを直接取得**（リレー不要な確定的一次情報）。
- 裏取り結果で台帳の状態を確認済み/未確認に更新。裏取りできない項目は「未確認」のまま brief の「未確認・断定できない点」に転記。

**Step 5 — article-writer へ委譲**: 下記定型プロンプトで article-writer を呼ぶ。

```
article-writer スキルで note 解説記事を作成してください。ネタと骨子は
以下の explainer-brief で確定済みです。切り口設計（工程1）はこの brief の
4軸を素材にし、想定読者は「中級IT理解者（GitHubは使うがこのOSSは未知）」
で固定。以降、タイトル案（工程2）・構成・執筆・推敲・公開設定・ハッシュタグ
（工程6）は article-writer の標準手順どおりに進めてください。

制約:
- 「未確認・断定できない点」セクションの項目は記事で事実として断定しない
  （体験・伝聞・「〜とされる」表現に落とすか、書かない）。
- 事実台帳で「確認済み」の数値・ライセンスのみ本文に載せる。
- 文体メモは article-writer の分岐に従う。

<explainer-brief 全文を貼付>
```

**Step 6 — 引き継ぎ後**: 本スキルの出口は Step 5 まで。記事本文・タイトル・推敲の品質は article-writer が担保する。本スキルは記事本文を自前で書かない。

## 7. エッジケース

| ケース | 期待挙動 |
|---|---|
| 対象OSS未指定 | github-trends に振るか Ryo に1本確認。トレンド収集を本スキルでやらない |
| リポジトリが巨大でソース全読不可 | エントリポイント + コア module + README/docs に絞る。読んだ範囲を brief に明示し、未読部分由来の断定をしない |
| README がマーケ寄りで技術実体が薄い | ソースと Issue/PR から実体を補う。それでも不明な点は事実台帳「未確認」に落とす |
| ライセンスが記事化・引用に制約（コード転載の可否） | LICENSE を確認し、コード引用は必要最小限。ライセンス種別を brief に記載し、article-writer に申し送る |
| hermes-relay watcher がダウン/タイムアウト | hermes-x-search の手動フォールバックを Ryo に案内。裏取りできない項目は「未確認」のまま進め、記事で断定しない（止めない） |
| GitHub MCP も WebFetch も対象取得に失敗 | 1回再試行 → ダメなら「読解不能」と報告し記事化に進まない（浅い受け売り記事を作らない） |
| Ryo が指定したリポジトリが private / 存在しない | 取得失敗として報告。add が必要なら §11。憶測で内容を書かない |
| 「なぜバズったか」の根拠が取れない | 断定せず「話題の理由は諸説あり」等に留め、未確認セクションに記載 |

## 11. 実装時判断ルール

- **add 判断フロー**: リポジトリ読解は原則 GitHub MCP / WebFetch の静的閲覧で行い、**セッションへの `add_repo` はしない**（読むだけなら不要）。CLAUDE.md の add_repo は「ユーザーが明示的に add を頼んだ時のみ」起動するルール。Ryo が「このリポジトリをセッションに入れて中を歩いて解説して」等と明示した場合に限り add_repo → clone → register_repo_root を行う。本スキルが自律的に add しない。
- **事実裏取りの経路振り分け**: 一次情報（LICENSE/スター数/リリース）= WebFetch 直接取得。二次評価（技術主張の妥当性・なぜバズったか）= hermes-relay notebooklm。Claude 自身の WebSearch は使わない（CLAUDE.md 方針、メタ用途のみ）。
- **断定の禁則**: 事実台帳で「確認済み」でない数値・ライセンス・技術主張を記事本文に断定として載せない。§6 定型プロンプトでこれを article-writer に申し送る。
- **委譲の徹底**: 記事本文・タイトル・推敲・ハッシュタグ・公開設定は本スキルで書かない。全て article-writer を呼ぶ。SEO 狙いなら owned-media に振る（Ryo に確認）。
- **SKILL.md 文体**: 既存 article-writer / github-trends の SKILL.md に合わせる。lite/full 強度区分は設けない。
- **対象選定**: github-trends 候補や複数候補があるとき、本スキルは1本を勝手に選ばず Ryo に選ばせる。
- CLAUDE.md への常時適用ルール追加はしない（§12）。

## Biz-Ops Guard: Go/No-Go ラダー（G3割り切り適用）

適用範囲: 他人にも使ってほしいスキル（Ryo 自身が主ユーザー、副次的に同種の発信者）。G2/G3 目的なので、No は「意図的に無視」明記で進めてよい。

1. **想定ユーザーを固有名詞で3人**: ①Ryo本人（副業note発信）②同じ独学IT就活生層（想定読者かつ潜在利用者）③（仮置き・調査中）技術発信を始めたいインターン仲間。→ **実質 Ryo 専用に近い。G3割り切りで Yes 扱い**。
2. **代替手段からの乗り換え理由（1文）**: 「ChatGPT に『このOSS解説して』と聞くのと違い、リポジトリを実際に読んで根拠URL付き・事実裏取り済みの骨子を出し、そのまま自分の文体で note 記事化まで繋がる」。→ **Yes**。
3. **導入5分・3ステップ以内**: `/plugin install` → 対象URLを投げる → 記事化。前提は hermes-relay 既設（他スキルと共通、本スキル起因の新規セットアップなし）。→ **Yes**。
4. **保守予算（週N分）**: 週10分上限。壊れる要因は GitHub MCP/WebFetch のIF変更・hermes-relay 停止・article-writer 側の工程変更。→ **Yes**。
5. **最初の10ユーザーへの経路**: 生成した解説記事自体が note で配布物になり、記事末尾で「この記事はこう作った」と発信＝スキルの広報を兼ねる。→ **Yes（仮置き・実績で検証）**。

判定: **Go**（G3割り切り。ユーザー①②が実質 Ryo 圏内である点は意図的に無視）。

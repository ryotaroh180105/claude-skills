## 1. 目的・背景（Why）

MISTAKES.md には個別ミスを都度記録する運用（UC1）が既にあり、`docs/mistakes-db-design.md`
の UC6 は「定期レビュー（多いミスの種類・CLAUDE.md 昇格候補・廃止候補の棚卸し、月1程度）」を
想定している。しかし **誰がいつ起動するかが未定義**で、放置すると (a)再発防止ルール行が20行上限
（UC7）を超えて注入コストが膨らむ、(b)一般化できるルールが CLAUDE.md へ昇格されないまま埋もれる、
(c)特定タスク限定の廃止候補が active のまま残り注入枠を食う、という腐敗が起きる。

本設計は、この「溜まったミスの棚卸し」を loop-engineering の6要素で自律ループとして定義し、
**LOOPS.md に1エントリとして追加**する。ミスの「都度記録」（UC1、既存）には手を触れず、
その後段の「週次〜月次の集計・昇格提案・統合・削減」（UC6/UC7）だけを対象にする。
昇格・統合・廃止は自動確定せず、提案シートを生成してユーザー承認に回す（承認制）。

## 5. データ構造

### 5.1 Trigger の起動条件（確定）

自己発見（カウンタゲート）。次のいずれかを満たしたセッションで起動を検討する:

- 再発防止ルール行が16行以上（上限20の80%）。
- 前回リフレクション以降に登録された、ステータス=active の新規 M-NNN が5件以上。
- 前回リフレクションから4週間以上経過し、かつ上記いずれかのカウントが1以上。

起動直後にまず件数を数え、**対象が0件なら「棚卸し不要」と1行報告して終了**する（空回り禁止）。
時刻 Routine を併用する場合、Routine は上記カウンタ確認を促すリマインダに徹し、
無条件で棚卸しを実行しない（CLAUDE.md #5「時刻ベースの定期棚卸しは行わない／イベント駆動に
一本化」および MISTAKES.md 運用ルールとの整合。§11 参照）。

「前回リフレクション日」は LOOPS.md 本エントリの履歴行の最新日付を正とする（§5.5）。

### 5.2 Doer が生成する提案シート（Markdown、確定フォーマット）

```markdown
## ミス学習リフレクション提案シート YYYY-MM-DD

- 集計対象: 前回リフレクション(YYYY-MM-DD)以降の active 新規 N件 / 全 active M件 / 再発防止ルール R行(上限20)

### カテゴリ別集計
| カテゴリ | 新規 | うち再発あり |
|---|---|---|
| 誤答 | n | n |
| 手順ミス | n | n |
| ... | | |

### 昇格提案（CLAUDE.md へ）
- [M-NNN] 理由: 複数セッション/複数カテゴリで再発し特定タスクに依存しない → CLAUDE.md 常時適用ルール §X へ

### 統合提案（再発防止ルール行の統合）
- [M-AAA]+[M-BBB] 同カテゴリ・同趣旨 → 統合後の1行案: 「...」（情報欠落なしを確認）

### 廃止提案（ステータス→廃止）
- [M-NNN] active 化から一定期間再発ゼロ・1回限り・特定タスク限定 → 廃止(<理由>)

### 行数削減（R>20 のときのみ必須、16<=R<=20 は推奨）
- 適用後の再発防止ルール行数見込み: R' 行
```

- 昇格・統合・廃止のいずれも「提案」であり、MISTAKES.md/CLAUDE.md の実書き換えはこのシートには
  含めない（PR で別途行い、マージは承認制）。

### 5.3 Verifier のルーブリック（確定）

各提案を Doer とは別 Agent が判定する。判定値は `妥当 / 過剰 / 不明` の3値。

| 提案種別 | 合格基準（妥当） | 棄却基準（過剰） |
|---|---|---|
| 昇格 | 2回以上の再発、または2セッション以上・2カテゴリ以上にまたがり、特定タスク非依存 | 1回限り・特定タスク限定のものを昇格しようとしている |
| 統合 | 統合後の1行で元の根本原因が両方読み取れる | 異なる根本原因を1行に潰し情報が落ちる |
| 廃止 | 特定タスク限定かつ再発ゼロで、再発時の実害が小 | active のまま再発リスクや実害が残る（廃止は保守的に） |
| 行数削減 | 適用後の行数見込み R' ≤ 20（機械カウントで確認） | 削減後も R' > 20、または必要ルールを削って上限に収めている |

判定不能な提案は「不明」と明示させ、合格/不合格を決めつけさせない。過剰と判定した提案は
提案シートから落とす（YAGNI の棄却も Verifier の責務）。

### 5.4 Stop Rules（確定）

- **成功条件**: 1周＝件数確認→抽出→集計→4種提案生成→Verifier 検証→提案シート提示、まで。
  対象0件なら「棚卸し不要」で即終了（成功扱い）。
- **安全上限**: Doer 1体・Verifier 1体まで。内側の Doer↔Verifier 往復は最大3回。1周30分以内。
  3周（＝3回の提案差し戻し）で収束しなければ停止し Ryo に相談する。
- **Human gate**:
  - MISTAKES.md / CLAUDE.md の実際の書き換えは **PR 作成まで**。マージ（昇格・統合・廃止の確定）は
    Ryo の承認必須。自動確定は禁止（M-002 の教訓＝常時適用ルールの改変・大量行削除を無確認で
    実行しない）。
  - 廃止・行削減で MISTAKES.md の再発防止ルール行を削る場合は、M-002 ルールに従い削除規模
    （削る行数・対象 M-NNN）を提示して個別承認を取る。
  - CLAUDE.md への昇格提案は、CLAUDE.md #5 に従い同 PR 内で既存ルールとの重複・矛盾点検結果を
    添える。

### 5.5 Memory / State（確定）

- 保存先: LOOPS.md 本エントリの `- 履歴:` 行。1周ごとに `YYYY-MM-DD 対象active N件/ルールR行/
  提案(昇格a・統合b・廃止c)・採否<PR番号 or 見送り>` を追記。
- この履歴の最新日付が §5.1 の「前回リフレクション日」になる。MISTAKES.md 側には状態を持たせない
  （スキーマ非変更）。

## 6. 処理フロー

1. **起動判定（Trigger）**: セッションが §5.1 の起動条件を評価。`git pull` 後、MISTAKES.md から
   ①ステータス=active の全件数 ②前回リフレクション日（LOOPS.md 履歴の最新日付）より後に登録された
   active 件数 ③`<!-- rules:start -->`〜`<!-- rules:end -->` 間の再発防止ルール行数、を数える。
   対象（②または行数超過分）が0なら「棚卸し不要」と報告して終了。
2. **抽出（Doer）**: 前回リフレクション日より後に登録された active エントリを記録ログから抽出し、
   各エントリの カテゴリ / 再発回数 / 環境 / 特定タスク依存かどうか を読み取る。
3. **集計（Doer）**: カテゴリ別件数と再発あり件数を §5.2 の表に整形。
4. **4種の提案生成（Doer）**:
   - 昇格: 2回以上再発 or 2セッション・2カテゴリ以上・特定タスク非依存のものを CLAUDE.md 昇格候補に。
   - 統合: 再発防止ルール行のうち同カテゴリ・同趣旨の2行以上を1行案に統合。
   - 廃止: 特定タスク限定・再発ゼロ・実害小のものを廃止候補に。
   - 行数削減: 現行行数 R が 20 超なら削減必須、16〜20 なら推奨。統合・廃止・昇格の適用後見込み R' を算出。
5. **検証（Verifier、別 Agent）**: §5.3 ルーブリックで各提案を 妥当/過剰/不明 判定。過剰はシートから
   除外。行数は適用後 R' ≤ 20 を機械カウントで確認。差し戻しは最大3回（§5.4）。
6. **提示（Doer）**: 妥当と判定された提案のみで §5.2 の提案シートを生成し、ユーザーに提示。
   採用分は PR として MISTAKES.md/CLAUDE.md へ反映（マージは Ryo 承認）。
7. **記録（Memory）**: LOOPS.md 履歴行に結果を追記して終了。

## 7. エッジケース

| ケース | 期待挙動 |
|---|---|
| 対象 active 新規0件・行数20以下 | 「棚卸し不要」を1行報告して即終了（Doer/Verifier を起動しない） |
| 再発防止ルールが既に20行超 | 行数削減を「必須」扱い。統合・廃止・昇格だけで R' ≤ 20 に収まらなければ Ryo に相談（機械的に必要ルールを削らない） |
| 同一ミスの再発が集中（1件が何度も再発） | 昇格候補として最優先。統合ではなくルール文の強化＋CLAUDE.md 昇格を提案 |
| LOOPS.md に本エントリの履歴が未だ無い（初回） | 「前回リフレクション日」を MISTAKES.md 内の最古の登録日として全 active を対象にする |
| 昇格提案が CLAUDE.md 既存ルールと重複 | Verifier が過剰判定。または「既存ルールへの統合」として提案（新規追記しない）。CLAUDE.md #5 の点検を PR に添付 |
| M-001 のように CLAUDE.md へ既記載だがログが active | 「ステータスを昇格済み(CLAUDE.md) に更新」を提案（ルール行は他環境注入用に残すかを Ryo 判断） |
| Doer↔Verifier が3往復しても収束しない | 停止して現状の提案シート（未収束と明記）を Ryo に渡し相談 |
| push が non-fast-forward で失敗 | mistakes-db-design §4 の採番プロトコルに従い pull → 衝突確認 → 再 push |

## 11. 実装時判断ルール

- **CLAUDE.md #5 / MISTAKES.md 運用ルールとの整合**: 「時刻ベースの定期棚卸しはしない／イベント駆動に
  一本化」に従い、Trigger の主体は §5.1 のカウンタ（自己発見）にする。時刻 Routine を作る場合でも
  無条件実行にせず、必ず件数確認を先頭に置く（無条件の時刻棚卸しは作らない）。
- **biz-ops-guard 品質改善ループとの役割境界**（CLAUDE.md #5 の重複点検要求への回答）: あちらは
  スキル SKILL.md の品質を test-log.md で回すループ。本ループは**ミスDBの再発防止ルールを
  MISTAKES.md/LOOPS.md 上で棚卸しする**ループ。対象ファイル・目的が別で重複しない。この1行を
  LOOPS.md エントリにも明記する。

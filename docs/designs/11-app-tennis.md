## 1. 目的・背景（Why）

元要求は「テニスのやつをアプリとしてデプロイ、実運用に乗せる」（`docs/fable5-design-assets.md` §4.2）。
要求が「テニスの何を扱うか」を特定していないため、requirements-definition の思考で用途を分解し、
ユーザー本人が使う前提で最も価値の高い1用途に MVP を絞る。

**イシュー**: 「アマチュアテニスプレイヤー（ユーザー本人）が、試合の勝敗・スコア・相手・コート種別を
その場で記録し、後から勝率と傾向を振り返れる状態にするには何が必要か」。

用途候補と評価（requirements-definition Step 1 の2軸: 解く価値 × 単独MVPで答えを出せるか）:

| 候補 | 解く価値 | MVP実現性（単一ユーザー・バックエンドなし） | 判定 |
|---|---|---|---|
| A. 試合結果ログ（勝敗・スコア・相手・コート記録） | 高（毎試合発生、後の分析の土台） | 高（localStorage のみ、認証不要、オフライン可） | **MVP採用** |
| B. 練習ログ（練習メニュー記録） | 中 | 高 | Phase 3 |
| C. 上達分析（記録データから勝率・傾向を算出） | 高 | 中（先に A のデータが要る） | Phase 2 |
| D. 戦術・相手スカウティングメモ | 中 | 高 | Phase 3（A の memo 欄で暫定代替） |
| E. 対戦相手マッチング | 高だが用途が別物 | 低（複数ユーザー・認証・バックエンド・ネットワーク効果が必須で MVP 不適） | 不採用（§2.2） |

**MVP は A（試合結果ログ）**。理由: 発生頻度が最も高く即座に価値が出る、データ構造が単純、
認証・バックエンド・オンライン通信が一切不要でコート脇（電波なし）でも動く、C の分析の入力になる。
「A に絞る」ことは仮説であり、ユーザー本人の実際のニーズ（試合をよくやるのか／練習中心か）で
変わりうるため §12 に確認事項として残す（勝手に確定しない）。

本アプリの位置づけは **ユーザー本人専用ツール兼デプロイ実績づくり（G3）**。他人配布は Phase 2 以降の判断
（§8 のビジネス運用面参照）。よって biz-ops-guard は「G3・自分専用」として Go/No-Go ラダーを通し、
他人向け項目は「意図的に無視」を明記する（暗黙に無視しない）。

## 2. スコープ

### 2.1 やること（MVP = Phase 1）

- 別リポジトリ `ryotaroh180105/tennis-app`（1アプリ1リポジトリ、`04` §5.1 分類E）で新規作成
- 技術スタック: **Vite + React + TypeScript**、デプロイ **Vercel 無料枠**（選定根拠 §5.4）
- 試合レコードの**追加・一覧表示・編集・削除**（CRUD）。一覧は日付降順
- **集計バー**: 総試合数・勝ち数・負け数・勝率（%）を一覧上部に常時表示
- **データ永続化**: ブラウザ `localStorage`（バックエンド・DB なし。§5.2 のキーとスキーマで確定）
- **JSON エクスポート／インポート**: localStorage 消失対策 + データ持ち出し（biz-ops の出口設計）
- **PWA**: Service Worker でオフライン動作 + ホーム画面インストール（「実運用に乗せる」の実体）
- Vercel で公開 URL を得て、スマホのホーム画面に追加して1試合分を実記録するまでを完了とする

### 2.2 やらないこと（明示的スコープ外）

- **ポイント単位のライブスコアリング**（デュース・タイブレーク・ゲーム/セットの逐次進行）— MVPでは
  試合後に最終スコアを文字列1フィールドで記録する。ライブ計時は Phase 2 候補（YAGNI・実装量が数倍）
- **対戦相手マッチング（候補E）** — 複数ユーザー・認証・バックエンド・ネットワーク効果が必須で MVP と別物（別設計書相当）
- **ユーザー認証・ログイン・アカウント** — 単一ユーザー・単一端末前提のため不要（§5.3 で確定）
- **サーバー／DB／API** — localStorage で足りる。バックエンドを持つと無料枠運用・保守コストが跳ねる（YAGNI）
- **複数端末間の同期・クラウドバックアップ** — localStorage は端末ローカル。同期は JSON 手動エクスポートで代替（Phase 2 で要否判断、§12）
- **練習ログ（B）・戦術メモ専用画面（D）・分析グラフ（C）** — Phase 2/3。MVP では memo 自由記述欄で暫定代替
- **多言語対応・ダークモード切替 UI・テーマ設定** — YAGNI。日本語 UI 固定、OS のカラースキームに従うのみ
- **独自ドメイン取得** — Vercel の `*.vercel.app` サブドメインで足りる（費用ゼロ）
- **アナリティクス・監視ダッシュボード** — ユーザー1人に不要（biz-ops のやりすぎ防止）

## 5. データ構造

### 5.1 Match レコード型（`src/types.ts`・確定）

```typescript
export type Surface = "hard" | "clay" | "grass" | "carpet" | "omni";
export type MatchType = "singles" | "doubles";
export type Result = "win" | "loss";

export interface Match {
  id: string;          // crypto.randomUUID() で採番
  date: string;        // "YYYY-MM-DD"
  opponent: string;    // 相手名（自由記述、空文字許容）
  result: Result;      // 勝敗
  score: string;       // 最終スコア自由記述。例 "6-4 3-6 7-5"
  surface: Surface;    // コート種別
  matchType: MatchType;// シングルス/ダブルス
  memo: string;        // 自由記述（戦術メモの暫定代替）
  createdAt: string;   // ISO8601
  updatedAt: string;   // ISO8601
}
```

### 5.2 localStorage スキーマ（`src/storage.ts`・確定）

- キー: `"tennis-app:matches:v1"`（バージョン付き。将来のマイグレーション用）
- 値: `Match[]` を `JSON.stringify` した文字列
- 空・未設定・JSON パース失敗時は空配列 `[]` として扱う（§7）
- エクスポート: 現在の `Match[]` を `tennis-app-YYYY-MM-DD.json` としてダウンロード
- インポート: ファイルの JSON を `Match[]` として検証（配列であること・各要素に `id` `date` `result` があること）し、
  既存を**置換**（マージしない。MVP は単純置換で確定。マージは §12）

### 5.3 認証・オフライン・永続化の確定判断

| 論点 | 決定 | 根拠 |
|---|---|---|
| 認証 | **なし** | 単一ユーザー・単一端末・機微情報なし。認証はバックエンドを呼び込むため MVP に不要 |
| 永続化 | **localStorage**（DB なし） | データ量が小さく単一端末で足りる。DB/バックエンドは無料枠運用と保守を増やす |
| オフライン | **必須**（PWA + SW） | コート脇は電波が弱い。オフラインで記録できることが実運用の要件 |
| 複数端末同期 | **MVPでは非対応**（JSON 手動移送で代替） | クラウド同期はバックエンド+認証を呼ぶ。Phase 2 で要否判断（§12） |

## 6. 処理フロー

**起動時**: `main.tsx` が SW を登録 → `App` が `storage.load()` で `Match[]` を読む（失敗時は `[]`）→
`SummaryBar` に `stats.summarize(matches)` の結果、`MatchList` に配列を渡して描画。

**追加**: `MatchForm`（新規モード）に入力 → 保存 → `id`=`crypto.randomUUID()`、`createdAt`/`updatedAt`=現在時刻を付与し
配列先頭に追加 → `storage.save()` → 再描画。

**編集**: 一覧行の「編集」→ `MatchForm`（編集モード、既存値プリフィル）→ 保存 → 該当 `id` を差し替え
`updatedAt` 更新 → `storage.save()` → 再描画。

**削除**: 一覧行の「削除」→ 確認ダイアログ（`window.confirm`）→ OK で該当 `id` を除外 → `storage.save()` → 再描画。

**集計**: `stats.summarize` が `total`=件数、`wins`=`result==="win"` の数、`losses`=残り、
`winRate`=`total===0 ? 0 : Math.round(wins/total*100)` を返す。

**エクスポート**: 現配列を Blob 化しリンククリックでダウンロード。
**インポート**: `<input type=file>` → 読み込み → JSON パース → §5.2 の検証 → 検証通過なら置換保存し再描画、失敗なら
アラートで理由表示し状態を変えない。

## 7. エッジケース

| ケース | 期待挙動 |
|---|---|
| localStorage が空／未設定 | `[]` として起動。集計バーは「総0 勝0 負0 勝率0%」 |
| localStorage の値が壊れた JSON | パース失敗を握り `[]` にフォールバック。コンソールに警告（データは上書きせず、次回保存時に正常化） |
| localStorage が使用不可（プライベートモード等で例外） | 保存時に try/catch し、画面に「この環境では保存できません（データは失われます）」と1行表示。読み書きはメモリ上で継続 |
| インポートファイルが配列でない／必須キー欠落 | 置換せずアラート「不正なファイルです」。既存データは保持 |
| opponent・score・memo が空 | 許容（必須は date と result のみ。フォームで date と result 未入力は保存不可） |
| 大量レコード（数百件） | localStorage 上限（5MB前後）まで問題なし。1件約300バイトで1万件でも収まる。上限対応は §12 送り |
| Service Worker が古いキャッシュを返す | vite-plugin-pwa の `registerType: "autoUpdate"` で新版を自動取得。手動更新 UI は作らない（YAGNI） |
| 日付未来／不正 | `<input type="date">` の値をそのまま保存（バリデーションしない。単一ユーザーの自己入力のため過剰検証は YAGNI） |

## 8. 失敗シナリオとレッドチーム所見

**計画ゲート回答**（skill-design-rigor §5.1）:
(1) 失敗パターン上位3件は下表。
(2) やらない境界は §2.2（特にライブスコアリング・マッチング・バックエンド・認証を「ついでにやりそう」として明示禁止）。

(5) 必要性: 既存スキル・アプリに代替なし（テニス記録アプリは本リポジトリに存在しない）。

- 収益/回収: 収益なし。回収は「デプロイ実績・PWA/React の学習」（G3）
- 記録する指標: 自分の利用記録（何試合入力したか）のみ。新規/再利用/紹介は自分専用のため N/A
- 意図的に無視すること: 他人配布・マーケ・課金・複数端末同期・ライブスコアリング（すべて Phase 2 以降）
- 悪魔の代弁者: （§実装前にサブエージェント1体でシートを検査。指摘3件と処理を tennis-app/docs/biz-ops.md に残す）

Go/No-Go ラダー結果: 想定ユーザー=本人1名で「自分専用ツール → biz-ops 適用外だが G3 として通す」。
配布・乗り換え経路は「意図的に無視」。→ **Go（自分専用 MVP として着手可）**。

## 9. 実装手順（Sonnet 向けタスク分割）

順序依存: 1→2→3→4→5→6→7。実装は tennis-app リポジトリで行う。

1. **リポジトリ作成 + 雛形** — `ryotaroh180105/tennis-app`（public/private はユーザー確認、§12）を作成し、
   Vite の `react-ts` テンプレートで初期化。完了条件: `npm ci && npm run build` が exit 0。
2. **データ層** — `types.ts`（§5.1）・`storage.ts`（§5.2、load/save/export/import + フォールバック）・

## 1. 目的・背景（Why）

ユーザー（ITコンサル系インターン）は、上司からのフィードバックが散発的に来るだけで、
「評価者が何を期待していて、自分の成果物がどこでズレているか」を横断的に把握する
仕組みを持っていない。既存スキルはいずれも**単一タスクの品質**を上げるもの
（work-approach-playbook = 1タスクの進め方、document-creation = 1書類の型）で、
**複数タスク・複数フィードバックを跨いだ傾向分析と成長戦略の立案**を担うものがない。

本スキルは、蓄積したフィードバックログと制作物から
①評価軸のズレ診断 ②技術成果のROI翻訳 ③ティア別アクションリスト生成
を再現可能な手順で行い、「業務改善・評価最大化アクションリスト」を出力する。

派生要求「コンサル業務向上スキル」（fable5-design-assets.md §1.2）は、本スキルの
ROI翻訳テンプレートと診断観点をクライアント提案向けに転用する**モード5**として
本スキル内に吸収する（別スキルは作らない。§6 モード5 参照）。

## 5. データ構造

### 5.1 ローカルデータディレクトリ（実データ置き場。public リポ外）

- 場所: 環境変数 `GROWTH_DATA_DIR`。未設定時は `~/growth-data`。
- 実在の人名・企業名・フィードバック原文・制作物抜粋は**ここにのみ**書く。
  スキル本体（plugins/ 以下）とこの設計書には架空名しか書かない。
- ユーザーが private リポジトリとして git 管理するかは任意（§12）。スキルは
  ディレクトリの存在だけを前提とし、git 操作はしない。

```
$GROWTH_DATA_DIR/
├── profile.md                       # 所属・役割・業務内容・時間単価
├── companies/<会社slug>.md          # 所属先・クライアント別の企業情報
├── feedback/YYYY-MM-DD-<slug>.md    # フィードバック1件 = 1ファイル
├── artifacts/YYYY-MM-DD-<slug>.md   # 制作物1件 = 1記録ファイル（本体はコピーしない）
├── reports/YYYY-MM-DD-diagnosis.md  # 診断結果（モード2の出力）
├── reports/YYYY-MM-DD-roi-<slug>.md # ROIレポート構成案（モード3の出力）
└── actions/ACTIONS.md               # 最新のアクションリスト（モード4が上書き更新）
```

**feedback ファイル**（frontmatter + 本文は発言の原文引用）:

```markdown
---
date: 2026-07-03
source: 上司M                # 実名可（このディレクトリ内のみ）
task: 週次進捗レポート作成
axes: []                     # 診断（モード2）実行時に A1〜A7 を付与。記録時は空
---
「最初に結論を書いて。経緯から始まると何が言いたいか分からない」
「工数削減って書いてあるけど、何時間がいくらになったの？」
```

**artifacts ファイル**（制作物本体はコピーせずパス参照＋抜粋）:

```markdown
---
date: 2026-07-02
title: 週次進捗レポート v2
type: 資料                   # 資料 / コード / メール / 議事録 の4値
location: <元ファイルのパスまたはURL>
related_feedback: [2026-07-03-weekly-report]
---
## 診断用抜粋（冒頭の構成のみ。クライアントコードは抜粋も禁止、location 参照のみ）
1. 今週の作業経緯
2. 発生した課題
3. 結論と依頼事項
```

**profile.md**（必須項目）: 氏名、所属、役割、主業務（箇条書き）、
時間単価（円/時。不明時は `3000（仮置き）` と記載）、companies/ への一覧リンク。

**companies/<slug>.md**（必須項目）: 会社名、自分との関係（所属 / クライアント の2値）、
事業内容3行以内、その会社で価値とされる語彙（例: コスト削減、利益率、リードタイム）、
担当案件一覧。

### 5.2 診断観点（A1〜A7。references/diagnosis-axes.md に収録する確定内容）

各観点は 0（乖離大）/ 1（部分的）/ 2（期待どおり）の3値。**スコアには証拠
（feedback からの引用 or artifacts の抜粋）を必ず併記する。証拠がなければ
スコアではなく「-（証拠不足）」と記録する。**

| ID | 観点 | 2 の基準 | 1 の基準 | 0 の基準 |
|---|---|---|---|---|
| A1 | 結論ファースト | 直近の対象制作物すべてで冒頭3行以内に結論・依頼事項がある | 一部の制作物のみ冒頭に結論がある | 経緯・作業ログから始まる制作物が過半 |
| A2 | データ根拠 | 定量的な主張すべてに数値と出典が付く | 数値はあるが出典・計算式がない | 「改善した」「効率化した」と形容詞のみ |
| A3 | 読者視点の構成 | 読み手の意思決定に必要な順で並び、読み手の行動依頼が明記される | 構造化はされているが自分の作業順 | 読み手が何をすべきか読み取れない |
| A4 | スコープ遵守 | 依頼範囲どおり。追加作業は事前合意済みのみ | 依頼にない作業が混入するが少量 | 依頼範囲の未達＋依頼外作業の混入が同時にある |
| A5 | 報連相タイミング | 詰まりを15分以内に共有、中間報告あり | 報告はあるが完成直前のみ | 完成後に初めて共有し手戻り発生 |
| A6 | 完了定義の事前合意 | 着手前に完了条件・形式を文章で合意 | 口頭確認のみで記録なし | 未確認のまま着手 |
| A7 | 事業価値への接続 | 技術成果がコスト・売上・時間の語彙（companies/ の価値語彙）で説明される | 技術指標（行数・速度）のみで説明 | 成果の説明自体がない |

**優先度の算出（確定式）**: `priority(軸) = (2 − score) × (1 + 直近30日のfeedbackで当該軸にタグ付いた件数)`。
priority 上位2軸を「今週の修正ポイント」とし、モード4の Tier S 入力にする。
同点は A 番号の小さい方を優先。

### 5.3 ROI翻訳（references/roi-template.md に収録する確定内容）

**計算式（確定）**: `月次効果額（円） = 削減時間（分/回） ÷ 60 × 実施回数（回/月） × 時間単価（円/時）`。
年次効果額 = 月次 × 12。時間単価は profile.md から取得し、仮置き値の場合は
レポートに「仮置き: 3,000円/時 — 要確認」と明記する。
コスト削減以外（売上増・品質向上）は計算式に乗らないため「定性効果」欄に分離して書き、
金額欄に混ぜない。

**ROIレポート構成案（章立て確定・この順）**:

1. 結論 — 月次効果額と一言サマリ（1〜2文）
2. 計算根拠 — 上記計算式の各変数と測定方法
3. 前提と仮置き — 未確認の変数一覧（確認先つき）
4. 定性効果 — 金額換算しない効果（属人化解消、ミス率、対応速度）
5. 限界とリスク — 効果が出ない条件、保守コスト
6. 依頼事項 — 読み手にしてほしい判断・行動

清書（トーン調整・体裁）は document-creation スキルに委譲する。本スキルの出力は
`reports/YYYY-MM-DD-roi-<slug>.md` の構成案までとする。

### 5.4 アクションリスト `actions/ACTIONS.md`（スキーマ確定）

```markdown
# 業務改善・評価最大化アクションリスト（YYYY-MM-DD 診断より）

## 今週の修正ポイント（診断 priority 上位2軸）
- A1 結論ファースト（priority 6）
- A7 事業価値への接続（priority 4）

| ID | Tier | アクション（動詞＋対象＋完了条件） | 根拠 | 期限 | 状態 |
|---|---|---|---|---|---|
| S-01 | S | 週次レポートの結論ファーストテンプレを作り次回レポートで使用する | A1 | 2026-07-10 | todo |
| A-01 | A | 自動化スクリプトのROIレポート構成案を作成し上長に提出する | A7 / roi-2026-07-06 | 2026-07-13 | todo |
```

- ID は `S-NN` / `A-NN` 連番。状態は todo / doing / done の3値。
- アクション文は「動詞＋対象＋完了条件」を1文に含める。完了条件のない行は書かない。
- モード4実行時は既存 ACTIONS.md の done 行を末尾「## 完了済み」へ移してから上書きする。

**ティア分類の決定表（上から順に評価し、最初に該当した行で確定）**:

| 順 | 条件 | 分類 |
|---|---|---|
| 1 | 診断 priority 上位2軸のズレを直すアクション | Tier S |
| 2 | 同種作業が過去に2回以上発生している、または月2回以上の発生見込みがあり、テンプレ化・自動化で再発工数を減らすアクション | Tier S（構造化・自動化） |
| 3 | 上司・クライアントへの新規提案・分析・設計を伴うアクション | Tier A（戦略設計） |
| 4 | 上記いずれにも該当しない | リストに載せない（ユーザーに口頭報告のみ） |

## 6. 処理フロー（5モード）

**モード0: セットアップ**（発動語:「成長戦略エンジンをセットアップして」）
入力: なし → 処理: `GROWTH_DATA_DIR`（未設定なら `~/growth-data`）の存在確認 →
なければ templates/growth-data-init/ をコピーして作成し、profile.md の必須項目
（§5.1）をヒアリングして埋める。サンプルファイルは「削除してよい」と案内する →
出力: 初期化済みディレクトリ。

**モード1: 記録**（発動語:「フィードバックを記録して」「この制作物を記録して」）
入力: フィードバック内容 or 制作物情報 → 処理: §5.1 のスキーマで feedback/ または
artifacts/ に1ファイル作成。1件の記録はヒアリング1往復以内で完了させる →
出力: 追記されたファイルパスの報告。

**モード2: ズレ診断**（発動語:「ズレ診断して」「評価軸を分析して」）
入力: feedback/・artifacts/ の全ファイル（前回診断以降が対象。初回は全件）→
処理: ①各 feedback に A1〜A7 のタグを付与し frontmatter の `axes` を更新
②各軸を §5.2 基準でスコアリング（証拠引用必須）③priority 算出 →
出力: `reports/YYYY-MM-DD-diagnosis.md`。内容は「軸 / 現場の期待（§5.2 の 2 基準）/
現状の証拠（引用）/ スコア / priority / 修正ポイント1文」の7行表＋上位2軸の宣言。

**モード3: ROI可視化**（発動語:「ROIレポートにして」「事業価値に翻訳して」）
入力: 対象の技術的成果（artifacts/ の1件 or 口頭説明）＋ profile.md の時間単価 →
処理: §5.3 の計算式変数をヒアリングで埋める（不明変数は仮置き＋要確認リスト行き）→
出力: `reports/YYYY-MM-DD-roi-<slug>.md`（§5.3 構成案）。清書要望が続く場合は
document-creation に切り替える。

**モード4: アクション生成**（発動語:「アクションリストを作って」）
入力: 最新の diagnosis レポート＋roi レポート → 処理: 修正ポイント・ROI提出物・
再発作業を候補化し §5.4 決定表で分類 → 出力: `actions/ACTIONS.md` 上書き。
TODO.md 管理中のユーザーには「task-management スキルで転記できる」と一言案内する
（自動転記はしない。§2.2）。

**モード5: クライアント提案モード**（1.2 吸収。発動語:「クライアント向けに論理とROIで提案を組み立てて」）
入力: クライアント企業の companies/<slug>.md ＋ 提案したい施策 →
処理: 診断観点のうち A1・A2・A3・A7 を「自分の成果物」ではなく「提案書ドラフト」に
適用してセルフチェックし、§5.3 の計算式・構成案を当該クライアントの価値語彙で埋める →
出力: 提案骨子（§5.3 構成案準拠）＋セルフチェック結果（A1/A2/A3/A7 の4行表）。
モード2〜4との違いは対象（自分の評価 → クライアントへの提案）のみで、テンプレは共用。

**モード判定の分岐**: 依頼が単発の書類作成・メール修正なら本スキルを発動せず
document-creation へ。単一タスクの進め方相談なら work-approach-playbook へ。
「評価」「フィードバック」「成長」「ROI」「アクションリスト」を含む横断的依頼のみ本スキル。

## 7. エッジケース

| ケース | 期待挙動 |
|---|---|
| `GROWTH_DATA_DIR` が存在しない状態でモード1〜5を発動 | モード0（セットアップ）を先に実行するか確認してから進む |
| feedback が0件でモード2 | 診断せず「feedback 3件以上の記録」を先に案内する（1〜2件なら実行するが、レポート冒頭に件数不足の注記を入れる） |
| 証拠がない軸がある | スコアを付けず「-（証拠不足）」とし、次回までに集める証拠の種類を修正ポイント欄に書く |
| 制作物がクライアントのコード・秘密資料 | artifacts に抜粋を書かない。location 参照のみ記録し、診断はフィードバック引用だけで行う |
| 同一フィードバックの重複記録 | date + task が同一のファイルが既にあれば追記提案し、新規ファイルを作らない |

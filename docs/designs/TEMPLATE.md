# 設計書テンプレート（Fable-Sonnet運用ブリッジ標準フォーマット）

Fable が書いた設計を Sonnet が**質問なしで**実装できることを目標とするフォーマット。
新しい設計書は本ファイルをコピーして `docs/designs/NN-<slug>.md` として作成する
（NN は 2桁連番。00 はブリッジ自身）。

**書き方の原則**（skill-design-rigor の計画ゲートに対応）:

1. 完成条件は「Sonnet が自分で真偽判定できる」形で書く（○○が動く、ではなく「コマンドXを実行するとYが出力される」）。
2. やらないことを、やること以上に具体的に書く。スコープ漏れは手戻りの最大要因。
3. 実装者が迷いそうな判断は「実装時判断ルール」に先回りして書く。書けないものは「ユーザーに確認」と明記する。
4. データ構造・ファイルパスは例ではなく確定値として書く。「〜など」「適宜」を使わない。
5. 各セクションが埋まらない場合は「該当なし」と明記する（空欄禁止。空欄は「未検討」と区別できない）。

---

以下、テンプレート本体。`<>` 内を置き換える。

```markdown
# <資産名> 設計書

| 項目 | 値 |
|---|---|
| ステータス | 設計完了 / レビュー済み / 実装中 / 実装完了 |
| 種別 | スキル / スクリプト / パイプライン / アプリ / ドキュメント |
| 優先度 | Tier F-<n> |
| 実装モデル | Sonnet 5（推奨 effort: high） |
| 依存する設計書 | <docs/designs/NN-xxx.md、なければ「なし」> |
| 依存する既存スキル | <plugins/xxx、なければ「なし」> |
| 外部依存 | <API キー・MCP・サービス。なければ「なし」> |

## 1. 目的・背景（Why）

<何の課題を解決するか。誰が使うか。既存の何では足りないか。3〜10行。>

## 2. スコープ

### 2.1 やること

<箇条書き。実装対象の機能を列挙。>

### 2.2 やらないこと（明示的スコープ外）

<箇条書き。実装者が「ついでに」やりそうなことを先回りして禁止する。
各項目に一言理由（YAGNI / 別設計書の担当 / ユーザー判断待ち）。>

## 3. 完成条件（Definition of Done）

<チェックリスト形式。各項目は実装者が単独で真偽判定できること。>

- [ ] <検証手順つきの条件。例: `python scripts/x.py --dry-run` が exit 0 で終わり、標準出力に「OK」を含む>
- [ ] <...>

## 4. 成果物の構成（ファイルレイアウト)

<作成・変更する全ファイルをツリーで確定させる。>

## 5. データ構造

<スキーマ・ファイルフォーマット・frontmatter 等を具体例つきで確定させる。該当なしなら「該当なし」。>

## 6. 処理フロー

<ステップごとに「入力→処理→出力」を明記。分岐がある場合は条件を明記。>

## 7. エッジケース

| ケース | 期待挙動 |
|---|---|
| <入力なし / キー未設定 / 巨大入力 / 重複 / 途中失敗 等> | <どうするか> |

## 8. 失敗シナリオとレッドチーム所見

<この設計が失敗するシナリオを確率が高い順に3つ。各シナリオに早期警報サインと設計上の対策を書く。>

| # | 失敗シナリオ | 早期警報サイン | 設計上の対策 |
|---|---|---|---|
| 1 | | | |
| 2 | | | |
| 3 | | | |

## 9. 実装手順（Sonnet 向けタスク分割）

<1タスク = 1コミット目安。各タスクに完了条件をつける。順序依存があれば明記。>

1. **<タスク名>** — <内容>。完了条件: <...>
2. ...

## 10. テスト計画

<何をどう検証するか。スクリプトを含む場合は実行テスト必須（キー必要部分は dry-run/モック）。>

## 11. 実装時判断ルール

<実装者が迷いそうな点への先回り回答。「この場合はこうせよ」「これはユーザーに確認せよ」。>

## 12. 未解決事項（ユーザー確認待ち）

<設計時点で決められなかったこと。なければ「なし」。実装前にユーザーに確認する項目。>
```

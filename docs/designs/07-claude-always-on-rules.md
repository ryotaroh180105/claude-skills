## 1. 目的・背景（Why）

Fable 5 無料期間終了（2026-07-07）後の運用原則「実装させるな、設計させろ」を、
ユーザーのトリガーワードを待たず**全セッションに常時適用**するため、CLAUDE.md の
「常時適用」節群に追記する。対象は fable5-design-assets.md B節の5項目:
(1) 実装させるな設計させろ (2) 指示の密度 (3) effort 運用 (4) レッドチーム計画時必須通過
(5) ルール・スキルの棚卸し。

これらは skill-design-rigor スキル（オンデマンド発動）や AGENT_TEAM.md（サブエージェント
起動時のみ）に部品としては存在するが、「毎セッション最初から効かせる」層が欠けている。
CLAUDE.md がその層を担う。使うのはこのリポジトリで作業する全セッション。

本設計は CLAUDE.md 自体を変更しない。実装フェーズで Sonnet が §5.2 の確定テキストを
CLAUDE.md に反映する。

### 5.2 CLAUDE.md に挿入する確定 Markdown テキスト（そのまま転記する）

```markdown
## 常時適用: Fable運用原則（設計優先・指示密度・effort・レッドチーム・棚卸し）

Fable/Opus は設計、Sonnet 等は実装、という分業を全作業の既定とする。根拠と詳細プロセスは
`docs/designs/00-fable-sonnet-bridge.md` と skill-design-rigor スキルが正。

1. **実装させるな、設計させろ**: 見積もり30分以上の作業は、実装に入る前に
   `docs/designs/TEMPLATE.md` で設計書を書く（skill-design-rigor の計画ゲート5項目を先に回答）。
   設計は Fable/Opus セッションで完成させ、実装は Sonnet セッションに skill-design-rigor §3 の
   定型プロンプトで渡す。30分未満の小タスクは設計書不要。
2. **指示の密度**: 曖昧な依頼を受けたら察しで補完せず、着手前に「目的・完了条件・スコープ外・
   出力形式」の4点を言語化してユーザーに確認する。4点が埋まらないまま設計・実装に進まない。
   （既存の「操作を依頼する時の説明義務」は Claude→ユーザー方向、本項はユーザー→Claude 方向の補完。）
3. **effort 運用**: 設計・要件定義・アーキテクチャ判断=MAX、設計書に基づく実装=高（high）、
   定型作業（整形・一括変換・転記）=low〜medium。確定表は
   `plugins/skill-design-rigor/skills/skill-design-rigor/SKILL.md` §4 が正（CLAUDE.md では再掲しない）。
   effort=MAX と token-saver は両立する（effort は思考の深さ、token-saver は出力の装飾削減で、次元が違う）。
4. **レッドチーム必須通過**: 次の3タイミングだけは、進める前に批判的分析を必ず1回通す —
   ① `docs/designs/` に新規設計書を書き終えた時 ② marketplace.json への追記を含むコミット
   （新スキルのリリース）の前 ③ ユーザーが「反証して」「レッドチームにかけて」と言った時。
   サブエージェントを起動するセッションは先に `AGENT_TEAM.md` を読み、章6の手順で
   `.claude/agents/red-team.md` を起動する。単独セッションでは同じ観点（この計画が失敗する
   シナリオを確率が高い順に3つ＋各早期警報サイン）を自答してから進む。上記3件以外の日常作業には適用しない。
5. **ルール・スキルの棚卸し**: 新規スキル、または本 CLAUDE.md の常時適用ルールを追加する時、
   その同一コミット内で既存の重複・矛盾を点検する。追加物と既存スキル/ルールの責務が重なる場合は
   統合するか役割境界を1行明記する。置き換えなら旧版を marketplace.json から外し、退避先は
   `docs/designs/04-repo-reorganization.md` の分類方針に従う。時刻ベースの定期棚卸しは行わない
   （静的ルールでは強制できず腐るため、イベント駆動に一本化する）。
```

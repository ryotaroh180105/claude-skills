# 新規スキル設計書（X投稿インベントリ由来）

設計: Fable 5（2026-07-07）。実装: Sonnet 5 サブエージェントに委譲する（10-80-10）。
素材の原文は `docs/x-posts-inventory.md` の該当節を参照。
各実装者は `repo-skill-creator` の規約（構成・frontmatter・100〜250行・水増し禁止）に従い、
`plugins/<name>/` 配下のみを作成する（marketplace.json 等は統合役が更新）。

共通の完成の定義: ①SKILL.md 単体を読んだ Claude が迷わず実行できる ②発動条件が
description に具体的な依頼文つきで書かれている ③エッジケース節がある
④`python3 scripts/validate_skills.py` が通る。

## 1. humanize-text（AI臭除去）

- **目的**: AI生成文の「AIっぽさ」を、内容・事実・文字数レンジを変えずに除去する推敲専用スキル。
- **トリガー**: 「AI臭を消して」「人間が書いたように直して」「この文章、AIっぽい」。
  article-writer 工程5・sns-ops-team 執筆後・owned-media 工程4の後処理としても呼ばれる。
- **設計**: インベントリ §2.10 の8プロンプトを「症状 → 適用する変換」の対応表に再構成する。
  8個を順に全部かけるのではなく、**症状診断 → 該当変換のみ適用**の2段構成にする:
  1. 診断: 文長の単調さ / 定型表現（「いかがでしたか」「〜と言えるでしょう」）/ 教科書調 /
     過剰な網羅・箇条書き / 感情の欠落 / 語りかけの欠如、の6症状をチェックして列挙。
  2. 変換: 症状に対応する変換（リズム調整・地声化・語りかけ変換・体温注入・編集長モード等）
     を適用。最後に必ず「仕上げパス」（§2.10-⑧）を1回。
- **制約**: 意味・事実・固有名詞・数値は変更禁止。文体メモ（article-writer の style-memo.md）が
  あれば必ず読み込み、その人の語尾・一人称に寄せる。誇張の追加・内容の水増しは禁止。
- **エッジケース**: 元が十分自然な場合は「変更不要」と返す（無理に変えない）。
  技術文書・法務文書は対象外（正確さ優先）と明記。
- **出典表記**: X投稿のプロンプト8選を再構成した旨を記載（アカウント名は原文テキストに
  含まれていないため「X投稿より」でよい）。

## 2. claude-env-audit（.claude 環境の棚卸し・整備）

- **目的**: `.claude/` 配下（skills, agents, settings, CLAUDE.md）と過去セッションの使い方を
  監査し、重複・死文・肥大化・未使用スキルを検出して整備計画を出す。
- **トリガー**: 「Claude環境を整備して」「スキルが増えすぎたので棚卸しして」
  「使ってないスキルを見つけて」「AUDIT.mdを作って」。
- **設計**: インベントリ §2.4（環境整備）と §2.8（セッション監査）を1本に統合。2モード制:
  - **診断モード（既定）**: 変更を加えない。①`.claude/skills`・`plugins/` の全 SKILL.md の
    name/description を一覧化 → 重複・矛盾・死文・肥大化・機密混入の5観点で分類
    ②（実機なら）`~/.claude/projects` のトランスクリプトから頻出操作・未使用スキルを抽出
    ③各問題に「新スキル化 / 統合 / 修正 / 廃止 / 何もしない」を提案 → `AUDIT.md` に書き出す。
  - **整備モード（明示指示時のみ）**: AUDIT.md に基づき修正を実行。**削除だけは実行前に
    一覧で確認を取る**。全変更を「何を・なぜ・どう変えたか」パス付きでログ化し、
    最後に before→after と残課題を出す。
- **境界**: daily-feedback（単日の使い方採点）とは別物。こちらは資産（スキル・設定）の
  構造監査。description に相互参照を書く。
- **エッジケース**: リモートセッションでトランスクリプトが見えない場合は①③のみ実施し
  ②はスキップと明記。

## 3. screenshot-to-app（スクショ→動くWebアプリ再現）

- **目的**: UIスクリーンショット1枚から、見た目と機能を忠実に再現した単一HTMLの
  動くプロトタイプを作る。
- **トリガー**: 「このスクショを再現して」「この画面と同じものを作って」「デザインをHTML化して」。
- **設計**: インベントリ §2.6 のプロンプトを工程化:
  1. 読み取り: 配色（HEX推定）・フォント・余白・角丸・影・コンポーネント一覧を先に列挙。
  2. 実装: 単一HTML（CSS/JS込み）。写っているUI要素は実際に動くところまで（ダミー禁止、
     状態はJS変数で保持）。写っていない部分はトーンに合わせて補完。
  3. 報告: 再現度の自己採点（100点満点・減点内訳）＋推測で補った箇所と根拠。
- **品質ゲート**: 完成後に `claude-design-review` スキルの a11y 観点だけ通す
  （AI slop 検査は「元スクショに忠実」が優先のため適用しない、と明記）。
- **エッジケース**: 画像が不鮮明で文字が読めない場合は読めた範囲を列挙し、不明箇所は
  プレースホルダにして報告。複数画面のスクショは画面ごとに分割して確認を取る。

## 4. ios-hig-prototype（iOS HIG準拠プロトタイプ生成）

- **目的**: アプリ情報を渡すと、Apple HIG 準拠・iPhone フレーム付き・タップ/遷移が実際に
  動く単一HTMLプロトタイプを生成する。
- **トリガー**: 「iOSアプリのモックを作って」「HIG準拠でプロトタイプを」「iPhoneの画面デザインを」。
- **設計**: インベントリ §2.9 の全文プロンプトが既に完成度が高いので、**プロンプトを
  references/ に原文保存し、SKILL.md は「ヒアリング→生成→検証」の運用手順に徹する**:
  1. ヒアリング: アプリ名・目的・ターゲット・主機能3〜5個・トーン・アクセントカラーの
     6項目（未回答項目は確認してから生成）。
  2. 生成: references/hig-prompt.md の仕様（393×852フレーム・SFシンボル風SVG・
     システムカラー・Inset Groupedリスト・プッシュ遷移0.35s等）に従い単一HTMLを出力。
  3. 検証: 全ボタン・全遷移の動作を頭の中でトレースし、空状態画面の有無を確認。
- **エッジケース**: Android/Web調の要望が混ざったら「HIG準拠と矛盾する」と指摘して
  どちらかに寄せる。localStorage 使用禁止（メモリ内state）を守る。
- **lp-builder との境界**: LP（縦長1枚もの）は lp-builder、アプリUIモックはこちら。

## 5. media-convert（動画→音声変換）

- **目的**: mp4等の動画ファイル・URLを mp3 等の音声に変換する小型ユーティリティ。
- **トリガー**: 「これをmp3にして」「動画から音声を抜いて」「voicememo用に変換して」。
- **設計**: ffmpeg ラッパー。①入力確認（ローカルファイル or URL。URLは yt-dlp が
  必要と案内）②`ffmpeg -i in.mp4 -vn -acodec libmp3lame -q:a 2 out.mp3` を基本形に、
  形式（mp3/wav/m4a）・ビットレート指定に対応 ③出力パスを報告。
- **前提セットアップ表**: ffmpeg（必須。未導入なら OS 別インストールコマンドを提示して停止）、
  yt-dlp（URL入力時のみ）。
- **制約**: DRM保護コンテンツ・権利侵害が明らかなソースは断る。voicememo-pipeline の
  前処理（動画で届いた会議録画→音声化）としての連携を description に明記。
- **yagni 注意**: バッチ変換・動画編集機能は付けない。変換1本に絞る。

## 6. compliance-checker は独立スキル化しない（設計判断）

薬機法・景表法・金商法チェックは、既に owned-media 工程5（v1.1.0）と sns-ops-team の
レビュー役プロンプトに組み込み済み。単独テキストのチェック依頼はその2箇所の
チェックリストを参照すれば足りるため、**3箇所目の重複が出るまで独立化しない**
（yagni-guard の「抽象化は3箇所目から」に従う）。note記事でも必要になった時点で
独立スキルに昇格させ、2箇所の既存チェックリストをそちらへ移す。

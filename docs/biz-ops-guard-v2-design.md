## 1.【必須】現実接触ゲート + ファストパス

### 問題
現状は机上の空想だけでラダー・シート・反証の全工程を通過できる。x_search 調査の最頻出の後悔
「作る前にそのペルソナと直接話すべきだった」に対し、行動でなく作文（Q1の括弧書き）で応えていた。

### 設計
シート着手の直後に**分岐**を置く:

```
動くデモ（コア価値1つだけ）を半日以内に作れるか？
├─ Yes → ファストパス:
│   デモを作る → 実在の3人に送る → 反応をシートの「実シグナル」欄に記録
│   → シートは事後に埋める（設計書の後追い記入を正式に許可する）
└─ No（半日超の建造物）→ 設計先行パス:
    シート記入 → 悪魔の代弁者（ピッチ磨き）→ 一言ピッチを実在の3人に送る
    → 実シグナル1件を得てから実装開始
```

**実シグナルの定義**（いずれか1件以上。空想ペルソナ・エージェントの反証は代替にならない）:
- 実在の人からの「使いたい/試したい」の返信
- 事前登録・予約
- デモの実使用（アクセスログ等で確認できるもの）

**シグナルが得られない場合**: ①ピッチを変えて再送（最大2回）②「学習目的（G3）」と明記して進む
③作らない。既存の3択と同型。**唯一の禁止事項（暗黙に無視して実装）は変えない。**

**悪魔の代弁者の位置づけ変更**: 「シート完成後の独立工程」から「ピッチを送る前の5分レビュー」に格下げ。
同一モデルの自作自演は実在ユーザーの反応の代替にならないため、ゲートではなく研磨工程とする。

## 2.【必須】ラダー/シート統合 + 削除ラウンド

### 問題
ラダー5問の答え＝シート先頭5行で、同じ内容を2回書かせている。v1.0→v1.6 の6版で削除ゼロ
（改善ループのVerifierに「削除を提案する」出力経路が無いラチェット構造）。

### 設計A: 成果物をシート1枚に統合（ラダー節は削除）

```markdown
# <product> ビジネス運用面シート
- 価値提案: （誰）が（既存手段）せずに（成果）できる
- 実在ユーザー3人（属性+痛み+使う場面。実名は書かない）:
- 実シグナル（誰から/何を/日付）:            ← 新設。ここが空のまま実装に進むのが禁止
- 導入: 手順数 __ / 所要 __分 / 前提条件:
- 保守運用: 週__分 / 壊れる要因: / 失敗通知: / 廃止基準:
- 配布: チャネル / 最初の10人 / 到達期限 __週:
- 収益/回収: 誰がいくら払うか。無料なら何で回収するか（1行厳守）
- 指標: 新規 / 7日内再利用 / 紹介
- 意図的に無視すること:
- 悪魔の代弁者: 指摘→処理:
```

- 「上から順に埋められるか」がそのままGo/No-Go判定（ラダーという別概念を廃止）
- 3択（直す/G3明記/作らない）と禁止事項はシート冒頭に1行で残す
- 収益/回収行の4文講釈（スモークテスト等の手法解説）は本文の「収益検証」1段落へ移動し、行は1行に戻す

### 設計B: 改善ループのラチェット解消

- Verifier ルーブリックに判定カテゴリ**「削除推奨」**を追加
- Verifier は毎周**削除提案を最低1件**出す（無い場合は「削除候補なし」と明記させる。無言不可）
- 週次 Routine の prompt は更新不可（update_trigger は name/cron/enabled のみ）のため、
  **既存 Routine `trig_01PfvJPPnoZd4GzXqg24FepM` を削除→新 prompt で再作成**が実装手順

## 3.【必須】hermes-relay 停止時のフォールバック

### 問題
リサーチ手順が relay にハードコードされているが、実機 watcher は20時間停止した実績がある。
Ryo が口頭で WebSearch を許可して回避した運用が文面に無い。

### 設計
SKILL.md リサーチ節に追記（+ CLAUDE.md の調査ルールにも同じ例外を1行追加）:

> relay が20分以内に結果を返さない、または pending に先行クエリが滞留している場合は、
> **ユーザーに一言確認の上** Claude 自身の WebSearch で代替してよい（根拠URL必須は同じ）。
> 復旧後は relay に戻す。x_search（Xの生の声）は WebSearch で代替できないため、
> 滞留時は「返着後に反映」として仮置きで先へ進む。

### 追記（2026-07-07 の CLAUDE.md 更新への追随）
v2 実装時、SKILL.md リサーチ節のエンジン指定も現行 CLAUDE.md に合わせて書き直す:
- 旧: 競合・記事調査 → `engine: notebooklm`。新: **ヘッダなし + プロンプト冒頭で web_search を指示**
  （x_search 不使用の明記・使用ツール名の自己申告要求）。NotebookLM は蓄積型QA専用のため単発調査に使わない
- 捏造ガード文言（取得成功したソースだけ書く・失敗時は「取得失敗」とだけ書く）をクエリ雛形に含める
- 特定URLの本文抽出（UC5）は relay では不可。必要ならユーザーに貼り付けを依頼する

## 4.【要判断→設計実施】5観点→3観点への統合

5観点は Ryo の元指定のため実装は要承認。設計のみ:

| 新3観点 | 吸収する旧観点 | 中身（既存原則は全て移設、削除しない） |
|---|---|---|
| ①選ばれる理由 | 差別化＋マーケ（価値提案系） | 代替列挙→10倍の1点→一文価値提案→検索性→README=LP |
| ②始めやすさ | 導入 | TTFV≤5分/3ステップ、zero-config、前提条件表、出口 |
| ③続けられる構造 | 保守＋運用＋マーケ（配布継続系） | 3ヶ月放置テスト、週N分予算、通知経路、限界費用、配布は継続、月次3指標、ドッグフーディングログ |

- 根拠: 保守と運用は個人開発では同じ問い（放置しても回るか）。マーケと差別化は乗り換え理由が重複
- 効果: 本文の見出し階層が浅くなり、シート（設計2）の行構成と1対1対応になる
- 名称は「導入・保守・運用・マーケ・差別化の5要素を3観点に束ねた」と冒頭に明記し、元の語彙は検索性のため description に残す

## 6. biz-ops-guard 自身のシート（ドッグフーディング・正直版）

```markdown
# biz-ops-guard ビジネス運用面シート
- 価値提案: 個人開発者が、作ってから宣伝を考える代わりに、実装前のシート1枚と実在ユーザーの実シグナル1件で「使われない物を作る」を防げる
- 実在ユーザー3人: Ryo（本リポジトリ全スキル/アプリの設計に常時適用）／それ以外は現状実在しない（仮置き・調査中）
- 実シグナル: なし（Ryo以外に未配布）→ ラダー基準では No
- 導入: 手順2 / 3分 / 前提: Claude Code + marketplace 追加
- 保守運用: 週30分（週次品質Routine）/ 壊れる要因: 参照先スキルの改名・relay仕様変更 / 通知: Routine失敗のpush通知 / 廃止基準: Ryoが3ヶ月使わなければ凍結
- 配布: 現状 Ryo の marketplace のみ。世界配布は設計5の案Bが担う
- 収益/回収: 無料。回収 = Ryo のプロダクト成功率向上 + G3素材 + note記事ネタ
- 指標: 適用回数（test-log とシート生成数で手動カウント）/ 適用したプロダクトの10ユーザー到達率
- 意図的に無視すること: Ryo以外への日本語版配布（案Bに委譲）
- 悪魔の代弁者: ①スキル無しでもClaudeに頼めば済む→閾値・禁止事項・ゲートの強制が差分だが効果は未実証（仮置き）②ユーザーがRyo1人③シート運用が形骸化する恐れ→処理: ①は適用プロダクトの成果で実証する②は案B③は現実接触ゲートが形骸化の歯止め
```

**正直な結論**: 本スキル自身は現状「Ryo専用ツール + G3」であり、それは適用範囲の判定表どおり正当。
「世界一のシェア」を狙う主体はこのスキルではなく、設計5の英語ポータブル版という**別プロダクト**。

# MISTAKES.md データベース設計書

## 1. ユースケース一覧

| ID | ユースケース | アクター | 頻度 | 必要なもの |
|---|---|---|---|---|
| UC1 | ミス発覚 → その場で新規登録 | Claude（push可能な任意のセッション） | 週数件以下 | 追記しやすい形式、ID採番、重複チェック |
| UC2 | push不可環境で発覚 → 「M-登録依頼」経由で後から登録 | claude.ai の Claude → ユーザー → repoセッション | 低 | 登録依頼書式とDBスキーマの1:1対応 |

## 2. ストレージ選定

制約: 全環境からの唯一の書き込み経路が git push（UC1, UC2）。読者は LLM と sed（UC4, UC5）。
想定規模は年間数十件。

| 候補 | 判定 | 理由 |
|---|---|---|
| SQLite | ✗ | バイナリで git マージ不可。SQL が必要なクエリが存在しない。全環境に sqlite3 がある保証もない |
| JSONL | ✗ | 追記マージには強いが、UC4 の注入が「人間可読な整形」を別途要求し、UC3 の行更新で JSON 編集ミスのリスク。読者が LLM なので構造化の利得が薄い |
| Markdown（フィールド規約付き） | ✓ | grep/sed で機械抽出可、人間可読、git diff/マージが素直、M-登録依頼書式とそのまま対応 |

**結論: フィールド規約付き Markdown 単一ファイル**。数百件を超えたら年次分割を検討
（ponytail: 現規模で分割・DB化はしない）。

## 3. スキーマ

### 3.1 再発防止ルール行（注入対象、UC4）

```
- [M-NNN][カテゴリ] ルール本文（1行）
```

- カテゴリ: `誤答` / `手順ミス` / `仕様誤解` / `確認漏れ` / `破壊操作` / `その他`
- **上限20行**。超えたら (a)同カテゴリの統合 (b)CLAUDE.md昇格 (c)ステータス=廃止 のいずれかで削減（UC7）

### 3.2 記録ログエントリ（UC1, UC3, UC6）

```markdown
### M-NNN: <タイトル>
- 登録日: YYYY-MM-DD / 環境: <claude.ai|code-local|code-remote> / カテゴリ: <上記>
- 事象: <何が起きたか>
- 根本原因: <なぜ起きたか>
- 再発防止: <ルール行と同文または詳細版>
- 再発: なし | YYYY-MM-DD (計N回)
- ステータス: active | 昇格済み(CLAUDE.md) | 廃止(<理由>)
```

- 全フィールド必須。「M-登録依頼」書式（docs/global-rules.md）は 事象/根本原因/再発防止ルール案 の3項目で、登録時に残りを補完する。

## 4. 運用プロトコル（書き込み時の整合性）

1. **重複チェック**（UC5）: 登録前に記録ログをキーワード grep。既出なら新規登録せず、該当エントリの「再発」を更新しルール文を強化する（UC3）。
2. **ID採番**: 登録直前に `git pull` → 既存最大 M-NNN + 1。push が non-fast-forward で失敗したら pull して番号衝突を確認、衝突時は振り直して再push。
3. **1コミット1ミス**: ルール行の追加とログエントリの追加を同一コミットにする（片方だけの状態を作らない）。
4. **昇格**: 一般化できるルールは CLAUDE.md へ移し、ルール行を削除、ログのステータスを「昇格済み」に更新。ログエントリ自体は消さない（履歴・集計用、UC6）。

## 5. 意図的に採用しなかったもの

- 環境別スコープでの注入フィルタ（例: claude.ai 向けルールだけ除外）: ルール総数20行以下なら全注入で十分。ponytail: 上限超過が常態化したら導入。
- アーカイブ用の別ファイル: 廃止エントリもログに残すだけで足りる規模。
- 自動集計スクリプト: UC6 の集計は月1で件数も少なく、LLM（月次 Routine）で足りる。
  機械化するのはスキーマ検証のみ（§6 の Verifier）。

## 6. ループ設計（loop-engineering 適用、2026-07-05）

本システムは3つのループで動く。6要素（Trigger/Doer/Verifier/Stop Rules/Memory/Skills）での点検結果:

| ループ | Trigger | Doer | Verifier | Stop Rules | Memory |
|---|---|---|---|---|---|
| 記録（UC1-UC3, UC5） | イベント: ミス発覚 | セッション中の Claude（運用ルールの登録手順） | `scripts/validate_mistakes.py`（CI で毎 push 実行。スキーマ・20行上限・ID整合を機械判定） | 1コミット1ミス。書式違反は CI が落とす | MISTAKES.md 本体（git） |
| 注入（UC4） | SessionStart フック | sed によるルール節抽出 | 注入節の肥大は validate_mistakes.py の20行上限が抑止 | 上限20行（機械強制） | MISTAKES.md ルール節 |
| 月次レビュー（UC6-UC7） | タイマー: Routine 毎月1日 09:00 JST（`trig_015S7ZVaajbca8vmZygMFoYE`） | 新規セッションが集計・昇格/統合/廃止を提案 | 2層: validate_mistakes.py + **Ryo の PR レビュー（human gate、自己マージ禁止）** | 30分・1体・往復3回。収束しなければ途中結果を PR に書いて終了 | MISTAKES.md「レビュー履歴」 |

初版設計（§1-§5）からの是正点:

- **Blind Loop 解消**: 登録の書式遵守・上限が登録者の自己申告だった → CI の機械 Verifier に分離。
- **幽霊ループ解消**: UC6「月1程度」に起動主体が無かった → Routine で自動起動（Manual Loop 回避）。
- **Stop Rule の機械化**: ルール20行上限がプロンプト指示のみだった → validate_mistakes.py が超過時に CI を落とす（指示文の上限は守られない前提で設計）。
- **Amnesiac 解消（レビュー）**: レビュー実施の記録が無かった → 「レビュー履歴」セクションを Memory 化。

詳細な設計書は `LOOPS.md` の「MISTAKES.md 月次レビューループ」。

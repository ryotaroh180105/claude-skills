# SNS Auto Posting

sns-ops-team が作った投稿キュー（`post-queue.md`）の **approved 行だけ**を読んで
実際に投稿する実行系スキル。企画・執筆・レビューはしない（sns-ops-team の担当）。

キューの契約（post-queue.md のフォーマット定義に従う）:

- 投稿してよいのは ステータス が `approved` の行だけ。**`draft` は絶対に投稿しない。**
- `approved` → `posted` への変更は、**投稿成功を確認した後に**このスキルだけが行う。
- 失敗・スキップした行は `approved` のまま残す。`draft` に戻すこともしない。

## 前提セットアップ

| 環境変数 | 必須? | 内容 |
|---|---|---|
| `X_API_KEY` | X投稿に必須 | Consumer Key |
| `X_API_SECRET` | X投稿に必須 | Consumer Secret |
| `X_ACCESS_TOKEN` | X投稿に必須 | Access Token（Read and Write 権限で発行したもの） |
| `X_ACCESS_TOKEN_SECRET` | X投稿に必須 | Access Token Secret |
| Meta Graph API（`IG_USER_ID` / `IG_ACCESS_TOKEN`） | 将来拡張 | v1 では未実装。Instagram は手動投稿テキスト出力のみ |
| TikTok Content Posting API（`TIKTOK_ACCESS_TOKEN`） | 将来拡張 | v1 では未実装。TikTok は手動投稿テキスト出力のみ |

X キーの取得手順: developer.x.com でアプリを作成 → App permissions を
**Read and Write** に変更 → Keys and tokens で4つのキーを発行（権限変更後は
Access Token の**再発行**が必要。Read のみのトークンでは 401 になる）。

**キー未設定でも動く範囲**: `--dry-run` でのリクエスト内容確認と、手動投稿用
テキストの整形出力はキーなしで可能。未設定のまま投稿を頼まれたら、この
フォールバックに切り替えたうえで上の取得手順を案内する。

## ワークフロー（キュー一括投稿）

「承認済みを投稿して」と言われたら次の順で進める。

### ① キュー読み込みと対象抽出

1. 対象アカウントの `sns/<アカウント名>/post-queue.md` を読む。どのアカウントか
   不明なら `sns/` 配下を一覧して選んでもらう。
2. 現在時刻を JST で取得する（`TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M'`）。
3. 投稿対象 = **ステータスが `approved`** かつ **予定日時が現在(JST)以前** の行。
   - 予定日時が未来の行は投稿せずキューに残し、サマリーで「予定待ち」と報告する。
   - `draft` / `posted` の行には一切触らない。
4. 対象が6件以上なら、**1回の実行では予定日時の古い順に最大5件**までにし、
   残りは「次回実行に持ち越し」と報告する（誤爆時の被害を限定する安全装置。
   ユーザーが明示的に「全部」と言った場合のみ上限を外してよい）。

### ② 投稿前チェック（1行ずつ）

- **重複チェック**: 本文が、同じキュー内の `posted` 行のいずれかと完全一致する
  場合は投稿せずスキップし、「重複の可能性」として報告する（X 側も同一本文の
  連続投稿を 403 で拒否する）。
- **本文の復元**: セル内の `<br>` は改行に、`\|` は `|` に戻してから投稿する。
- **X で文字数超過**（日本語は2字、半角英数は1字、URLは23字換算で280超）:
  投稿せずスキップし、短縮案を提示して人間の再承認を待つ。勝手に本文を
  縮めて投稿しない。

### ③ X への投稿（1件ずつ、逐次）

同梱の `scripts/post_x.py` を使う。並列実行せず、1件ずつ結果を確認して進める。

```bash
# 本文はファイル経由が安全（クォート事故を防ぐ）
python3 scripts/post_x.py --file /tmp/post-001.txt          # 投稿
python3 scripts/post_x.py --file /tmp/post-001.txt --dry-run # 事前確認
python3 scripts/post_x.py --text "返信本文" --reply-to <tweet_id>  # スレッド返信
```

- 初回実行時や本文に不安がある場合は、まず `--dry-run` で内容を確認してから
  本投稿する。
- **成功時**（exit 0、URL が出力される）: 直ちにその行の ステータス を `posted`
  に書き換え、投稿URLを post-queue.md 末尾の `## 投稿ログ` 節（無ければ作る）に
  `| id | 投稿日時(JST) | URL |` の表で追記する。表本体の列構成は変えない。
- **失敗時**: ステータスは `approved` のまま。exit code で分岐する:
  - `3`（キー未設定）: 以降の X 行も全部スキップし、手動投稿テキスト出力に
    切り替え。セットアップ手順を案内。
  - `4`（401/403 認証・拒否）: 以降の X 投稿を中断。キーと権限（Read and
    Write）の確認を案内。403 で「duplicate」なら重複として報告。
  - `5`（429 レート制限）: **残りの投稿をすべて中断**し、解除見込み時刻と
    「時間を置いて再実行」を案内。自動で連続リトライしない（1回だけ、数分
    待っての再試行を提案するに留める）。
  - `2`（文字数など入力エラー）: その行だけスキップして次の行へ。
- **メディア付きの X 行**（メディア列が `-` 以外）: v1 のスクリプトは画像
  アップロード未対応。投稿せず「手動投稿対象」として下記④の形式で出力する。

### ④ Instagram / TikTok（および投稿できなかった X 行）

API 未実装・キー未設定のプラットフォームは、**手動投稿用テキストとして整形
出力する**（これはエラーではなく v1 の正常動作）。1件ごとに次の形式:

```
--- 手動投稿 [id: 004 / instagram / 予定: 2026-07-08 21:00] ---
本文:
（<br> を改行に戻した本文そのまま。コピペで使える状態）
メディア: sns/xxx/media/004.png
手順: 上記をコピーして Instagram アプリから投稿してください。
```

これらの行のステータスは `approved` のまま残す（実際に投稿されたかをこの
スキルは確認できないため）。ユーザーが「手動で投稿した」と言った時だけ、
その申告に基づいて `posted` に更新し、投稿ログにも「手動投稿」と記録する。

### ⑤ 結果サマリー

最後に必ず全行の結果を表で報告する:

| 区分 | 内容 |
|---|---|
| 成功 | id・プラットフォーム・投稿URL |
| 失敗 | id・理由（認証/レート制限/文字数超過など）・次のアクション |
| スキップ | id・理由（予定日時が未来 / 重複疑い / 手動投稿対象 / 件数上限） |

キューの残り状況（approved 残 n 件、うち予定待ち m 件）も添える。

## 単発投稿（キューを経由しない依頼）

「これをXに投稿して」と本文を直接渡された場合:

1. 本文の文字数を確認し、`--dry-run` の出力（本文とカウント）を見せて
   **投稿してよいか確認を取ってから**本投稿する。キュー経由の approved 行と
   違い、単発依頼には承認プロセスがないため、確認なしで即投稿しない。
2. 投稿後は URL を報告する。post-queue.md がある運用アカウントなら、記録の
   ため `posted` 行としてキューに追記するか提案する。
3. Instagram/TikTok への単発依頼は、手動投稿用テキストに整形して渡す。

## エッジケースの扱い

- **キューが空 / 表が無い**: 「投稿対象がありません」と報告し、sns-ops-team で
  投稿を作るフローを案内する。勝手に投稿を作らない。
- **全行 draft**: 投稿できるものは無い。「approved への変更は Ryo が行う」という
  契約を伝え、承認待ちの draft 一覧（id と本文冒頭）を見せて終わる。
- **approved だがすべて予定日時が未来**: 何も投稿せず、次に投稿可能になる
  日時を報告する。定期実行したい場合はトリガー/cron の設定を提案してよい。
- **280字超の approved 行**: 投稿せずスキップ。短縮案は提示するが、書き換えて
  よいのは人間の承認後（書き換え後も `approved` のままなら次回実行で投稿）。
- **画像・動画付き**: X も含め v1 は手動投稿対象として整形出力（③参照）。
- **重複投稿防止**: `posted` 行と本文が完全一致する `approved` 行は投稿しない。
  「同じ内容が id NNN で投稿済みです。それでも投稿しますか」と確認する。
- **同一実行内で同じ本文が2行**: 1件目だけ投稿し、2件目は重複としてスキップ。
- **post-queue.md のフォーマットが崩れている**（列数不一致など）: 解釈で補わず、
  壊れている行を示して修正を促す。読める行だけで続行してよいか確認する。

## やらないことの明確化

- `draft` 行の投稿、`draft` → `approved` の変更（承認は Ryo だけが行う）
- 本文の無断リライト（文字数超過でも短縮は提案止まり）
- 投稿の失敗を隠して `posted` にすること（成功確認できた行だけ更新する）
- 企画・執筆・レビュー（sns-ops-team の担当。頼まれたらそちらを案内する）
- API キーの値を出力・ログ・キューに書き残すこと

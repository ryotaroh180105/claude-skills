# Fable Distill — Fable 5 の思考様式プレイブック

2026-07-07（無料期間最終日）に Fable 5 セッション自身が自分の動作パターンを言語化したもの。
目的は、**Fable が使えない環境・期間でも、Opus 4.8 / Sonnet 5 が同じ規律で難タスクを進められる**ようにすること。
賢さは移植できないが、**賢いモデルほど徹底している規律**は移植できる。以下はその規律。

## 適用場面

- 設計・要件定義・難デバッグ・スキル作成・リファクタなど、失敗コストが高いタスク。
- 「完了するまで自律で進めて」と依頼された長時間タスク。
- 単純作業には適用しない（読み込むだけコストの無駄。そのまま手を動かせばよい）。

## 1. タスク分解の型

**着手前に、成果物を1文で言語化する。**
「このターンの終わりにユーザーが受け取るものは何か」を先に決める。
これが言えないうちはツールを触らない。言えたら即座に動く。

- **未知を2種類に分ける**: ①調べれば分かる未知（ファイルの中身・エラーの原因・APIの仕様）
  → 聞かずに自分で調べる。②ユーザーにしか決められない未知（好み・予算・スコープの取捨）
  → これだけ質問する。①を質問するのは怠慢、②を勝手に決めるのは越権。
- **完成の定義を先に固定する**: 検証可能な形で「何が満たされたら完了か」を書き出してから
  実装する（CLAUDE.md「完成の定義」参照）。定義がないまま書いたコードは「動いた気がする」で終わる。
- **計画は3〜7手の粒度**: それ以上細かい計画は実行中に必ず崩れる。それ以上粗い計画は
  計画になっていない。各手は「終わったかどうかが客観的に分かる」単位で切る。
- **散策→計画→実行の順**: 既存コード・既存資産を見る前に計画を立てない。
  「すでにあるもの」を知らずに立てた計画は、ほぼ確実に車輪の再発明を含む。
- **独立な作業は同時に投げる**: 相互に依存しない読み込み・調査・サブエージェントは
  1回のレスポンスでまとめて並列発行する。直列に待つのは時間の浪費。

## 2. 自己検証の型

**「完了」と言ってよいのは、完成の定義に照らした観察事実がある時だけ。**
「実装した」は完了ではない。「実装し、validate が通り、出力を目視した」が完了。

- **変更したら必ず検証コマンドを打つ**: このリポジトリなら
  `python3 scripts/validate_skills.py`。テストがあるならテスト。無いなら最低限、
  成果物を開いて自分の目で読む。
- **主張と証拠を対応させる**: 報告に書く各主張について「その証拠をどのツール結果で
  見たか」を言えるか自問する。言えない主張は書かないか、「未検証」と明記する。
- **数値・URL・固有名詞は取得値のみ**: 推測で埋めない。取れなかったら「取得失敗」と書く。
  もっともらしい捏造が一番信頼を壊す（Epistemia対策。CLAUDE.md 参照）。
- **報告前に1回だけ自分を疑う**: 「この結論が間違っているとしたら、どこか」を30秒考える。
  反証が見つかればそれを潰してから報告し、見つからなければ確信度を添えて報告する。
- **サブエージェントの報告を鵜呑みにしない**: 桁のおかしい数値・都合の良すぎる結論は、
  自分で1〜2点サンプル検証してから採用する。

## 3. 次の一手の決め方

**ターンを終える前に、自分の最後の段落を読み返す。**
それが「計画」「次にやることのリスト」「〜します、という約束」「確認の質問（②以外）」なら、
ターンを終えてはいけない。それを今、ツールを叩いてやる。

- **詰まった時のループ**: エラー全文を読み直す → 原因仮説を1つだけ立てる →
  仮説を最小の実験で検証する → 外れたら次の仮説。同じ修正を2回繰り返さない。
  3回連続で外れたら、仮説ではなく前提（環境・入力・自分の理解）を疑う。
- **結果を先頭に置いて報告する**: 「何が起きたか・何が分かったか」を最初の1〜2文で言う。
  過程・根拠は後ろ。読む側が「で、結局？」と聞き返す報告は失敗。
- **決まったことを再演しない**: ユーザーが既に決めたこと・会話で確定した事実を
  再検討・再確認しない。選ばなかった選択肢の解説もしない。
- **エスカレーションは本物のスコープ変更だけ**: 依頼の自然な延長は黙って進める。
  破壊的操作・外部公開・依頼の趣旨が変わる分岐だけ止まって確認する。

## 4. やらないこと（Fable がやらないから速い、の裏返し）

| アンチパターン | 症状 |
|---|---|
| 偽の done | 検証せず「完了しました」。後で壊れているのが見つかる |
| スコープ膨張 | 依頼にないリファクタ・改名・「ついでの改善」を混ぜる |
| 網羅の演技 | 選択肢を全部並べて比較表を作るだけで、推奨を1つに絞らない |
| 実況中継 | 「では次に〜を実行します」をツールコールの前に毎回書く |
| 質問による停止 | 調べれば分かることをユーザーに聞いて作業を止める |
| 再導出 | 会話の前半で確定した事実を、後半でもう一度調べ直す |

## 5. 運用メモ

- このプレイブックは **model-switcher の 10-80-10 采配とセットで使う**：
  設計・検収フェーズの下位モデルに規律を足すのが役目。判断の難しさ自体は消えないので、
  「Opus/Sonnet で3回詰まったら、その論点だけ上位モデル（従量課金の Fable 等）に上げる」
  基準は維持する。
- セッション冒頭で全文を読み込むほか、「§2 だけ適用して（検証を厳しく）」のような
  部分適用も可。
- 併用推奨: `token-saver`（応答の無駄削り）、`yagni-guard`（コードの無駄削り）、
  `work-approach-playbook`（依頼主がいる仕事の報連相）。

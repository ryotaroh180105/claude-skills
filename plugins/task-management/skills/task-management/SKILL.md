# Task Management（Markdown タスク管理）

## 目的

個人のタスク（インターン業務・副業・学習）を 1 つの `TODO.md` に集約し、
「全部書き出す → 分解する → 優先順位をつける → 今日やる 3 つを決める →
進捗を更新する → 週次で振り返る」という一連のサイクルを回せるようにする。
専用ツールを増やさず、リポジトリ内の Markdown だけで完結するのが特徴。

重要な原則: **タスクを依頼されても勝手に消化しない。** まず優先順位と着手順を
ユーザーと確認してから作業に入る。このスキルの役割は「代わりに全部やる」ことでは
なく、「何をどの順でやるかをユーザーが決められる状態を作る」こと。

## 発動条件

- 「タスクを整理したい」「やることが多すぎて混乱している」と相談されたとき
- 「今日やることを決めたい」「優先順位をつけて」と依頼されたとき
- 「TODO.md を更新して」「このタスクを Done にして」など進捗更新を求められたとき
- 「今週の振り返りをしたい」「週次レビューをして」と依頼されたとき
- 新しいタスクを口頭で渡され、既存のタスクボードに追加すべきとき

## 前提セットアップ

- **ローカル運用（デフォルト）**: 追加セットアップ不要。プロジェクトルート、
  またはユーザーが指定した場所に `TODO.md` を作成して運用する。
- **GitHub 連携（オプション）**: GitHub Issues と同期したい場合は
  GitHub MCP サーバー（`mcp__github__*` ツール）が必要。
  未接続の場合は連携をスキップし、ローカル `TODO.md` のみで運用する。
  接続済みなら `mcp__github__list_issues` / `mcp__github__issue_write` などで
  Issue の取り込み・作成・クローズを行える。

初回はまず `TODO.md` が既に存在するか確認する（`Glob` で `**/TODO.md` を検索）。
既存ファイルがあればその形式を尊重し、勝手にテンプレートで上書きしない。

## ワークフロー

### ① 受付 — やることを全部書き出す

- ユーザーが挙げたタスクを、粒度を気にせずまず全部 `## Backlog` に書き出す。
- 会話の中に埋もれているタスク（「あとで〜もやらないと」等）も拾って確認する。
- この段階では順番を決めない。漏れなく集めることを優先する。

### ② 分解 — ゴール・ステップ・見積もりを出してから着手する

**1セッションで終わらない規模のタスク（新機能・新スキル・複数ステップの調査等）は、
着手前に以下3点をセットで出し、ユーザーの確認を取ってから Today/This Week に
入れる。** ワンライナーで終わる依頼にはこのゲートは不要（②のまま軽く分解するだけでよい）。

1. **ゴール**: 何が完了すれば終わりか、1文で明文化する。
2. **ステップ**: ゴールまでの手順を順序立てて列挙する（2時間以内の粒度に分割、
   従来通り）。
3. **見積もり**: ステップごとの想定時間と、担当フェーズを明記する。
   - **設計フェーズ**（ゴールの精査・ステップ分解・技術選定）→ Fable 5 / Opus 4.8
   - **リサーチ・実装フェーズ**（決まった手順の実行・調査・コーディング）→
     Sonnet 5（大量・定型作業は Haiku 4.5 に委譲）
   - モデルの選び方の詳細・判断基準は `model-switcher` スキールを参照する
     （ここでは重複して説明しない）。

この3点はタスクの下にインデントしたサブ項目として TODO.md に記録し（下記
出力フォーマット参照）、以後の進捗管理（⑤）はステップ単位で `[x]` を付けていく。

分割案・見積もりは必ずユーザーに提示して合意を取る。「レポート作成」→
「構成を決める(1h, 設計/Fable)」「本文を書く(2h, 実装/Sonnet)」のように、
完了条件が明確な動詞＋見積もり＋担当フェーズで書く。

### ③ 優先順位付け — 緊急度 × 重要度 + 締切

- 各タスクを緊急度 × 重要度のマトリクスで分類する:
  - **緊急かつ重要** → 最優先（Today 候補）
  - **重要だが緊急でない** → 計画的に This Week へ
  - **緊急だが重要でない** → 短時間で片付けるか、可能なら断る・減らす
  - **どちらでもない** → Backlog の下位、または削除を提案
- 締切があるものは締切順を加味する。優先度は `高` / `中` / `低` で記録する。

### ④ 着手順の決定 — 今日やる 3 つを決める

- Today に入れるのは **原則 3 つまで**。合計想定時間が現実的か確認する。
- 候補を提示し、**必ずユーザーに確認してから** Today を確定する。
  勝手に着手順を決めて作業を始めない。

### ⑤ 進捗管理 — ステータス更新

- 完了したタスクは `- [x]` にして `## Done` へ移動する（完了日を付記）。
- 着手できなかった Today のタスクは、理由を一言添えて This Week か Backlog に戻す。
- 新規タスクが割り込んだら ①〜③ を軽く回して位置を決める。

### ⑥ 週次振り返り

週の終わり（またはユーザーの依頼時）に以下をまとめて報告する:

1. **完了数**: 今週 Done に入った数と主な成果
2. **持ち越し理由**: 終わらなかったタスクと、その原因（見積もり過小・割り込み・優先度変更など）
3. **来週への調整**: 分解の粒度・Today の個数・見積もり時間の修正案

振り返り後、`## Done` の古い項目はアーカイブ（別セクションや別ファイル）に移して
ボードを軽く保つ。

## 出力フォーマット

`TODO.md` は以下のテンプレートで運用する。各タスクは
`- [ ] タスク名 (期限, 想定時間, 優先度)` 形式で書く。

```markdown
# TODO

最終更新: YYYY-MM-DD

## Today
<!-- 今日やる 3 つまで -->
- [ ] インターン: レビュー指摘の修正 (7/4, 1h, 高)
- [ ] 副業: クライアントへ進捗報告 (7/4, 0.5h, 高)
- [ ] 学習: 教材 3 章を読む (7/6, 1.5h, 中)

## This Week
- [ ] インターン: 新機能の設計メモ作成 (7/8, 2h, 高)
- [ ] 副業: LP の修正対応 (7/10, 2h, 中)
- [ ] 個人開発: 予約機能を追加 (7/12, 見積もり計4h, 高)
  - ゴール: ユーザーがLPから日時を選んで予約を送信できる
  - [ ] 設計: データ構造・API方針を決める (1h, 設計/Fable)
  - [ ] 実装: フォームとAPIを実装する (2h, 実装/Sonnet)
  - [ ] 実装: 動作確認・調整 (1h, 実装/Sonnet)

## Backlog
- [ ] 学習: 資格試験の申し込み (7/31, 0.5h, 低)
- [ ] ポートフォリオの更新 (期限なし, 2h, 低)

## Done
- [x] インターン: 環境構築 (完了 7/2)
```

記法のルール:

- 期限がないものは `期限なし` と明記する（空欄にしない）。
- 想定時間は `0.5h` 単位程度で十分。精密さより見積もりの習慣を優先する。
- カテゴリ（インターン / 副業 / 学習など）はタスク名の接頭辞で表す。
- 設計ゲートを通したタスクは、上記の予約機能の例のように
  「ゴール」の1行＋ステップのサブチェックリスト（担当フェーズ付き）を
  タスクの下にインデントして記録する。ステップ単位で進捗が追える。

GitHub 連携時は、Issue 由来のタスクに `(#123)` のように Issue 番号を付記し、
Done へ移す際に対応する Issue のクローズを提案する（クローズ自体もユーザー確認後）。

## 注意点

- **勝手に消化しない**: タスクを渡されたら、まずボードに載せて優先順位を確認する。
  「今すぐやって」と明示されたものだけ即実行する。
- **既存ファイルを尊重する**: 既に `TODO.md` がある場合、セクション構成や記法を
  勝手に作り替えない。テンプレートへの移行はユーザーに提案して合意を得る。
- **Today を膨らませない**: ユーザーが 5 個以上入れようとしたら、経験上持ち越しが
  増えることを伝え、3 つに絞ることを提案する（最終判断はユーザー）。
- **見積もりは外れる前提**: 週次振り返りで実績と比較し、翌週の見積もりを補正する。
  外れたこと自体を責める書き方はしない。
- **設計ゲートは規模に応じて**: 一言で終わる依頼にまでゴール・ステップ・見積もりを
  強制しない。「1セッションで終わらなそうか」を目安に、大きい依頼だけ通す。
- **GitHub 連携は任意**: MCP サーバー未接続の環境でエラーになったら、連携を諦めて
  ローカル運用にフォールバックする旨をユーザーに伝える。

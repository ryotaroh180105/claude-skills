# Code Review + ADR

コードレビューの質を上げ、レビュー中に見つかった「アーキテクチャ上の判断」を
ADR（Architecture Decision Record）として `docs/adr/` に残すためのスキル。
単なる指摘で終わらせず「決定の記録を残せるレビュアー」になることが目的。

## いつ使うか

- 自分の PR を push 前にセルフレビューしたいとき
- 他人の PR・ブランチのレビューを依頼され、コメント下書きを作りたいとき
- 既存コードベース（ディレクトリ指定）の改善提案をまとめたいとき
- レビューとは別に、ADR だけを書きたいとき（「この決定を記録して」）

## ワークフロー

1. **対象把握** — レビュー対象を特定する。優先順: ユーザー指定 > PR 番号/URL >
   `git diff`（未コミット変更 → ブランチ差分の順に確認）> 指定ディレクトリ。
   対象が曖昧なら着手前に必ず確認する。diff だけでなく、変更が呼ばれる側・
   呼ぶ側のコードも必要に応じて読む（diff 単体では正しさを判断できないため）。
2. **観点別レビュー** — 下のチェックリスト5観点を順に適用する。
3. **指摘まとめ** — 指摘フォーマットに従い、重要度順（must → should → nits）に整理。
   良い点も必ず1つ以上書く。
4. **アーキテクチャ判断の検出** — 後述の検出基準に該当するものがあれば、
   「この変更は ADR に残す価値があります」と提案し、同意を得てから下書きを作る。
   該当がなければレビューだけで完了してよい（無理に ADR を作らない）。
5. **ユーザー確認後に確定** — レビューコメントの投稿（GitHub MCP がある場合）や
   ADR ファイルの保存は、必ずユーザーが内容を確認してから行う。勝手に投稿・
   コミットしない。

## レビュー観点チェックリスト

### 1. 正しさ（Correctness）
- 仕様・PR の意図どおりに動くか。diff の外側（呼び出し元）を壊していないか
- エッジケース: 空配列・null/undefined・0件・境界値・重複・タイムゾーン
- エラー処理: 例外の握りつぶし、失敗時のリソース解放・ロールバック漏れ
- 並行処理: 競合状態、非同期処理の await 漏れ、トランザクション境界

### 2. 可読性（Readability）
- 命名が実態を表しているか（`data`, `tmp`, `flag` のような曖昧名を許さない）
- 関数が1つの責務に収まっているか。ネストが深すぎないか（早期 return で解消可能か）
- コメントは「何を」ではなく「なぜ」を説明しているか。死にコード・コメントアウトの残骸
- マジックナンバー・重複ロジックの放置

### 3. セキュリティ（Security）
- 入力検証: 外部入力（リクエスト、ファイル、環境変数）を信用していないか
- 秘密情報: API キー・パスワードのハードコード、ログへの出力
- インジェクション: SQL/コマンド/パス結合の文字列連結、XSS（エスケープ漏れ）
- 認可: 認証済みでも「その操作をしてよいユーザーか」の確認があるか

### 4. 性能（Performance）
- N+1 クエリ（ループ内での DB/API 呼び出し）
- 不要な再計算・再レンダリング、ループ内での重い処理の繰り返し
- 大量データ時の挙動: 全件ロード、ページネーションの欠如
- ただし推測で最適化を要求しない。計測可能な根拠か明らかなパターンのみ指摘

### 5. テスト（Testing）
- 変更されたロジックに対応するテストが追加・更新されているか
- 正常系だけでなく異常系・境界値のケースがあるか
- テストが実装の写しになっていないか（振る舞いを検証しているか）
- 既存テストの削除・skip 化には正当な理由があるか

## 指摘フォーマット

指摘は以下の形式で、**重要度順**に並べる。

```
[must] src/api/users.ts:42
ユーザー入力の `id` をそのまま SQL に文字列連結しており、SQLインジェクションが可能。
修正案: プレースホルダを使う → `db.query("SELECT ... WHERE id = ?", [id])`
```

- **[must]** — マージ前に修正必須（バグ・セキュリティ・データ破壊の恐れ）
- **[should]** — 修正を強く推奨（保守性・性能の問題。今やらないなら issue 化）
- **[nits]** — 好みの範囲（命名・スタイル。対応は任意と明記する）

各指摘には必ず: ①該当箇所 `file:line` ②理由（なぜ問題か）③具体的な修正案 を含める。
「なんとなく気になる」だけの指摘はしない。

**良い点も必ず1つ以上言及する。** レビューは粗探しではなくコードベースと
チームを良くする行為。「このエラーハンドリングの分離は読みやすい」のように
具体的に書く（レビュー文化への配慮であり、指摘の受け取られ方も変わる）。

## ADR 連携（このスキルの独自価値）

### アーキテクチャ判断の検出基準

レビュー中に以下のいずれかを見つけたら ADR 化を**提案**する:

- フレームワーク・主要ライブラリの選定/乗り換え（例: Redux → Zustand）
- データモデル・スキーマの変更（テーブル追加・カラム型変更・非正規化）
- 外部サービス/インフラの採用（決済・認証・キュー・ストレージ等）
- 非自明なトレードオフ（例: 整合性を犠牲にキャッシュ導入、あえての重複実装）
- 横断的な規約・パターンの変更（エラーハンドリング方針、ディレクトリ構成）

### レビューだけで終えるケース（ADR にしないもの）

- バグ修正・タイポ・リファクタリング（外部から見た振る舞い・構造方針が不変）
- 命名・スタイル・小さな関数分割などの局所的な改善
- 既存 ADR に沿っただけの実装（その場合は該当 ADR を参照として挙げる）

判断基準は「**半年後に『なぜこうなってるの?』と聞かれ得るか**」。Yes なら ADR、
No ならレビューのみ。迷ったら ADR 候補としてユーザーに提示し、判断を委ねる。

### ADR の作成手順

1. `docs/adr/` の既存ファイルを確認し、最大の連番 + 1 を採番する
   （4桁ゼロ埋め。例: `docs/adr/0007-セッション管理をDBセッションに変更.md`）
2. `templates/adr-template.md` をベースに下書きを作る。「検討した選択肢」には
   採用しなかった案（現状維持を含む）とその Pros/Cons を必ず書く
3. ユーザーに下書きを見せ、ステータス（提案中/承認済み）を確認してから保存する
4. レビューコメント側にも「この判断は ADR 0007 に記録した」と相互参照を残す

ADR だけを依頼された場合（レビューなし）は、背景・選択肢・決め手を
ヒアリングしてから手順 1〜3 を実行する。

## エッジケースの扱い

- **diff が巨大（目安: 1,000 行超 or 30 ファイル超）**: 全体を薄くレビューしない。
  まず変更をコミット単位・ディレクトリ単位に分割し、「正しさ・セキュリティ優先で
  この範囲から見る」と方針を提示して合意を取る。残りは範囲を明示して後続に回す。
- **テストが無いリポジトリ**: テスト観点を「テストが無い」の一言で済ませない。
  今回の変更で最もリスクが高い箇所に絞った最小のテスト追加を [should] として提案し、
  手動確認手順（何をどう叩けば検証できるか）を代替として書く。
- **ADR ディレクトリが未整備**: `docs/adr/` が無い場合は勝手に作らず、
  「ADR 運用を始めるか」「別の場所（例: `docs/decisions/`）が既にあるか」を確認する。
  新設に同意を得たら `docs/adr/` を作成し `0001-` から採番を開始する。
- **GitHub MCP が無い/PR に直接コメントできない**: レビュー結果を
  そのまま貼り付けられる Markdown の下書きとして出力する（機能としては劣化しない）。

## 前提セットアップ

外部依存なし。ローカルの diff・ファイルレビューと ADR 作成はそのまま動く。

| 依存 | 必須? | 用途 |
|---|---|---|
| なし | - | ローカル diff / ディレクトリのレビュー、ADR 作成 |
| GitHub MCP | 任意 | GitHub 上の PR 取得・PR への直接コメント投稿（未接続なら下書き出力に切り替え） |

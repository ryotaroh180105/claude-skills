# 市場・競合・ボトルネック分析（biz-analysis）

## 目的

市場分析・競合分析・競合ボトルネック分析を、毎回ゼロから組み立てずに
「ヒアリング → 調査クエリ設計 → hermes-relay調査 → 分析 → レポート」の固定工程で回す。

- **利用者A: インターンのコンサル業務。** クライアント（IT企業・地方エネルギー企業のような
  BtoB クライアント）向けの市場・競合分析資料を作る。求められるのは出典が示せて
  プロセスを追える社内向けレポート。
- **利用者B: 自分の副業。** LP案件・SNS運用・note の市場選定と競合調査。求められるのは
  「参入するか/どの切り口で差別化するか」を30分で判断できる軽量アウトプット。

関連スキルとの役割分担:
- **SEO記事の見出し構成比較 → owned-media**（本スキルは事業・商品の市場/競合分析。記事の見出し構成は扱わない）
- **フレームワークの知識解説・演習（「3Cって何？」等）→ consulting-quiz**（本スキルは実分析のみ。フレームワークの説明は行わない）
- **分析後の施策立案・提案書化 → document-creation の提案書**（本スキルは差別化機会の列挙まで。施策の具体化はしない）
- **調査の実行手順 → hermes-x-search**（本スキルはクエリ本文の設計とレポート整形のみ）

## 発動条件

- 市場規模・成長性・参入判断の分析を頼まれたとき
- 競合の機能・価格比較やポジショニングマップを頼まれたとき
- 競合の弱点から自社の差別化ポイントを出すことを頼まれたとき
- 「市場分析して」「競合を調べて」「TAM/SAM/SOMを出して」のような依頼
- **すでにデータが揃っていて整形だけ求められた場合は、下記ワークフローの Step 2（調査クエリ設計と実行）を飛ばし、Step 1 で手元素材を確認した上で Step 3 に進む**
- 次の依頼は本スキルでは扱わない（案内して終了する）:
  - SEO記事の競合構成調査 → owned-media を案内
  - フレームワークの知識質問（例:「3Cって何？」）→ consulting-quiz を案内

## 前提セットアップ

外部依存: hermes-relay ブランチへの git push（調査工程で必須）。push・ポーリングの
具体的な手順（`automation/queries/pending/` への配置、結果取得、トラブルシュート）は
`plugins/hermes-x-search/skills/hermes-x-search/SKILL.md` の「Automated relay」節に
従う（本スキルでは二重管理しない）。ローカルPCの watcher と NotebookLM ログインは
ユーザー側セットアップ済みが前提。

**Claude 自身の WebSearch / WebFetch はこのスキルの調査工程で使わない。**
relay がタイムアウト・エラーになっても Claude 自身の検索には切り替えない（§7 参照）。

## ワークフロー

### Step 0: モード判定と振り分け

ユーザーの依頼文から市場分析 / 競合分析 / ボトルネック分析のどのモードか判定する。

- SEO記事の競合構成調査なら owned-media を、フレームワークの知識質問なら consulting-quiz を案内して終了する（分析工程を開始しない）。
- 判定できない場合は「何を決めたい分析か」を1回だけ聞く。

### Step 1: ヒアリング

共通5問（ユーザーの最初の発言で判明している項目は飛ばし、不明分だけまとめて1回で聞く）:

| # | 質問 | 使い道 |
|---|---|---|
| 1 | 分析対象は何か（業界・商品・サービスを1文で） | 調査 topic の確定 |
| 2 | 読み手は誰か（社内上司 / クライアント / 自分） | 出力形式の選択（社内向けレポート or 軽量版） |
| 3 | この分析で何を決めたいか（参入判断 / 提案の根拠 / 差別化方針） | 示唆（So What）の照準 |
| 4 | 手元にある素材（社内資料・既知の競合名・過去調査） | relay クエリの削減。機密素材は relay に載せない判定 |
| 5 | 期限と深さ（今日中の速報 / 数日かけた本調査） | クエリ本数の決定（速報=1本、本調査=モード規定数） |

モード別の追加1問:

| モード | 追加質問 |
|---|---|
| 市場分析 | 市場の地理・顧客セグメント境界はどこか（例: 国内・中小企業向けに限定するか） |
| 競合分析 | 比較したい競合は特定済みか（社名リスト有無。無ければ競合特定クエリを先行させる） |
| ボトルネック分析 | 自社（またはクライアント）が動員できる強みは何か（弱点→機会の変換に必須） |

ユーザー素材（質問4）に機密（クライアント実名・未公開の価格戦略等）が含まれるか判定する（機密一般化ルールは後述）。

### Step 2: 調査クエリ設計と実行

下記「hermes-relay 調査クエリテンプレート」に値を埋め、機密一般化ルールを適用し、
hermes-x-search SKILL.md の手順で push → バックグラウンド Bash でポーリングする。

クエリ本数:
- 市場分析 = クエリA × 1
- 競合分析 = クエリB（特定1本 + 社別最大5本。競合特定済みなら社別のみ）
- ボトルネック分析 = クエリC × 最大3本
- 連鎖依頼（例:「市場も競合も」）なら合算。速報指定なら各モード1本に絞る

ユーザー素材（ヒアリング質問4）で埋まる項目のクエリは発行しない。

### Step 3: 分析（フレームワークへの流し込み）

調査結果 + ユーザー素材から、モードに対応するフレームワークの表を埋める。
出典URLの無い主張は「未確認」にする。

- 市場分析 = (1)3Cサマリー (2)TAM/SAM/SOM (3)PEST（軽量版は(3)省略・(2)はSOMのみ）
- 競合分析 = (4)機能・価格比較表 (5)ポジショニングマップ
- ボトルネック分析 = (6)バリューチェーン弱点→機会変換表（(4)(5)が未実施なら先に競合分析モードを実行することを伝えてから連鎖実行）

### Step 4: レポート整形

Step 3 の表とヒアリング質問2（読み手）から、読み手が社内/クライアントなら
「出力形式①: 社内向け分析レポート」、自分なら「出力形式②: 副業向け軽量版」で整形する。
チャット提示し、ユーザー希望時にファイル保存する。

3モードの連鎖依頼（「市場も競合も」）では市場→競合→ボトルネックの順で実行し、
レポートは1本にまとめる（「2. 調査結果」節にモードごとの小節を切る）。

### Step 5: セルフチェックと提示

提示前に次を確認する。

1. 全ての事実行に出典URLまたは「仮定」「未確認」ラベルがあるか
2. 示唆がヒアリング質問3「決めたいこと」に答えているか
3. 未確認事項が結論への影響度（高/中/低）付きで明示されているか
4. 機密（実名・金額・未公開情報）が relay クエリに漏れていないか（事後確認）

全て通ったら提示し、追加調査の要否を1回だけ確認して終了する。

## 収録フレームワーク6個（確定。増やさない）

5Forces・SWOT・7S・4P・アンゾフは収録しない（5Forces は PEST+競合比較で代替可、
SWOTは再整理で新情報を生まない、7Sは組織診断でユースケース外、4P・アンゾフは
本スキルの出口=差別化機会の特定より先の施策立案フェーズの道具。「この枠が欲しい」が
3件以上発生したら追加検討）。フレームワークの知識解説は consulting-quiz が担当。

| モード | フレームワーク |
|---|---|
| 市場 | 3Cサマリー |
| 市場 | TAM/SAM/SOM |
| 市場 | PEST |
| 競合 | 機能・価格比較表 |
| 競合 | ポジショニングマップ（2軸） |
| ボトルネック | バリューチェーン弱点→機会変換表 |

### (1) 3Cサマリー

- 入力: ヒアリング結果 + relay 調査結果（市場クエリ）
- 手順: Customer（市場規模・成長率・顧客の購買決定要因）→ Competitor（主要プレイヤーとシェア）→ Company（自社/クライアントの強み・制約）の順に事実を埋め、各行に示唆を書く
- 出力テーブル:

| 観点(Customer/Competitor/Company) | 事実（出典URL付き） | 示唆(So What) |
|---|---|---|

- 制約: 示唆列が空の行を残さない。事実が取れなかった観点は「未確認」と書き、示唆列に「追加調査の要否」を書く

### (2) TAM/SAM/SOM

- 入力: 市場定義（ヒアリングのモード別質問）+ 統計・業界レポートの数値（relay 調査）+ 単価・顧客数の仮定
- 手順: ①トップダウン（公表市場規模 × 絞り込み率）とボトムアップ（顧客数 × 単価 × 購入頻度）の両方で計算 ②2つの結果の乖離が3倍を超えたら仮定を疑い、どちらを採用したか理由を書く
- 出力テーブル:

| 層(TAM/SAM/SOM) | 市場の定義 | 計算式（仮定を式中に明記） | 金額 | 出典/仮定の根拠 |
|---|---|---|---|---|

- 制約: 出典のない数値は「仮定」とラベルし、仮定だけで構成された層には「フェルミ推定」と明記する

### (3) PEST

- 入力: relay 調査結果（市場クエリの規制・マクロ環境セクション）
- 手順: Politics/Economy/Society/Technology の4分類で事実を集め、対象事業への影響方向（追い風/向かい風）と時期を付ける
- 出力テーブル:

| 分類(P/E/S/T) | 事実（出典URL付き） | 事業への影響（追い風/向かい風 + 1文） | 時期・確度 |
|---|---|---|---|

- 制約: 4分類とも最低1行。埋まらない分類は「該当事実の調査で確認できず」と書く（無言で省略しない）

### (4) 機能・価格比較表

- 入力: 競合リスト（ヒアリング or 競合特定クエリ）+ 各社の relay 調査結果
- 手順: ①比較項目を顧客の購買決定要因から5〜8個選ぶ（機能の全列挙をしない）②自社/クライアントを必ず1列含める ③価格は「プラン名・金額・課金単位」を分離する
- 出力テーブル（機能）:

| 比較項目 | 自社 | 競合A | 競合B | 競合C | 出典URL |
|---|---|---|---|---|---|

- 出力テーブル（価格）:

| 社名 | プラン名 | 価格 | 課金単位（月額/年額/従量） | 無料枠 | 出典URL |
|---|---|---|---|---|---|

- 制約: 競合は最大5社（超えたら購買決定要因への影響が大きい順に切る。除外した社名は脚注に列挙）。確認できなかったセルは「－（未確認）」と書き、空欄にしない

### (5) ポジショニングマップ（2軸・Markdown表現）

- 入力: 機能・価格比較表（(4)の完成が前提。単独では作らない）
- 手順: ①軸は顧客の購買決定要因の上位2つから選ぶ（価格 × 主要機能軸が既定。ヒアリング質問3の決定事項に合わせて差し替え可）②各社を「高/中/低」の3段階で両軸に配置 ③空白セル（=競合不在の組み合わせ）を特定する
- 出力テーブル:

| 軸1＼軸2 | 低 | 中 | 高 |
|---|---|---|---|

の3×3表に社名を配置し、直後に「空白地帯: <セル> — <参入余地の評価1〜2文>」を必ず書く。
- 制約: 図版・mermaidは使わない（Markdown表で足りる）

### (6) バリューチェーン弱点→機会変換表

- 入力: 競合分析の結果（(4)(5)）+ 各競合の評判・レビュー調査（ボトルネッククエリ）+ 自社の強み（ヒアリングのモード別質問）
- 手順: ①対象業界のバリューチェーンを5〜7工程で列挙する（例: 集客→提案→契約→提供→サポート→更新。業界に合わせて工程名を置き換える）②各工程で競合の弱点を事実（レビュー・公開情報）から拾う ③弱点ごとに「顧客が被る不利益」→「自社の強みで埋められるか」を評価する
- 出力テーブル:

| 工程 | 競合の弱点（事実 + 出典URL） | 顧客への影響 | 自社の差別化機会 | 実行難易度(高/中/低) |
|---|---|---|---|---|

- 制約: 「差別化機会」列は自社の強み（ヒアリング済み）と紐づかないものを書かない。弱点が見つからない工程は行ごと省略してよい（全工程を埋めることが目的ではない）

## hermes-relay 調査クエリテンプレート（確定）

置き場所・push手順・ポーリングは `plugins/hermes-x-search/skills/hermes-x-search/SKILL.md`
が正（`automation/queries/pending/<UTC時刻>-<slug>.md`、結果は1〜4分後に `automation/results/`）。
本スキルはクエリ本文のみ規定する。共通ルール:

- ヘッダは `engine: notebooklm` + `topic: <調査トピック15字以内>` の2行
- 本文にASCIIダブルクォート（`"`）を使わない（強調は「」を使う）
- 1ファイル1トピック。市場規模と競合リストを1クエリに混ぜない
- 全セクションで「主張1つにつき根拠URL1つ」を要求し、「未確認・断定できない点」セクションを必ず含める
- クライアント実名・未公開情報を本文に書かない（下記の機密一般化ルールを適用）
- テンプレートの `<>` 置換以外の改変（セクション追加・削除）はしない。調査観点を増やしたい場合は別クエリファイルとして追加する（1ファイル1トピック維持）

### クエリA: 市場調査（市場分析モードで1本）

```
engine: notebooklm
topic: <業界名>の市場規模と動向

<業界名>（<地理・セグメント境界>）について、日本語で次のセクション構成で回答してください。

1. 市場規模と成長率 — 公表されている市場規模の推計値（複数あれば併記）、直近3年の成長率
2. 市場の構造 — 主要な顧客セグメントと、顧客が製品・サービスを選ぶ決定要因
3. 規制・マクロ環境 — 政治・経済・社会・技術の観点で、この市場に影響する動き
4. 根拠URL — 上記の主張1つにつき出典URLを1つ、対応が分かる形で列挙
5. 未確認・断定できない点 — 推計が割れている数値、出典が見つからなかった主張
```

### クエリB: 競合特定・比較調査

競合分析モードで、競合未特定なら本クエリ（競合特定）→社別クエリの2段。特定済みなら
社別クエリのみ。社別は最大5本。

競合特定:

```
engine: notebooklm
topic: <業界名>の主要プレイヤー

<業界名>（<地理・セグメント境界>）の主要な企業・サービスについて、日本語で次のセクション構成で回答してください。

1. 主要プレイヤー一覧 — 企業名・サービス名と1行説明（最大10件、シェアや知名度の高い順）
2. 各社の位置づけ — 価格帯（高/中/低）とターゲット顧客の違い
3. 根拠URL — 主張1つにつき出典URLを1つ
4. 未確認・断定できない点
```

社別（競合1社につき1本）:

```
engine: notebooklm
topic: <サービス名>の機能と価格

<企業名>の<サービス名>について、日本語で次のセクション構成で回答してください。

1. 提供機能 — 主要機能の一覧（特に<比較項目リスト>の各項目に該当する情報）
2. 価格 — プラン名・金額・課金単位・無料枠
3. ターゲット顧客と訴求点 — 公式サイトが打ち出している顧客層と強み
4. 根拠URL — 主張1つにつき出典URLを1つ（価格は公式ページのURL必須）
5. 未確認・断定できない点
```

### クエリC: 競合の弱点・評判調査

ボトルネック分析モードで競合1社につき1本、最大3本。

```
engine: notebooklm
topic: <サービス名>の評判と課題

<企業名>の<サービス名>の利用者評価について、日本語で次のセクション構成で回答してください。

1. 利用者からの不満・低評価点 — レビューサイト・比較記事・導入事例で言及される弱点
2. 弱点が現れる場面 — 導入時・利用中・サポート・解約時のどの工程での不満か
3. 良い評価点 — 弱点の裏返しの確認用に、評価されている点も列挙
4. 根拠URL — 主張1つにつき出典URLを1つ
5. 未確認・断定できない点 — 少数の声にすぎない可能性があるもの、投稿時期が古いもの
```

## 出力形式①: 社内向け分析レポート（インターン業務用）

document-creation の原則（事実と意見の分離・1文60文字目安・社内フォーマルトーン）を
継承しつつ、本文は**結論の言いっぱなしを避けたプロセス重視構成**にする: 冒頭サマリーで
結論を1度示した後、本文は「前提→調査→分析→示唆」の順で、読み手が同じ結論に到達できる
道筋を再現する。

```markdown
# <対象>の<市場/競合/ボトルネック>分析
- 作成日: YYYY-MM-DD / 作成者: <名前> / 読み手: <宛先>

## サマリー（結論と限界を3行で）
- 結論: <分析から言えること1〜2文>
- 根拠の強さ: <出典付きの事実N件 / 仮定M件に基づく>
- 限界: <未確認事項のうち結論を覆しうるもの1つ>

## 1. 分析の前提
- 目的（何を決めるための分析か）/ 対象の定義・境界 / 調査期間と調査手段
```

## 機密一般化ルール

relay クエリを設計する際に必ず適用する。

1. relay クエリにはクライアント・自社の実名、未公開の金額・戦略を書かない。
2. 実名は「<業界名>の<事業形態>企業」の形の一般名詞に置換する（例: 地方都市ガス事業者）。
3. 置換で調査精度が成立しない場合（その企業自体の評判調査等、対象が公開企業で調査内容が
   公開情報のみの場合）に限り実名可。判断に迷ったらユーザーに確認する。

レポート本体には実名を書いてよい（ローカル成果物のため）。ただしリポジトリへのコミットはしない。

## エッジケース

| ケース | 期待挙動 |
|---|---|
| relayの結果が15分待っても返らない（タイムアウト） | 再pushはせず、hermes-x-search SKILL.mdのトラブルシュート（watcher.log確認）を案内。ユーザーが急ぐ場合は「ユーザー自身が素材（競合の公式ページのコピー・手元資料）を貼る」代替でStep 3に進む。ClaudeのWebSearchには切り替えない |
| 結果のstatus: error | 本文のstderrを読んで原因を報告。同一クエリの盲目的再pushをしない |
| 調査結果に出典URLが無い主張が多い | 該当主張を全て「未確認」に落とし、レポート「5. 未確認事項」に集約。断定表現に書き換えない |
| 市場規模の公表値が見つからない | ボトムアップのフェルミ推定（仮定を式中に明記）でSOMのみ算出し、TAM/SAMは「公表値なし」と書く |
| ユーザーが調査済みデータを持参 | Step 2をスキップまたは不足分のみクエリ発行。持参データにも出典（社内資料名・取得日）を付けて表に載せる |
| 依頼に機密（クライアント実名・未公開の価格戦略）が含まれる | relayクエリでは業界一般語に置換（機密一般化ルール）。レポート本体には実名を書いてよい（ローカル成果物）。リポジトリへのコミットはしない |
| 競合が6社以上見つかった | 購買決定要因への影響が大きい順に5社へ絞り、除外した社名を脚注に列挙 |
| ボトルネック分析を単独依頼されたが競合比較が未実施 | 競合分析モードを先に実行することを伝えてから連鎖実行（(6)は(4)(5)に依存） |
| 「速報で」と「本調査」の指定がない | ヒアリング質問5で必ず確認。回答がなければ速報（各モード1クエリ）で開始し、深掘りは結果提示後に提案 |

## セルフチェック

提示前に次を確認する（Step 5 と同一）。

1. 全ての事実行に出典URLまたは「仮定」「未確認」ラベルがあるか
2. 示唆がヒアリング質問3「決めたいこと」に答えているか
3. 未確認事項が結論への影響度（高/中/低）付きで明示されているか
4. 機密（実名・金額・未公開情報）がrelayクエリに漏れていないか（事後確認）
5. 出力テーブルの列名がフレームワーク定義から変更されていないか（列の追加要望が
   ユーザーから出たら追加してよいが、削除はユーザー確認）

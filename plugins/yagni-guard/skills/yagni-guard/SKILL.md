# YAGNI Guard（ponytail 方式・過剰設計防止）

目的は **依頼された分だけを、最小の形で実装する**こと。
本家 [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail)（コード量約54%削減）の
「怠け者のシニアエンジニア」哲学をこのリポジトリ用に再構成したもの。
大原則: **「最良のコードは書かれなかったコード」**。怠惰＝効率。

## 発動条件

- 新しい関数・クラス・設定フラグ・抽象化レイヤー・依存を書こうとしている時。
- 依頼にない「将来のために」「汎用的に」という拡張をしそうになった時。
- diff・PRのレビューで過剰設計を検出したい時（下記「レビューモード」）。
- ユーザーが「シンプルに」「YAGNIで」「ponytail」と言った時。

## 持続ルール

- 一度発動したら**ユーザーが「stop ponytail」「通常モードで」と言うまで維持**する。
- デフォルト強度は **full**。

## 強度レベル

| レベル | 挙動 |
|---|---|
| **lite** | 依頼どおり作るが、より怠惰な代替案を1行で提案する。 |
| **full**（既定） | 判断ラダーを厳格に適用してから書く。 |
| **ultra** | YAGNI過激派。依頼された要件自体が本当に必要かまで問い直す。 |

## 判断ラダー（コードを書く前に、この順で止まれる所を探す）

1. **このタスク自体、存在する必要があるか？**（YAGNI）
2. **既にコードベースにあるか？**（既存の関数・パターンを再利用）
3. **標準ライブラリで済むか？**
4. **プラットフォームのネイティブ機能で済むか？**
5. **既にインストール済みの依存で済むか？**（新規依存は追加しない）
6. **1行で書けるか？**
7. ここまで全部 No の時だけ、**動く最小のコード**を書く。

## コアルール

- 頼まれていない抽象化・ボイラープレート・先回りの足場を作らない。
- **追加より削除**。賢いコードより退屈なコード。
- 最少ファイル数・最短の動くdiffを選ぶ。
- 意図的に簡略化した箇所には `ponytail:` コメントで上限と拡張パスを1行残す
  （例: `# ponytail: 直列処理。100件/日を超えたらキュー化`）。
- 出力はコード先行。説明は「何を省いたか」を最大3行。
- 抽象化は3箇所目の重複が出てから。2箇所なら重複のままでよい。
- 使う人が想定できない設定オプション・feature flag・後方互換シムを追加しない。

## 絶対に怠けてはいけないもの

- 外部入力のバリデーション（境界の検証は省略対象外）。
- エラーハンドリング（起こり得るケースについて）。
- セキュリティ。
- アクセシビリティ。
- ユーザーが明示的に要求した仕様。
- コードを書く前の問題理解（理解を省くのは怠惰ではなくただの手抜き）。

## レビューモード（/ponytail-review 相当）

diff・PRを過剰設計の観点**だけ**でレビューする。正確性バグ・脆弱性・性能は
通常レビュー（`code-review-adr` / `pr-review`）に回す。

5つの無駄タグで検出する:

| タグ | 検出対象 |
|---|---|
| `delete` | 未使用コード・置き換え先のない投機的機能 |
| `stdlib` | 標準ライブラリの再発明 |
| `native` | プラットフォーム組み込み機能で置き換え可能な依存・コード |
| `yagni` | 実装が1つしかない抽象化・未使用の設定・呼び出し元が1つのレイヤー |
| `shrink` | 同じロジックをより少ない行数で書ける箇所 |

出力形式（1指摘=1行厳守）:

```
L<行>: <タグ> <指摘>。<置き換え案>。
<ファイル>:L<行>: ...   ← 複数ファイルdiffの場合
net: -<N> lines possible.
```

指摘ゼロなら `Lean already. Ship.` とだけ出す。
最小限のテスト・アサーションは削除対象にしない。

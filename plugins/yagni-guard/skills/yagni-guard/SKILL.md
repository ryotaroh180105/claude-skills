# YAGNI Guard

目的は **依頼された分だけを、最小の形で実装する**こと。
コミュニティで広まっている "Ponytail" 的な発想（怠け者のシニアエンジニア人格）を、
チェックリストとして明文化したもの。トークンとコードの両方の無駄を削るが、
必要な処理を削るものではない。

## 発動条件

- 新しい関数・クラス・設定フラグ・抽象化レイヤーを書こうとしている時。
- 依頼にない「将来のために」「汎用的に」という理由で拡張しようとした時。
- 既存コードのレビュー・リファクタで「これは本当に呼ばれているか」と疑問に思った時。
- ユーザーが「シンプルに」「過剰設計しないで」「YAGNIで」と明示した時。

## 実装前チェック（コードを書く前に自問する）

1. **今回の依頼で本当に必要か？** — 「あると便利そう」は不要のサイン。
   依頼の文言に立ち返り、それを満たす最小の変更は何かを先に決める。
2. **同じパターンは何回出てくるか？** — 2箇所ならそのまま重複でよい。
   抽象化・ヘルパー化が要るのは3箇所目が出てからで十分なことが多い。
3. **その設定/フラグは誰が触るのか？** — 使う人が想定できない設定オプション・
   feature flag・後方互換シムは追加しない。
4. **そのエラーハンドリング/バリデーションは起こり得るケースか？** — 内部コードや
   フレームワークの保証を信頼する。境界（外部入力・外部API）だけ検証する。
5. **既存のものを直接変更できないか？** — 新しい抽象化を足す前に、
   既存の関数・設定を直接変更・拡張して済まないかを先に検討する。

## 実装後チェック(diffレビュー時)

- 依頼に書かれていない新しい公開APIや設定項目が増えていないか。
- 呼び出し元が1つしかないのに「汎用関数」として切り出していないか。
- テストされない分岐・到達しない分岐（防御的すぎるcatch/if）が増えていないか。
- コメントが「何をしているか」の説明になっていないか（自明なら削る。
  非自明な制約・理由の説明だけ残す）。
- 依頼の一部を先回りして「ついでに」直していないか（スコープ外の変更は
  別途確認してから着手する）。

## 判断に迷ったら

- 依頼が曖昧で「将来ここも変わりそう」と感じても、まず最小実装で確認を取ってから
  拡張する。先に全部作ってしまうと手戻りが大きい。
- 「3行の重複」と「1個の抽象化」を比べたら、まず3行の重複を許容する。
  重複が3箇所目に増えた時に初めて抽象化を検討する。
- 大きな設計判断（新しい依存の導入・アーキテクチャ変更）は、この場でチェックを
  終わらせず、ユーザーに一言確認してから進める。

## 外部依存

なし。実装前後のセルフチェックのみで完結する。`token-saver` スキルと併用すると、
コード量・応答量の両面で無駄を削れる。

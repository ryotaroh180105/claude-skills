# dev-catchup（開発キャッチアップ・引き継ぎ補助）

未知の、または中断していたコードベース／エージェント開発プロジェクトを読み、
**「今どこまで出来ているか」「次に何をすべきか」が一目で分かる引き継ぎサマリー**を
1本の Markdown として生成する。対象の品質を評価したり、書き換えたりはしない。

## いつ使うか

- 他人が作った開発を巻き取るとき（前任者不在で仕様書がない）
- 中断した自分の作業を数週間後に再開するとき（当時の文脈を失っている）
- 後任インターンに渡す引き継ぎ資料を作るとき
- エージェント開発（本リポジトリのような SKILL/plugin/agent 構成）の全体像を掴みたいとき

以下は本スキルの担当外。該当する場合は案内のみ行い、代行実行はしない（詳細は
「委譲先（本スキルが扱わないこと）」節）。

- データフローの図・シーケンス図が欲しい → code-flow-visualizer スキルを使う（実装済み）
- コードの品質評価・バグ指摘・レビューコメントが欲しい → code-review-adr
- これから作る機能の要件を定義したい → requirements-definition
- 抽出した「次にやること」を管理・優先順位付け・進捗追跡したい → task-management

## ワークフロー

### Step 0: 受付・規模判定

対象パス／URL を確認する。曖昧なら着手前に確認する（カレントリポジトリを既定候補として提示してよい）。

**ネガティブ確認**: 対象が単一ファイルかつ100行未満の場合、サマリーを作らず
「小規模のため直接読めば足りる」と返して終了する。

### Step 1: メタ把握（git 履歴）

次を順に取得する。git 管理外なら本 Step をスキップし、後述の「情報源メタ」に
「git 履歴なし」と明記してファイルの mtime で直近作業を代替推定する。git コマンドが
失敗した場合（git 未インストール等）もエラーで止めず、そのコマンドだけスキップして続行する。

- `git log --oneline -20` — 直近コミット
- `git shortlog -sn -20` — 貢献者
- `git log --pretty=format: --name-only -50 | sort | uniq -c | sort -rn | head` — 変更頻度（churn）上位ファイル
- `git branch -a` — 未マージブランチ

### Step 2: 読む優先順位（固定順）

巨大リポジトリ（目安 1,000 ファイル超）では上から順に読み、時間切れなら途中で打ち切って
「情報源メタ」に未読範囲を記録する。作りかけでも7セクションは必ず埋めて出力する。

1. `README*` / `CLAUDE.md` / `docs/` を読む（プロジェクトの自己申告）
2. パッケージ manifest（`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` 等）を読む（依存とエントリの宣言）
3. `git ls-files | head -200` 相当でディレクトリツリーを把握する（全体量を掴む）
4. Step 1 の churn 上位ファイルを読む（プロジェクトの重心＝最近触られている＝重要かつ流動的）
5. エントリポイント（manifest の `main`/`scripts`/`bin`、`if __name__`、`func main`、CI 定義）から
   呼び出しを1〜2段辿る
6. `rg -n "TODO|FIXME|XXX|HACK|not implemented|未実装|後で"` で未完了作業を全抽出する

README も manifest も無い場合は churn とエントリ探索への依存度を上げ、「概要」節は
推定であることを明記する。

### Step 3: 抽出

Step 2 の読解結果を、下記「出力フォーマット」の各セクション素材に整理する。
データフローは図ではなく箇条書きテキストで記述する。

### Step 4a: 委譲判定

以下に該当したら本スキルでは扱わず、案内だけして進める（Step 5 の出力自体は続けてよい）。

| 該当条件 | 委譲先 |
|---|---|
| データフローの図が必要 | code-flow-visualizer（実装済み） |
| コードの良し悪し・バグ指摘が欲しい | code-review-adr |
| これから作る機能の要件が欲しい | requirements-definition |
| 抽出した「次にやること」の管理・優先順位付け・進捗追跡をしたい | task-management |

### Step 4b: エージェント開発リポジトリ検出時の追加チェック

`**/SKILL.md` または `marketplace.json` または `.claude-plugin/plugin.json` を検出したら、
通常の抽出に加えて以下を「2. アーキテクチャ」「3. 現在地」節に含める。

- 各 plugin の SKILL.md の `name` / `description`（発動トリガー）一覧
- marketplace.json 登録済み/未登録の差分
- ROADMAP.md のステータス（未着手/実装中/完了）
- `.claude/agents/` のサブエージェント定義

### Step 5: 出力

- パス: `docs/handoffs/YYYY-MM-DD-<repo-slug>.md`（`<repo-slug>` はリポジトリのディレクトリ名を
  小文字化しスペースを `-` に置換したもの）
- `docs/handoffs/` が無ければ作成してよい（本スキル専用ディレクトリのため確認不要）
- 既存の同名ファイルがある場合は上書きせず、末尾に `-2`, `-3` を付す
- 生成後、ユーザーに要約を提示し、「次にやるべきこと」を task-management の Backlog に
  載せるか尋ねる（載せる操作自体は task-management に委ねる。本スキルは代行しない）

## 出力フォーマット（固定7セクション）

出力 Markdown は次の7セクションを**この順・この見出しで**必ず持つ。該当情報が無い
セクションも削除せず「該当なし（理由）」と書く（空欄は「未調査」と区別できないため）。

```markdown
# 引き継ぎサマリー: <リポジトリ名>

| 項目 | 値 |
|---|---|
| 調査日 | YYYY-MM-DD |
| 対象 | <パス or リポジトリURL> / <調査時点のコミットハッシュ> |
| 調査者 | <名前 or セッション> |
| 規模 | 約 N ファイル / 主要言語 <lang>（M%） |

## 1. 概要（3行で何のプロジェクトか）
<何をするものか・誰のためか・現在の成熟度（PoC/開発中/運用中）を3〜5行>

## 2. アーキテクチャ
- エントリポイント: <ファイル:行 or コマンド>
- 主要モジュール: <ディレクトリ/ファイル → 役割> を表で3〜10件
- データフロー: <入力→処理→出力を箇条書き。図が要るなら「08-code-flow-visualizer を実行」と明記>
- 外部依存: <API/DB/MCP/SaaS/主要ライブラリ → 用途> を表で
- 設定・秘密情報: <env / 設定ファイルの場所と必要キー名（値は載せない）>

## 3. 現在地（どこまで出来ているか）
- 動くもの: <確認できた稼働機能>
- 未完成・スタブ: <未実装・TODO・FIXME・空関数を file:line 付きで>
- 直近の作業: <git log 直近10件から推定した「最後に何を触っていたか」>

## 4. 次にやるべきこと
- [ ] <着手候補。根拠（どの TODO / どの中断点か）を1行添える>
（task-management へ渡す場合はこの節をそのまま Backlog に転記できる粒度で書く）

## 5. 詰まりどころ・落とし穴
- <ビルド/起動の非自明な前提、壊れやすい箇所、暗黙の依存、危険な操作>

## 6. 用語集
| 用語 | 意味 | 出典 file:line |
|---|---|---|
| | | |

## 7. 情報源メタ
- 読んだ主要ファイル: <パス列挙>
- 未読・不明で確認が必要: <時間切れ/権限で読めなかった箇所。無ければ「なし」>
```

## エッジケース

| ケース | 期待挙動 |
|---|---|
| 対象が単一ファイル・100行未満 | サマリーを作らず「小規模のため直接読めば足りる」と返す |
| git 管理外のディレクトリ | Step 1 をスキップ。「情報源メタ」に「git 履歴なし」と明記し、ファイル mtime で直近作業を代替推定 |
| 巨大リポジトリ（目安 1,000 ファイル超）で時間切れ | Step 2 の優先順で読めた範囲までで7セクションを埋め、未読を「情報源メタ」に列挙。作りかけでも必ず出力する |
| README も manifest も無い | churn とエントリ探索への依存度を上げ、「概要」は推定と明記する |
| TODO/FIXME が0件 | 「未完成・スタブ」に「明示マーカーなし。未マージブランチ／空関数から推定」と書く。空欄にしない |
| リモートのみ（未 clone）でローカルに無い | GitHub MCP があれば `get_file_contents` 等で主要ファイルのみ取得。無ければ clone を促す |
| 対象が曖昧（パス未指定） | 着手前に対象を確認。カレントリポジトリを既定候補として提示 |

## 注意点

- 書き換えは一切しない。対象コードの修正・フォーマット・リファクタは本スキルの責務外（読み取り専用）。
- 委譲は案内のみ。08-code-flow-visualizer / code-review-adr / requirements-definition /
  task-management を代行実行しない。
- 秘密情報: env・設定ファイルにキーの実値を見つけてもサマリーに転記しない。キー名と場所のみ記す。
- サマリーは日本語固定（多言語出力はしない）。
- 判断に迷いこのファイルに無いものは、着手前にユーザーへ確認する。

# skill-design-rigor（設計規律・Fable-Sonnet運用ブリッジ）

目的: 設計する側（Fable/Opus）の意図を、実装する側（Sonnet）が**質問なしで**実装できる
粒度まで落とす。手戻りは「設計が曖昧だった」ことの結果であり、実装の巧拙ではない。

## 発動条件

- 新しいスキル・アプリ・パイプラインを設計する時。
- Sonnet（や他の実装担当）に渡す指示書・依頼文を書く時。
- 既存の設計書・指示書をレビューする時。
- ユーザーが「設計して」「指示書を書いて」「Sonnetに渡して」「壁打ち前に整理して」と言った時。

## 使い方

1. 依頼を受けたら、書き出す前に **計画ゲート5項目** に回答する（§1）。
2. `docs/designs/TEMPLATE.md` をコピーして `docs/designs/NN-<slug>.md` を作成し、全12
   セクションを埋める（NN は既存ファイルの最大連番+1。空欄は「該当なし」と明記する）。
3. 書き終えたら **自己反証＋刈り込み4項目** を実行する（§2）。
4. 設計書のステータスを「設計完了」にして、実装セッションには §3 の定型プロンプトで渡す。

## 1. 計画ゲート（執筆前に回答を書き出す）

1. この設計が失敗する最も確率の高いパターンは何か（最低3つ）。
2. スコープの境界線はどこか — 「ついでにやりそうで、やらないこと」は何か。
3. 完成条件を、実装者が単独で真偽判定できる文で書けるか。
4. 実装者が最初に詰まる箇所はどこか。そこに先回り回答を書いたか。
5. この作業は本当に必要か（既存スキル・既存設計書で代替できないか）。

回答5の結論が「不要／既存で代替可能」なら、設計を進めずその旨を報告して終了する。

## 2. 自己反証＋刈り込み（執筆後に実行する）

1. 自分の指示に対し「これでは動かない」と反証を試みる（最低1周）。
2. 1文ずつ読み、削っても意味が変わらない文を削る（形容詞・重複説明が対象。データ・数値・
   URL・コードは削らない）。
3. 「〜など」「適宜」「必要に応じて」を検索し、全て確定値または「実装時判断ルール」節に
   置換する。
4. テスト・検証手順が「実行結果の観察」になっているか確認する（コードを読んで確認、は不可）。

## 3. Sonnet 実装セッション開始プロンプト（定型文）

設計書を実装担当に渡すときは、以下をそのまま使う。

```
docs/designs/<NN-slug>.md を読み、設計書どおりに実装してください。
- 完成条件（§3）を1項目ずつ検証し、全て満たすまで終了しない
- スコープ外（§2.2）には一切手を出さない
- 迷ったら §11 実装時判断ルールに従う。書かれていない判断は AskUserQuestion で確認
- 実装完了後、設計書のステータスを「実装完了」に更新してコミットに含める
- effort: high。token-saver / yagni-guard 常時適用（CLAUDE.md どおり）
```

## 4. effort 運用ルール

| 作業 | モデル | effort |
|---|---|---|
| 設計・要件定義・アーキテクチャ判断 | Fable/Opus | max |
| 設計書に基づく実装 | Sonnet | high |
| 定型作業（整形・一括変換・転記） | Sonnet/Haiku | low〜medium |

## 5. 小タスクの例外

見積もり30分未満の作業には設計書は不要（口頭指示でよい）。それ以上の見積もりになったら
テンプレの簡易版（§1〜3・§9のみ）を先に書く。

## 6. 設計書が実装後に腐らないためのルール

- 実装完了時、設計書ステータスを「実装完了」に更新することをコミットに含める
  （更新なしで実装だけ終わらせない）。
- 実装済みの設計書は遡及修正しない。テンプレ改訂は今後の新規設計書にのみ適用する。
- 実装中に設計の欠陥を見つけても勝手に設計変更しない。設計書 §12（未解決事項）に追記し
  AskUserQuestion でユーザーに確認する。

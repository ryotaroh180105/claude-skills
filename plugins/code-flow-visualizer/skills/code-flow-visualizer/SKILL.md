# Code Flow Visualizer

指定された**エントリポイント1つ**を起点に既存コードを静的に読み、処理の流れを
Mermaid 記法の図として生成するスキル。未知のコードベースに入った人が処理の
流れを追い、全体像を素早く掴めるようにすることが目的。

**発動境界（重要）**: 本スキルはコードの流れの**可視化のみ**を担当する。
品質の良し悪しの指摘・バグ検出は `code-review-adr`、アーキテクチャ決定の記録
（ADR）も `code-review-adr`、要件の構造化は `requirements-definition` の担当。
「レビューして」「品質を見て」という依頼には本スキルは発動しない。

## いつ使うか

- インターン・新規参画者が未知コードの全体像を掴みたいとき
- 他人にコードの流れを説明する資料を作りたいとき
- 自分の実装を後から見返すための図が欲しいとき
- 「この関数の処理フローを図にして」「`POST /orders` の流れをシーケンス図にして」
  のように、既存コードの制御フロー・データフローの可視化を求められたとき

## やらないこと（スコープ外）

- コードレビュー・品質指摘・バグ検出（図中に「ここはバグ」等の評価を書かない）
- アーキテクチャ決定の記録（ADR）
- 要件定義・仕様の構造化
- 動的解析・実行トレース・カバレッジ計測（静的読解のみ）
- リポジトリ全体を1枚で網羅する図（読めないため方針として拒否）
- 図の自動コミット・自動PR（生成物は既定で作業ディレクトリ止まり）
- 図の自動更新・CI連携・常駐化（都度生成のみ）
- flowchart / sequenceDiagram 以外の UML 記法（クラス図・ER図・状態遷移図等）
- Mermaid 以外の作図ツール（PlantUML / Graphviz / draw.io 等）

## ワークフロー

### Step 1: 入力粒度確定フロー

エントリポイントを1つに確定してから着手する。まだ着手しない。

1. 依頼が次のいずれかに該当する → そのまま採用しStep 2へ:
   関数/メソッド1つ、APIパス1つ、CLIサブコマンド1つ、ファイル1つ、明確な1ユースケース。
2. 「リポジトリ全体」「このディレクトリ全部」「ぜんぶ」など粒度が広すぎる場合
   → **着手前に分割提案**する。`main`/ルーティング定義/公開API/CLI定義/`README`
   記載の入口からエントリポイント候補を最大5件列挙し、「まずどの1フローから
   図にするか」をユーザーに選ばせる。図生成には進まない。
3. 対象が特定できない → 対象ファイル/関数を質問する。推測で描き始めない。

### Step 2: 読解

エントリポイントから静的にコールグラフ・分岐・ループ・早期return・外部I/O
（DB/API/ファイル/キュー）をたどる。

- **上限（確定値）**: 深さ**3階層**、または1図あたりノード**25個**。どちらか
  先に達した時点で打ち切り、打ち切り点を「詳細は別図」ノード（破線）として残す。
  ユーザーが上限変更を指示したら従う。
- **推測禁止（確定）**: 動的ディスパッチ・DI・リフレクション等で呼び出し先が
  静的に解決できない箇所は、関数名からの推測で矢印を引かない。
  「動的呼び出し（解決先不明）」ノードにし、読み方注記に「静的解析の限界」と明記する。

### Step 3: 記法選択ルール

- 単一コンポーネント内の分岐・ループ・処理順を描くなら `flowchart TD`。
- 複数のコンポーネント/サービス/レイヤー（クライアント⇄API⇄DB 等）をまたぐ
  呼び出し順とデータの往復を描くなら `sequenceDiagram`。
- 両方の性質がある場合、既定は `flowchart`。ユーザーが「シーケンス図で」と
  言えば `sequenceDiagram` に切り替える。

### Step 4: 図生成

`templates/flow-markdown.md` に流し込む。以下を必ず含める:

- 全ノードの `file:line` 対応表（コードを読んだ根拠を明示。根拠のないノードを作らない）
- 読み方の注記（菱形=分岐、二重枠=外部I/O、破線=別図に続く 等）
- 打ち切り理由（深さ上限 / ノード上限 / I/O境界）

### Mermaid 表現限界時の縮退手順

矢印が錯綜する・並行分岐が読めなくなる（= Mermaid の表現限界を超える、degrade
判断が必要）と判断したら、順に試す。

1. `subgraph` でグルーピングする
2. 枝を別図（別ファイル）に分割し「別図に続く」破線ノードで繋ぐ
3. `flowchart` → `sequenceDiagram` に記法変更する
4. それでも不可なら Mermaid をあきらめ、「番号付きステップ箇条書き + 補足文」
   で出力し、Mermaid 化できなかった旨を注記する

### Step 5: 構文検証（提示前に必須）

生成した Mermaid を提示前に必ず検証する。壊れていれば修正して再検証する。

- **標準手順**: `npx -y @mermaid-js/mermaid-cli -i flow.md -o flow.svg` を
  実行し exit code 0 を確認する。
- **npx/ネットワーク不可環境の目視チェックリスト**（代替手順。全項目を確認する）:
  1. `flowchart TD` または `sequenceDiagram` の宣言行がある
  2. 全ノードIDが英数字である
  3. 矢印（`-->` / `->>` 等）の左右にノードが存在する
  4. `subgraph` を使った場合、対応する `end` がある
  5. 日本語ラベルは `["..."]` のように囲まれている

構文エラーのある Mermaid をそのまま提示してはいけない。

### Step 6: 出力・成果物の置き場ルール

- **既定**: `./flows/<entrypoint-slug>.md` に保存し、チャットにも内容を表示する
  （`./flows/` が無ければ作成する）。
- **HTML（要望時のみ）**: ユーザーが自己完結HTMLを希望した場合のみ
  `./flows/<entrypoint-slug>.html` を追加生成する。`templates/flow-standalone.html`
  をベースにする。外部CDNは使わず、Mermaid ランタイムをインライン同梱できるなら
  それを使い、取得不可なら**レンダリング済みSVGをインライン埋め込み**に切り替える。
  いずれの場合も生成HTMLは外部ホストへ一切リクエストしない。
- **リポジトリへのコミットはしない**（生成物であり、コードと二重管理になると
  すぐ腐るため）。ユーザーが「コミットして」「`docs/` に置いて」と明示した
  ときのみ、置き場を確認してから従う。CLAUDE.md の常時適用スキルとは無関係に
  この置き場ルールは固定。

## エッジケース

| ケース | 期待挙動 |
|---|---|
| 「リポジトリ全体を図にして」 | 1枚で描かない。Step1 の分割提案フローでエントリポイント候補を最大5件提示し、1フローを選ばせる |
| 対象が巨大（深さ/ノード上限超過） | 上限で打ち切り、打ち切り点を「別図に続く」ノード（破線）にする。続きは要望があれば別ファイルの図として追加生成 |
| Mermaid で表現しきれない複雑さ | Step4 の縮退手順（①subgraph ②別図分割 ③記法変更 ④箇条書きに切替）を順に試す |
| 生成した Mermaid が構文エラー | 提示しない。修正して再検証する。npx が使えない環境では目視チェックリストで確認する |
| 動的呼び出し・リフレクション・DIで呼び出し先が不明 | 推測で矢印を引かず「動的呼び出し（解決先不明）」ノードにし、「静的解析の限界」と明記する |
| コードが読めない（対象ファイルが存在しない/空） | 図を作らず、対象の再指定を求める |
| HTML出力でMermaidランタイムを外部CDNから取れない | レンダリング済みSVGをインライン埋め込みする方式に切り替える（外部リクエスト無し） |
| 生成物をコミットしてほしいと言われた | 置き場（`docs/flows/` 等）と、実データ扱いでコミットするか作業ディレクトリ止まりかをユーザーに確認してから従う |
| 「このコードの品質をレビューして」 | 本スキルは発動せず `code-review-adr` に委ねる（可視化のみで評価しない） |

## 前提セットアップ

外部依存なし。Mermaid のレンダリングは閲覧側（GitHub/エディタ）が担うため、
生成側に追加の依存インストールは不要。

| 依存 | 必須? | 用途 |
|---|---|---|
| なし | - | Markdown+Mermaid の生成、目視チェックリストによる構文確認 |
| `npx -y @mermaid-js/mermaid-cli` | 任意 | 構文検証をコマンドで自動化したい場合（ネットワーク不可なら目視チェックリストで代替） |

# Personal Growth Strategy Engine（成長戦略エンジン）

## 目的

上司・クライアントからのフィードバックは散発的に来るだけで、「評価者が何を
期待していて、自分の成果物がどこでズレているか」を横断的に把握する仕組みが
なければ蓄積されない。本スキルは、蓄積したフィードバックログと制作物記録から

1. 評価軸のズレ診断（7観点 × 0/1/2 スコア × 証拠引用必須）
2. 技術成果のROI翻訳（事業価値への計算式ベースの翻訳）
3. ティア別アクションリスト生成（Tier S / Tier A）

を再現可能な手順で行い、「業務改善・評価最大化アクションリスト」を出力する。
クライアント向け提案の組み立て（モード5）も同じ診断・ROIテンプレートを転用して
行う。

## 発動条件

- 「成長戦略エンジンをセットアップして」（モード0）
- 「フィードバックを記録して」「この制作物を記録して」（モード1）
- 「ズレ診断して」「評価軸を分析して」（モード2）
- 「ROIレポートにして」「事業価値に翻訳して」（モード3）
- 「アクションリストを作って」（モード4）
- 「クライアント向けに論理とROIで提案を組み立てて」（モード5）
- 「評価」「フィードバック」「成長」「ROI」「アクションリスト」を含む、
  複数タスク・複数フィードバックを横断する依頼

### 発動しない場合（除外条件）

- 単発の書類作成・メール修正・トーン調整のみの依頼 → **document-creation** に譲る
  （例:「このメールを直して」「議事録にまとめて」）
- 単一タスクの着手前チェック・報連相・完了報告の相談 → **work-approach-playbook** に譲る
- ACTIONS.md の項目を TODO.md へ転記したいだけの依頼 → **task-management** に譲る
  （本スキルは転記の一言案内はするが、自動転記はしない）

迷ったら、依頼が「1件の成果物・1件のタスク」で閉じているか「複数件を跨いだ
傾向・戦略」を求めているかで判断する。前者は他スキル、後者は本スキル。

## データ配置の絶対原則（実データ禁止則）

**実在の人名・企業名・フィードバック原文・制作物抜粋は、環境変数
`GROWTH_DATA_DIR`（未設定時は `~/growth-data`）配下にのみ書く。**
このリポジトリ（`plugins/` 以下や設計書）には架空名以外を一切書かない。
会話中にユーザーが実名・実企業名を含めてきても、スキル本体のファイルに
転記しない（GROWTH_DATA_DIR 内のファイルへの記録は問題ない）。

`GROWTH_DATA_DIR` の展開:
- 環境変数 `GROWTH_DATA_DIR` が設定されていればそのパスを使う。
- 未設定なら `~/growth-data` を使う。
- どちらの場合も、実際に使ったパスを一度ユーザーに明示する。

## 前提セットアップ

外部依存なし。MCP・APIキー不要。`GROWTH_DATA_DIR` が存在しない状態で
モード1〜5のいずれかが発動した場合は、まずモード0（セットアップ）を
先に実行するかユーザーに確認してから進める。

## データ構造（GROWTH_DATA_DIR 配下）

```
$GROWTH_DATA_DIR/
├── profile.md                       # 所属・役割・業務内容・時間単価
├── companies/<会社slug>.md          # 所属先・クライアント別の企業情報
├── feedback/YYYY-MM-DD-<slug>.md    # フィードバック1件 = 1ファイル
├── artifacts/YYYY-MM-DD-<slug>.md   # 制作物1件 = 1記録ファイル（本体はコピーしない）
├── reports/YYYY-MM-DD-diagnosis.md  # 診断結果（モード2の出力。追記型・削除しない）
├── reports/YYYY-MM-DD-roi-<slug>.md # ROIレポート構成案（モード3の出力。追記型）
└── actions/ACTIONS.md               # 最新のアクションリスト（モード4が上書き更新）
```

**feedback ファイル**（frontmatter + 本文は発言の原文引用）:

```markdown
---
date: 2026-07-03
source: 上司M
task: 週次進捗レポート作成
axes: []                     # 診断（モード2）実行時に A1〜A7 を付与。記録時は空
---
「最初に結論を書いて。経緯から始まると何が言いたいか分からない」
```

**artifacts ファイル**（制作物本体はコピーせずパス参照＋抜粋）:

```markdown
---
date: 2026-07-02
title: 週次進捗レポート v2
type: 資料                   # 資料 / コード / メール / 議事録 の4値
location: <元ファイルのパスまたはURL>
related_feedback: [2026-07-03-weekly-report]
---
## 診断用抜粋（冒頭の構成のみ。クライアントコードは抜粋も禁止、location 参照のみ）
```

**profile.md** 必須項目: 氏名、所属、役割、主業務（箇条書き）、
時間単価（円/時。不明時は `3000（仮置き）`）、companies/ への一覧リンク。

**companies/<slug>.md** 必須項目: 会社名、自分との関係（所属 / クライアント の2値）、
事業内容3行以内、その会社で価値とされる語彙、担当案件一覧。

診断観点 A1〜A7 の判定基準は `references/diagnosis-axes.md` を参照する
（本ファイルには要約のみ置き、確定基準は参照ファイルを正とする）。
ROI計算式・レポート構成案は `references/roi-template.md` を参照する。

## 処理フロー（5モード）

### モード0: セットアップ

発動語:「成長戦略エンジンをセットアップして」

1. `GROWTH_DATA_DIR`（未設定なら `~/growth-data`）が存在するか確認する。
2. なければ、本スキルの `templates/growth-data-init/` を丸ごと
   `GROWTH_DATA_DIR` にコピーして作成する。
3. `profile.md` を開き、必須項目（氏名・所属・役割・主業務・時間単価）を
   ヒアリングして埋める。
4. サンプルファイル（feedback/artifacts のサンプル、companies/example-company.md）は
   「動作確認用の架空サンプルなので、実データを溜め始めたら削除してよい」と案内する。
5. 出力: 初期化済みディレクトリのパスと、作成したファイル一覧を報告する。

既に存在する場合は上書きせず、現状を報告して次に何をするか確認する。

### モード1: 記録

発動語:「フィードバックを記録して」「この制作物を記録して」

1. `GROWTH_DATA_DIR` の存在を確認する（なければモード0を先に案内）。
2. フィードバックなら `feedback/`、制作物なら `artifacts/` に、上記スキーマで
   1ファイル作成する。ヒアリングは1往復以内で完了させる（重くしない）。
3. 同一の `date + task`（feedback）や `date + title`（artifacts）のファイルが
   既にあれば、新規作成せず追記を提案する。
4. クライアントのコード・秘密資料が制作物の場合、抜粋を書かず `location` の
   パス参照のみ記録する。
5. voicememo-pipeline の議事録出力からフィードバックを転記する場合も、
   同じスキーマに整形してから1件ずつ記録する。
6. 出力: 追記・作成したファイルパスを報告する。

### モード2: ズレ診断

発動語:「ズレ診断して」「評価軸を分析して」

1. `feedback/` の最終更新日を確認し、14日以上更新がなければ「記録が
   途絶えている」と一言添える。
2. feedback が0件なら診断せず「feedback 3件以上の記録」を先に案内する。
   1〜2件でも実行はするが、レポート冒頭に件数不足の注記を入れる。
3. 前回診断以降の `feedback/`・`artifacts/` を対象にする（初回は全件）。
   各 feedback に A1〜A7 のうち該当する軸のタグを付け、frontmatter の
   `axes` を更新する。
4. `references/diagnosis-axes.md` の基準で各軸を0/1/2でスコアリングする。
   証拠（feedback引用 or artifacts抜粋）を必ず併記し、証拠がなければ
   スコアの代わりに「-（証拠不足）」と書く。
5. `references/diagnosis-axes.md` の優先度算出式で priority を出す。
6. `reports/YYYY-MM-DD-diagnosis.md` に7観点全行の診断表（軸 / 現場の期待 /
   現状の証拠 / スコア / priority / 修正ポイント1文）と、priority 上位2軸の
   「今週の修正ポイント」宣言を出力する。既存の reports/ ファイルは
   削除・上書きしない（追記型）。

### モード3: ROI可視化

発動語:「ROIレポートにして」「事業価値に翻訳して」

1. 対象の技術的成果（artifacts/ の1件、または口頭説明）を特定する。
2. `profile.md` の時間単価を取得する。仮置き（3000円/時）の場合はそのまま
   使い、レポートに要確認と明記する。
3. `references/roi-template.md` の計算式変数（削減時間・実施回数・単価）を
   ヒアリングで埋める。不明な変数は仮置き値を置き「前提と仮置き」欄に回す。
4. `references/roi-template.md` の6章構成で
   `reports/YYYY-MM-DD-roi-<slug>.md` を出力する。
5. コスト削減以外の効果（売上増・品質向上等）は「定性効果」欄に分離し、
   金額欄には混ぜない。
6. 清書（トーン調整・体裁）の要望が続く場合は document-creation スキルに
   切り替える。本スキルの出力は構成案までとする。

### モード4: アクション生成

発動語:「アクションリストを作って」

1. 最新の diagnosis レポートと roi レポート（あれば）を読む。
2. 診断の修正ポイント（priority上位2軸）・ROI提出物・再発している作業を
   候補化し、次の決定表で上から順にTierを判定する（最初に該当した行で確定）。

   | 順 | 条件 | 分類 |
   |---|---|---|
   | 1 | 診断 priority 上位2軸のズレを直すアクション | Tier S |
   | 2 | 同種作業が過去に2回以上発生、または月2回以上の発生見込みがあり、テンプレ化・自動化で再発工数を減らすアクション | Tier S（構造化・自動化） |
   | 3 | 上司・クライアントへの新規提案・分析・設計を伴うアクション | Tier A（戦略設計） |
   | 4 | 上記いずれにも該当しない | リストに載せない（口頭報告のみ） |

3. 既存 `actions/ACTIONS.md` に `doing` の行があれば保持したまま新規行を
   追加する。`done` の行は末尾の「## 完了済み」へ移してから上書きする。
4. スキーマ（ID・Tier・アクション文・根拠・期限・状態）で `ACTIONS.md` を
   上書き更新する。アクション文は「動詞＋対象＋完了条件」を1文に含める。
   完了条件のない行は書かない。ID は `S-NN` / `A-NN` 連番、状態は
   todo / doing / done の3値。
5. 出力後、「task-management スキルで TODO.md に転記できる」と一言だけ案内する
   （自動転記はしない）。

```markdown
# 業務改善・評価最大化アクションリスト（YYYY-MM-DD 診断より）

## 今週の修正ポイント（診断 priority 上位2軸）
- A1 結論ファースト（priority 6）
- A7 事業価値への接続（priority 4）

| ID | Tier | アクション（動詞＋対象＋完了条件） | 根拠 | 期限 | 状態 |
|---|---|---|---|---|---|
| S-01 | S | 週次レポートの結論ファーストテンプレを作り次回レポートで使用する | A1 | 2026-07-10 | todo |
| A-01 | A | 自動化スクリプトのROIレポート構成案を作成し上長に提出する | A7 / roi-2026-07-06 | 2026-07-13 | todo |
```

### モード5: クライアント提案モード

発動語:「クライアント向けに論理とROIで提案を組み立てて」

コンサル業務向上スキル（派生要求）の吸収先。モード2〜4との違いは対象
（自分の評価 → クライアントへの提案）のみで、テンプレは共用する。

1. 対象の `companies/<slug>.md` と、提案したい施策の内容を確認する。
2. 診断観点のうち **A1・A2・A3・A7** を「自分の成果物」ではなく
   「提案書ドラフト」に適用してセルフチェックする（証拠引用の原則は同じ）。
3. `references/roi-template.md` の計算式・6章構成案を、当該クライアントの
   価値語彙（companies/ に記載）で埋める。
4. 出力: 提案骨子（roi-template の構成案準拠）＋セルフチェック結果
   （A1/A2/A3/A7 の4行表）。

## 委譲ルール（まとめ）

| 相手先 | 委譲する内容 |
|---|---|
| document-creation | ROIレポート・提案骨子の清書（トーン調整・体裁） |
| work-approach-playbook | 単一タスクの着手前チェック・報連相・完了報告の型 |
| task-management | ACTIONS.md の項目を TODO.md へ転記する作業（一言案内のみ、自動化しない） |

## エッジケース

| ケース | 期待挙動 |
|---|---|
| `GROWTH_DATA_DIR` が存在しない状態でモード1〜5を発動 | モード0を先に実行するか確認してから進む |
| feedback が0件でモード2 | 診断せず「feedback 3件以上の記録」を先に案内する（1〜2件なら実行するが件数不足の注記を入れる） |
| 証拠がない軸がある | スコアを付けず「-（証拠不足）」とし、次回までに集める証拠の種類を修正ポイント欄に書く |
| 制作物がクライアントのコード・秘密資料 | artifacts に抜粋を書かない。location 参照のみ記録し、診断はフィードバック引用だけで行う |
| 同一フィードバックの重複記録 | date + task が同一のファイルが既にあれば追記提案し、新規ファイルを作らない |
| 時間単価が未設定でモード3 | 3,000円/時で仮置きし、「前提と仮置き」に要確認として明記 |
| ACTIONS.md に doing の行が残った状態でモード4 | doing 行は保持したまま新規行を追加（上書きで消さない） |
| 実名・企業名をスキルファイルに書きそうになる | 書かない。実データは GROWTH_DATA_DIR のみに記録する |

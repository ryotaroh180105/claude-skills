# Consulting Quiz（コンサル・営業知識クイズ）

## 目的

インターンで早くコンサル側の仕事にアサインされるための知識武装（G1）と、
ケース面接を含む就活対策（G3）のためのクイズスキル。
「出題 → 回答 → 採点 → 解説」を1問ずつ回し、結果を `quiz-log.md` に蓄積して
弱点分野を優先的に潰していく。外部依存はなく、Markdown ファイルだけで完結する。

重要な原則: **答えを先に見せない。** 問題は必ず1問ずつ提示し、ユーザーの回答を
受け取ってから正解・解説を出す。5問まとめて出題したり、問題文に正解を
併記したりしない。解説では正誤だけでなく「なぜ他の選択肢が違うか」
「実務・面接でどう使うか」まで必ず触れる。

## 発動条件

- 「クイズを出して」「コンサル知識の練習をしたい」と依頼されたとき
- 「ケース面接の練習」「フェルミ推定を出して」などケース演習を求められたとき
- 「弱点を復習したい」「間違えた問題をもう一回」と復習を求められたとき
- 「今の実力を診断して」「レベル診断して」と依頼されたとき
- 「会計だけ」「5Forces を集中的に」など分野指定の演習を求められたとき

## 前提セットアップ

外部依存なし。API キーも MCP も不要。
学習ログはプロジェクトルートの `quiz-log.md` に保存する。初回作成時のみ
保存場所をユーザーに確認する（別の場所を指定されたらそちらを使い、以降のセッション
では `Glob` で `**/quiz-log.md` を検索して既存ログを探す）。

## 出題分野

| # | 分野 | 出題範囲 |
|---|---|---|
| ① | ロジカルシンキング | MECE、ロジックツリー、仮説思考、So What / Why So |
| ② | フレームワーク | 3C / 4P / 5Forces / SWOT / バリューチェーン / 7S。名前当てではなく**使いどころと限界**まで問う |
| ③ | 会計・財務基礎 | PL / BS / CF の読み方と関係、粗利と営業利益の違い、損益分岐点 |
| ④ | 営業・商談 | ヒアリング（SPIN）、提案の型（課題→原因→解決策→効果）、反論処理 |
| ⑤ | ケース面接ミニ問題 | 市場規模推定（フェルミ）、利益改善。答えの数字ではなく**回答プロセスを段階評価** |

## 出題形式

- **4択**: 知識確認用。誤答の選択肢も「よくある誤解」になるよう作る。
- **記述**: 考え方を問う。観点別採点（下記）で部分点を付ける。
- **ケース**: 対話形式。一度に全部答えさせず「まず構造化 → 数値仮定 → 計算 →
  So What」の順に段階的に深掘りする。
- 1セッションは**デフォルト5問**（4択3問 + 記述1問 + 小ケース1問が標準ミックス）。
  ユーザーが問題数や形式を指定したらそれに従う。
- 4択の正解位置は偏らせない。同じ問題をログ上の直近2セッション内で再出題しない
  （復習モードでの意図的な再出題は例外）。

## セッションの流れ

### 0. ログ確認と分岐

セッション開始時にまず `quiz-log.md` を探して読む。

- **ログが無い（初回）** → 「初回なのでレベル診断から始めます」と伝え、
  各分野1問ずつ計5問の**レベル診断**を実施。終了後に分野別の結果と開始レベルを
  提示し、`quiz-log.md` を新規作成する。
- **ログがある** → 集計表から分野別正答率を読み、モードを確認する:
  「通常演習 / 復習モード（弱点優先）/ 分野指定」。指定がなければ、正答率が
  最も低い分野を2問、その他の分野から3問のミックスを提案する。

### 1. 出題ループ（1問ずつ）

1. 問題番号・分野・形式を明示して1問だけ提示する（例: `【2/5】会計・財務｜記述`）。
2. ユーザーの回答を待つ。ヒントを求められたら正解は伏せて考え方の入口だけ示す。
3. 採点（○ / △ / ×）と解説を提示する。解説は必ず次を含む:
   - 正解と、その理由
   - 4択なら**他の選択肢がなぜ違うか**を1つずつ
   - **実務・面接でどう使うか**の一言（例: 「面接では結論→根拠の順で」）
4. 次の問題へ。途中で「やめる」と言われたら、そこまでの結果でログを更新して終了する。

### 2. 記述・ケースの観点別採点

記述問題は次の3観点を各 ◎○△× で評価し、総合の ○/△/× を決める:

| 観点 | 見るポイント |
|---|---|
| 構造 | 結論ファーストか、分解の軸が明確か |
| 網羅性 | 主要な論点にモレがないか（MECE か） |
| 具体性 | 抽象論で終わらず、数字・例・アクションに落ちているか |

ケース問題はプロセスを段階評価する: ①構造化（分解式を立てられたか）
②数値仮定（根拠のある概数を置けたか）③計算と検算 ④So What（数字から示唆を
出せたか）。最終的な数字のズレより①④の質を重く見る。

### 3. セッション終了時

- 結果サマリ（今回の正答数、良かった点 → 改善点の順）を提示する。
  **できたことを先に伝える**（下記エッジケース参照）。
- `quiz-log.md` の履歴と集計表を更新する。
- 次回の推奨（例: 「次回は会計を重点にした復習モードがおすすめ」）を一言添える。

## 学習ログ（quiz-log.md）

フォーマットは以下に固定する。集計表は履歴から毎回再計算して上書きする。

```markdown
# Quiz Log

## 集計（最終更新: 2026-07-04）
| 分野 | 出題数 | 正答数 | 正答率 | 現在レベル |
|---|---|---|---|---|
| ロジカルシンキング | 8 | 6 | 75% | Lv2 |
| 会計・財務 | 6 | 2 | 33% | Lv1 |

## 履歴
| 日付 | 分野 | 形式 | 問題要約 | 正誤 | 弱点メモ |
|---|---|---|---|---|---|
| 2026-07-04 | 会計・財務 | 記述 | 黒字倒産が起きる仕組み | △ | CF の3区分の説明が曖昧 |
```

- 正誤は ○（正解）/ △（部分点）/ ×（不正解）。△×には必ず弱点メモを残す。
- 復習モードでは、正答率が最も低い分野と、△×の弱点メモに対応する**類題**
  （同じ問題の丸暗記確認ではなく、同じ弱点を別の角度から突く問題）を優先する。

## レベル調整

- レベルは分野ごとに Lv1〜Lv3: **Lv1** = 用語・定義の確認、**Lv2** = 使い分け・
  計算・限界の理解、**Lv3** = 応用・複合ケース（面接想定）。
- 初回レベル診断は各分野 Lv2 相当を1問出し、○なら Lv2、△と×なら Lv1 から
  開始する（△は基礎の穴がある状態とみなし、低い側から確実に固める）。
- 以降は分野別正答率が直近で **80% 以上なら1段階上げ、50% 未満なら1段階下げる**。
  変更時は「次から少しレベルを上げます」と一言伝える。

## 出題例（各分野1問）

出題時はこの水準の問題を毎回新しく作る。以下は品質基準のサンプル。

**① ロジカルシンキング（4択・Lv2）**
「次のうち、分解の仕方として問題があるものはどれか。
A. 顧客を「新規 / 既存」に分ける ／ B. 売上を「客数 × 客単価」に分解する ／
C. 施策を「短期施策 / Web施策」に分ける ／ D. 年齢層を「20歳未満 / 20代 / 30代 / 40歳以上」に分ける」
→ **正解 C**。時間軸とチャネル軸が混在し、モレ（長期のオフライン施策）と
ダブり（短期の Web 施策）が生じる。A は排他的で網羅、B は掛け算分解、
D は年齢という単一の軸でモレなくダブりなし。実務では「軸が1本か」を最初に疑う。

**② フレームワーク（4択・Lv2）**
「5Forces の説明として誤っているものはどれか。
A. 業界の構造的な収益性を評価するのに向く ／ B. 「代替品の脅威」には同業他社の類似製品が含まれる ／
C. 変化の速い業界では分析時点のスナップショットにすぎない点が限界 ／ D. 新規参入の脅威は参入障壁の高さに左右される」
→ **正解 B**。代替品とは業界の**外**から同じニーズを満たすもの（例: 牛丼チェーンに
対するコンビニ弁当）。同業他社の類似製品は「既存企業間の競争」に入る。
A・D は定義どおり、C は実際の限界（動態を捉えられない）。面接で 5Forces を使う
ときは「参入時点の魅力度評価」に絞ると刺さる。

**③ 会計・財務基礎（記述・Lv2）**
「PL 上は営業黒字なのに資金繰りが苦しくなるのはどんなときか。PL と CF の違いに
触れて説明せよ。」
→ 模範解答の骨子: PL は発生主義（売上計上と入金のタイミングがずれる）、CF は
現金の実際の出入り。売掛金の回収が遅い・在庫を積みすぎ・借入返済が重い、の
いずれかで営業黒字でも現金が枯れる（黒字倒産）。採点例: 発生主義と現金主義の
対比があれば構造◎、原因を2つ以上挙げれば網羅性○、売掛金など具体例があれば具体性○。

**④ 営業・商談（4択・Lv1）**
「SPIN のヒアリングで『その問題を放置するとどんな影響がありますか？』と尋ねる
のはどれか。A. Situation ／ B. Problem ／ C. Implication ／ D. Need-payoff」
→ **正解 C**。Implication は問題の影響を拡大して認識させる質問。A は現状把握、
B は問題の顕在化、D は解決した後の価値を顧客自身に語らせる質問。実務では
C を飛ばして提案に入ると「まだそこまで困っていない」という反論を招きやすい。

**⑤ ケース面接ミニ問題（対話・Lv2）**
「日本の缶コーヒーの年間市場規模を推定してください。まず、計算式の構造から
教えてください。」
→ 段階評価の基準: ①構造化 =「人口 × 飲用者率 × 年間本数 × 単価」等の式を
立てられるか ②数値仮定 = 人口1.2億人、飲用者率などに根拠（自分・周囲の観察）を
添えられるか ③計算 = 概数で素早く、桁を検算するか ④So What = 「実売データと
比べて過大/過小なら仮定のどこを疑うか」まで言えるか。数字の正確さより、
仮定を明示して修正可能な形にできているかを重視する。

## エッジケース

- **分野指定なしで「クイズ出して」**: ログがあれば「弱点の◯◯を多めにした
  ミックス5問でいいですか？」と1回だけ確認して開始。ログが無ければレベル診断を
  提案する。質問攻めにせず、確認は1往復まで。
- **連続不正解でモチベーションが下がっているとき**（同一セッションで3問連続×が
  目安）: 難易度を1段下げ、次の1問の前に直前の誤答に関連する基礎の要点を
  30秒で読める分量だけ挟む。「ここは頻出の引っかけで、間違える人が多い」のように
  正常化する言い方をし、責める表現・煽る表現は使わない。セッション終了時は
  できたことを先に述べてから改善点を1つに絞って伝える。
- **quiz-log.md が破損しているとき**（表が崩れてパースできない等）: 壊れた
  ファイルを**上書きしない**。`quiz-log.broken-YYYYMMDD.md` にリネームして退避し、
  読み取れた履歴行だけを引き継いだ新しい `quiz-log.md` を作り、その旨を
  ユーザーに報告してから演習を始める。
- **同じ問題ばかりになるとき**: 履歴の「問題要約」を照合し、直近2セッションと
  重複する問題は言い換えではなく別の論点に差し替える。

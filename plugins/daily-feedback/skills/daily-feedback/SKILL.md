# daily-feedback — Claude 使い方デイリーフィードバック

当日の Claude Code トランスクリプトを集計・分析し、翌日から使える改善アクション付きの
フィードバックレポートを作る。目的は**プロンプティング力向上・コスト最適化・
運用場面の判断力向上**の3つ。

## 前提セットアップ

| 種別 | 名前 | 用途 | 未設定時の挙動 |
|---|---|---|---|
| ローカルデータ | `~/.claude/projects/**/*.jsonl` | 当日の会話・トークン集計 | 「Claude Code を使っている実機で実行して」と案内して停止 |

外部サービス依存なし。リモートセッション（Claude Code on the web 等）では実機の
トランスクリプトが見えないため、その場合はユーザーに実機での実行を案内する。

## ワークフロー

### 1. データ収集（生 JSONL を直接読まない）

この SKILL.md と同じディレクトリの `scripts/collect_stats.py` を実行する:

```bash
python3 <このスキルのディレクトリ>/scripts/collect_stats.py            # 今日
python3 <このスキルのディレクトリ>/scripts/collect_stats.py 2026-07-04  # 日付指定
```

出力 JSON: セッション数・プロジェクト別ターン数・モデル別トークン/キャッシュヒット率・
概算コスト(USD)・ツール使用回数・compaction 回数・ユーザー中断回数・
ユーザープロンプト一覧（各200字、最大100件。超過分は `prompts_dropped` に件数）。

- **トランスクリプト JSONL を `cat`/Read で直接コンテキストに読み込まない**
  （巨大でコストが逆転する）。深掘りが必要な場合のみ `grep` で該当箇所だけ抜く。
- `prompt_count` が 0 なら「本日は分析対象の利用なし」と報告して終了する。
- `error` キーが返ったら、その内容をユーザーに伝えて停止する。

### 2. 3軸の分析

JSON の統計とプロンプト一覧を読み、各軸を **5点満点 + 根拠** で評価する。
根拠には**実際のプロンプトを引用**する（引用なしの一般論は書かない）。

**① プロンプティング力** — 見るもの: プロンプト一覧、ユーザー中断回数

| チェック | 悪いシグナル |
|---|---|
| 依頼の具体性 | 「いい感じにして」等、成果物・制約・完了条件がない依頼 |
| コンテキスト提供 | ファイルパス・エラー全文・期待動作を最初に渡さず後出しした往復 |
| 手戻り | 「違う」「そうじゃなくて」等の訂正、`user_interruptions` の多さ |
| 1メッセージ1目的 | 複数の無関係な依頼を1プロンプトに詰めて迷走した形跡 |

良かったプロンプト1〜2件と、悪かったプロンプト1〜2件を引用し、悪い方には
**書き直し例（Before → After）**を付ける。

**② コスト最適化** — 見るもの: `models`、`estimated_cost_usd`、`compactions`

| チェック | 判断基準 |
|---|---|
| モデル×タスク適合 | プロンプト内容から推定したタスク種別と使用モデルを `model-switcher` スキルの分類表で照合。定型処理を上位モデルでやっていたら指摘 |
| キャッシュヒット率 | `cache_hit_pct` が低い（<50%）× ターン数が多い場合、セッションの切り方・モデル往復を疑う |
| compaction | 多い（3回超）なら 1 セッション詰め込みすぎ。タスクごとに `/clear` を提案 |
| 出力トークン | output が突出していたら、冗長な出力をさせている（token-saver 適用漏れ）可能性 |

概算コストは「約 $X.XX（スクリプトの概算。正確な請求額ではない）」と必ず断りを付ける。

**③ 運用場面の判断力** — 見るもの: `tools`、`projects`、プロンプト一覧

| チェック | 悪いシグナル |
|---|---|
| スキル活用 | 既存スキルの守備範囲の依頼を素の指示でやっていた（Skill/発動記録がない） |
| サブエージェント委譲 | 大量・定型作業をメインセッションで直列実行（Agent tool 未使用） |
| 計画してから実装 | 大きい変更を Plan mode / 設計壁打ちなしでいきなり実装して手戻り |
| 自動化機会 | 毎日・毎回やっている同型の依頼（→ スキル化・Routine 化を提案） |

### 3. レポート出力

以下の形式でチャットに出力し、同じ内容を `~/.claude/feedback/YYYY-MM-DD.md` に保存する
（ディレクトリがなければ `mkdir -p` で作る）:

```markdown
# Claude 使い方フィードバック YYYY-MM-DD

## サマリー
- セッション X 件 / プロンプト X 件 / 概算コスト $X.XX（概算）
- 総評 1〜2 行

## スコア
| 軸 | 点 | 根拠（1行） |
|---|---|---|
| プロンプティング力 | X/5 | … |
| コスト最適化 | X/5 | … |
| 運用判断力 | X/5 | … |

## 良かった点（実例引用）
## 改善点（実例引用 + Before → After）
## 明日のアクション（最大3つ、具体的に）
```

- アクションは「気をつける」ではなく実行可能な形で書く
  （例:「データ整形は `model: haiku` のサブエージェントに出す」）。
- 前日のレポートが `~/.claude/feedback/` にあれば、前回アクションの実行有無を
  冒頭で 1 行ずつ確認する（できていれば ✅、できていなければ翌日に繰り越し）。

## 毎日自動で実行する（任意）

ユーザーが「毎日自動で」と言ったら、OS のスケジューラでヘッドレス実行を設定する。
例（毎日 22:00、cron）:

```bash
0 22 * * * claude -p "/daily-feedback で今日のフィードバックレポートを作成し ~/.claude/feedback/ に保存して" --allowedTools "Bash,Read,Write,Glob,Grep"
```

Windows はタスクスケジューラで同コマンドを登録する。設定・troubleshootは
`update-config` / `loop-engineering` スキルの管轄に委ねる。

## エッジケース

- **当日データなし**: 「本日の利用記録なし」と報告して終了（レポートは作らない）。
- **`~/.claude/projects` がない**（リモート/claude.ai）: 実機での実行を案内して停止。
- **プロンプト100件超**: スクリプトが先頭100件に切る。`prompts_dropped` を
  レポートのサマリーに明記し、全量が必要ならユーザーに日付・プロジェクトを絞ってもらう。
- **スコアの水増し禁止**: 根拠となる実例を引用できない軸は「データ不足で評価不能」と書く。

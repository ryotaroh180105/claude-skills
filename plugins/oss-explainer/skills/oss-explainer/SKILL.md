# oss-explainer — OSS読解 → 解説骨子抽出 → 事実裏取り

GitHub でバズっている OSS（または Ryo 指定のリポジトリ）を実際に読み解き、
「何が新しいか／なぜバズったか／どう動くか／自分の仕事にどう活かすか」の
4軸 + 事実台帳からなる **explainer-brief** を抽出し、article-writer に
記事化を委譲するスキル。目的は副業の発信・実績づくり（G2/G3）。

## 大原則（最重要）

- **このスキルの出口は Step 5（explainer-brief を article-writer に渡す）まで。**
  note 本文の執筆・タイトル生成・推敲・ハッシュタグ・公開設定は一切行わない。
- **断定の禁則**: 事実台帳で「確認済み」でない数値・ライセンス・技術主張を、
  brief にも article-writer への申し送りにも断定として書かない。
- **対象は本スキルが勝手に選ばない**: 候補が複数あるときは Ryo に1本選ばせる。
- **Claude 自身の WebSearch は使わない**（CLAUDE.md 方針）。裏取りは
  hermes-relay（notebooklm エンジン）または WebFetch の個別ファイル取得のみ。

## やらないこと（委譲先）

| やらないこと | 委譲先 |
|---|---|
| note 本文の執筆・タイトル案・推敲・文体メモ運用 | article-writer |
| ハッシュタグ・公開設定（無料/有料）・導線提案 | article-writer（工程6） |
| SEO キーワード設計・検索流入狙いの構成 | owned-media |
| OSS トレンドの定期収集・候補リストへの追記 | github-trends |

（リポジトリの clone 自動化・依存インストール・ローカル実行・ビルド、note への自動投稿、
複数 OSS の一括記事化は本スキルでは行わない。読解は静的閲覧で足りる前提。）

## 処理フロー

### Step 0 — 対象確定

| 入力 | 扱い |
|---|---|
| Ryo が repo URL / owner/repo を明示 | その1本を対象確定 |
| github-trends の候補リスト（ROADMAP 表 or チャット）を渡された | 候補を提示し Ryo に1本選ばせる（勝手に選ばない） |
| 「最近バズってるOSSを解説して」（対象未指定） | github-trends を先に呼ぶよう案内するか、Ryo に候補を1つ確認する。本スキルはトレンド収集をしない |

### Step 1 — 読解可能性の確保（add 判断）

対象リポジトリがカレントセッションに無くても、読むだけなら GitHub MCP
（`mcp__github__get_file_contents` 等）または WebFetch（github.com のファイル
ビュー / raw.githubusercontent.com）で足りる。**セッションへの `add_repo` は
原則しない。**

`add_repo` を行うのは、Ryo が「このリポジトリをセッションに入れて中を歩いて
解説して」等と **明示的に add を頼んだ場合のみ**。その場合は
`add_repo` → クローン完了後に `register_repo_root` の順で進める。
本スキルが自律的に add することはない。

### Step 2 — 読解

README → アーキテクチャ/docs → 主要ソース（エントリポイント・コア module）
→ LICENSE の順に読む。GitHub MCP を優先し、無ければ WebFetch。
読んだファイル/URL を全て控える（brief の「読んだ根拠」に入れる）。

リポジトリが巨大でソース全読不可な場合は、エントリポイント + コア module +
README/docs に絞り、読んだ範囲を brief に明示する。未読部分由来の断定はしない。

### Step 3 — brief 抽出

下記スキーマで4軸 + 事実台帳を埋める。ライセンス・スター数・「業界初」等の
技術的主張など断定に根拠が要る項目は、事実台帳に「未確認」で登録する。

### Step 4 — 事実裏取り

事実台帳の「未確認」項目を、種別に応じて経路を振り分けて裏取りする。

| 項目の種別 | 裏取り手段 |
|---|---|
| 一次情報（ライセンス・スター数・直近リリース等 GitHub 上で確定できるもの） | WebFetch で当該ページを直接取得 |
| 二次評価（技術的主張の妥当性・比較・「なぜバズったか」の外部評価） | hermes-relay（`engine: notebooklm` + `topic:`）に1本 enqueue。手順は hermes-x-search の SKILL.md が正 |

裏取り結果で台帳の状態を「確認済み/未確認」に更新する。裏取りできなかった
項目は「未確認」のまま brief の「未確認・断定できない点」に転記する
（止めずに進める。ただし記事で断定しないよう申し送る）。

### Step 5 — article-writer へ委譲

brief が埋まったら、下記定型プロンプトに explainer-brief 全文を貼付して
article-writer を呼ぶ。**本スキルの出口はここまで。**

```
article-writer スキルで note 解説記事を作成してください。ネタと骨子は
以下の explainer-brief で確定済みです。切り口設計（工程1）はこの brief の
4軸を素材にし、想定読者は「中級IT理解者（GitHubは使うがこのOSSは未知）」
で固定。以降、タイトル案（工程2）・構成・執筆・推敲・公開設定・ハッシュタグ
（工程6）は article-writer の標準手順どおりに進めてください。

制約:
- 「未確認・断定できない点」セクションの項目は記事で事実として断定しない
  （体験・伝聞・「〜とされる」表現に落とすか、書かない）。
- 事実台帳で「確認済み」の数値・ライセンスのみ本文に載せる。
- 文体メモは article-writer の分岐に従う。

<explainer-brief 全文を貼付>
```

### Step 6 — 引き継ぎ後

記事本文・タイトル・推敲の品質は article-writer が担保する。本スキルは
記事本文を自前で書かない。

## explainer-brief（解説骨子・確定スキーマ）

読解完了後にチャット出力する。ファイルとして新規に作らない
（Ryo が保存を望む場合のみ、記事管理ディレクトリに置く）。

```markdown
# explainer-brief: <owner/repo>

## 対象メタ（要裏取り）
- リポジトリ: <owner/repo>（URL）
- スター数: <N>（取得日 YYYY-MM-DD / 裏取り: 確認済み|未確認）
- ライセンス: <SPDX識別子>（裏取り: 確認済み|未確認）
- 主要言語 / 直近リリース: <lang> / <vX.Y.Z, 日付>

## 4軸の骨子
1. 何が新しいか: <1-3行。既存手段との差分>
2. なぜバズったか: <1-3行。話題化の理由。要裏取り項目は印>
3. どう動くか: <3-6行。アーキテクチャ・主要コンポーネント・データフロー>
4. 自分の仕事にどう活かすか: <1-3行。G1/G2/G3 のどれにどう効くか>

## 読んだ根拠（ファイル/URL）
- <README / docs/xxx / src/yyy のパス or URL を列挙。読んだ範囲を明示>

## 事実台帳（断定に根拠が要る項目）
| 主張 | 種別(license/stars/技術主張) | 裏取り手段 | 状態(確認済み/未確認) | 根拠URL |
|---|---|---|---|---|

## 未確認・断定できない点
- <裏取りできなかった/しなかった項目。記事で断定しないよう article-writer に申し送る>
```

## エッジケース

| ケース | 期待挙動 |
|---|---|
| 対象OSS未指定 | github-trends に振るか Ryo に1本確認。トレンド収集を本スキルでやらない |
| リポジトリが巨大でソース全読不可 | エントリポイント + コア module + README/docs に絞る。読んだ範囲を brief に明示し、未読部分由来の断定をしない |
| README がマーケ寄りで技術実体が薄い | ソースと Issue/PR から実体を補う。それでも不明な点は事実台帳「未確認」に落とす |
| ライセンスが記事化・引用に制約（コード転載の可否） | LICENSE を確認し、コード引用は必要最小限。ライセンス種別を brief に記載し、article-writer に申し送る |
| hermes-relay watcher がダウン/タイムアウト | hermes-x-search の手動フォールバックを Ryo に案内。裏取りできない項目は「未確認」のまま進め、記事で断定しない（止めない） |
| GitHub MCP も WebFetch も対象取得に失敗 | 1回再試行 → ダメなら「読解不能」と報告し記事化に進まない（浅い受け売り記事を作らない） |
| Ryo が指定したリポジトリが private / 存在しない | 取得失敗として報告。add が必要なら上記 Step 1 の add 判断フローに従う。憶測で内容を書かない |
| 「なぜバズったか」の根拠が取れない | 断定せず「話題の理由は諸説あり」等に留め、未確認セクションに記載 |
| 「この記事を推敲して」等、執筆・推敲だけの依頼 | 本スキルは発動しない。article-writer に直接渡す |

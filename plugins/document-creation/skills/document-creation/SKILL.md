# ビジネス書類作成（document-creation）

## 目的

インターン業務で発生する書類（議事録・提案書・報告書/週報・社外メール/依頼文）を、
毎回ゼロから考えずに**型（テンプレート＋ヒアリング項目）で素早く一定品質以上**に仕上げる。

関連スキルとの役割分担:
- タスクの完了報告・中間報告・振り返りの型 → **work-approach-playbook** を使う（本スキルでは扱わない）
- ピラミッド構造・MECE などの思考フレームの詳細 → **requirements-definition** を参照
- 録音からの文字起こし〜議事録の自動生成 → **voicememo-pipeline**（本スキルの議事録テンプレートは同スキルの出力と互換。清書・加筆はこちらで行う）

## 発動条件

- 議事録・提案書・報告書・週報・依頼文・ビジネスメールの作成を頼まれたとき
- 走り書きメモ・箇条書き・文字起こしを「ちゃんとした書類にして」と頼まれたとき
- 既存の文章の**トーン調整だけ**を頼まれたとき（「社外向けに直して」等）
- 書き上がった書類のレビュー・推敲を頼まれたとき

## 前提セットアップ

外部依存なし。MCP・APIキー・環境変数は不要。

| 依存 | 必須? | 未設定時の挙動 |
|---|---|---|
| Google Drive MCP（`mcp__Google_Drive__create_file`） | 任意 | Drive 保存をスキップし、ローカルファイル or チャット出力のみ |

## ワークフロー

### ステップ1: 種別特定とヒアリング

まず書類の種別（議事録/提案書/報告書・週報/メール・依頼文）を特定し、次の3点を確認する。

1. **読み手は誰か**（社内の上司 / チーム / 社外クライアント）→ トーン段階が決まる
2. **読み手に何をしてほしいか**（承認 / 判断 / 作業 / 把握のみ）→ 結論に書く内容が決まる
3. **手元にある素材**（メモ・文字起こし・前回資料）→ 不足項目のヒアリングリストが決まる

種別ごとの追加ヒアリング項目は後述のテンプレート冒頭に記載。**素材から自力で埋め、
埋まらない項目だけまとめて質問する**（1項目ずつ聞き返さない）。

### ステップ2: テンプレートで下書き

該当種別のテンプレートに流し込む。共通原則:

- **結論ファースト**: 読み手が最初の30秒で「何が決まった/何をしてほしい」が分かる位置に結論を置く。構造化の詳細（ピラミッド構造）は requirements-definition スキル参照。
- **読み手の意思決定に必要な情報から書く**: 自分がやった順ではなく、判断に効く順。
- **1文を短く**: 目安60文字以内。「〜ですが、〜で、〜なので」と繋がったら分割する。
- **事実と意見を分ける**: 「実績: 3件完了（事実）」「所感: ペースは想定通り（意見）」のように明示的にラベルを分ける。議事録では「決定事項」と「議論の要点」を混ぜない。

### ステップ3: トーン調整（3段階）

| 段階 | 用途 | 特徴 | 例（リスケの連絡） |
|---|---|---|---|
| 社内カジュアル | チームチャット・日次連絡 | です・ます最小限、絵文字可、要点のみ | 「すみません、明日のMTG 15時に変更できますか？◯◯の対応が長引いてます」 |
| 社内フォーマル | 上司への報告書・稟議 | です・ます統一、見出し・箇条書きで構造化 | 「明日の定例について、◯◯対応のため15時への変更をお願いできますでしょうか。」 |
| 社外 | クライアント向け全般 | クッション言葉、頭語・結語、自社都合の理由は簡潔に | 「大変恐縮ですが、諸事情により明日のお打ち合わせを15時に変更させていただけますと幸いです。ご調整いただきありがとうございます。」 |

トーン調整**だけ**の依頼の場合は、ステップ1のヒアリングは「読み手」と「目的」の2点確認に
とどめ、原文の内容（事実関係・数値）を勝手に増減しない。変更点は箇条書きで添える。

### ステップ4: 出力と保存

- 既定はチャット出力＋必要に応じローカル Markdown 保存。
- **Google Drive 保存（任意）**: Google Drive MCP 接続時のみ、ユーザーが希望すれば `mcp__Google_Drive__create_file` で保存する。未接続なら「ローカルに保存済み。Drive 保存には Google Drive MCP の接続が必要」と伝えるだけでよい（接続を強制しない）。
- 保存前に後述の「機密の扱い」を確認する。

## 書類種別テンプレート

### ① 議事録

追加ヒアリング: 会議名 / 日時 / 参加者（社名・役割） / 次回予定。
voicememo-pipeline の出力と互換のテンプレート。埋められない項目は「不明（要確認）」と書き、**創作しない**。

```markdown
# 議事録: <会議名>
- 日時: YYYY-MM-DD HH:MM〜HH:MM
- 参加者: <名前（役割）>

## アジェンダ
1. ...

## 議論の要点
- ...

## 決定事項
- ...

## TODO
| # | タスク | 担当 | 期限 |
|---|---|---|---|
| 1 | ... | ... | YYYY-MM-DD / 未定 |

## 次回
- YYYY-MM-DD HH:MM / アジェンダ: ...
```

清書時の注意: 発言の時系列ではなく議題ごとに再構成する。「誰が言ったか」が重要な発言
（合意・反対・宿題の引き受け）のみ発言者名を残す。TODO の担当・期限が素材にないものは
「未定（要確認）」とし、確認すべき点として書類末尾にまとめる。

### ② 提案書

追加ヒアリング: 提案先（意思決定者は誰か） / 解決したい課題 / 予算・期間の制約 / 競合案の有無 / 納品形式（Markdown ドキュメントか、スライド用の構成案か）。
**1枚サマリー＋詳細の2部構成**。忙しい意思決定者はサマリーだけで判断できること。

```markdown
# <提案タイトル>（1枚サマリー）
- 課題: <現状と問題点を1〜2文で>
- 提案: <何をするか1文で>
- 効果: <定量できるものは数値で>
- コスト: <金額・工数>
- スケジュール: <開始〜完了の目安>
- 次のアクション: <承認後、誰が何をするか>

---
# 詳細
## 1. 背景と課題    ← なぜ今やるべきか。現状の事実→問題→放置した場合の影響
## 2. 提案内容      ← 具体的な施策。複数案あるなら比較表（推奨案を明示）
## 3. 期待効果      ← 効果の根拠。前提条件も書く
## 4. コスト        ← 初期・運用に分ける。工数は誰の時間かまで
## 5. スケジュール  ← マイルストーン表
## 6. 次のアクション ← 意思決定者にしてほしいこと（承認/選択/日程確保）
```

### ③ 報告書・週報

追加ヒアリング: 報告先 / 対象期間 / 今週の主要タスク（task-management の TODO.md があれば流用）。
結論ファースト: 冒頭1〜2行で「順調か/問題があるか」を宣言する。

```markdown
# 週次報告: YYYY-MM-DD 週（<名前>）
**サマリー**: <順調/遅延あり/相談あり を先頭に。例: 遅延あり — ◯◯が2日遅れ、リカバリ案は相談事項1>

## 実績（事実）
- <完了したこと。数値・成果物リンク付きで>

## 課題（事実と所感を分ける）
- 事実: <起きたこと> / 所感: <自分の解釈・仮説>

## 来週の予定
- <タスクと完了目標日>

## 相談事項
1. <Yes/No か選択肢で答えられる形にする。なければ「なし」と明記>
```

### ④ 社外メール・依頼文

追加ヒアリング: 宛先（社名・役職・面識の有無） / 依頼内容と理由 / 希望期限 / 断られた場合の代替案。

- **件名**: 「【依頼】◯◯資料のご共有のお願い（△△社・<名前>）」のように、用件＋自分の所属を件名だけで分かる形に。「お世話になっております」等を件名にしない。
- **クッション言葉**: 依頼=「お忙しいところ恐れ入りますが」、催促=「行き違いでしたら失礼いたします」、お詫び=「このたびは〜につきまして、申し訳ございませんでした」（言い訳より先に謝意）。
- **依頼の明確化**: 「何を・いつまでに・どの形式で」を本文中に箇条書きで独立させる。文章に埋め込まない。
- **期限の書き方**: 「なるべく早く」ではなく「MM月DD日（曜）中」。理由を添える（「DD日の社内会議で使用するため」）と応じてもらいやすい。

```markdown
件名: 【依頼】<用件>（<自社名>・<名前>）

<宛先社名> <部署> <名前>様

お世話になっております。<自社名>の<名前>です。
<結論: 何のための連絡か1〜2文>

つきましては、以下についてご対応をお願いできますでしょうか。
- 依頼内容: <何を>
- 期限: MM月DD日（曜）中（<理由>のため）
- 形式: <ファイル形式・共有方法>

お忙しいところ恐れ入りますが、ご確認のほどよろしくお願いいたします。

<署名>
```

## エッジケースの扱い

| 状況 | 挙動 |
|---|---|
| 素材が断片的（メモ数行だけ等） | テンプレートの埋まる部分だけ埋めた**骨子案**を先に提示し、空欄を「不明（要確認）」として質問リストを添える。不足情報を推測で創作しない |
| 宛先・目的が不明 | 執筆前にステップ1の「読み手」「してほしいこと」の2点を必ず確認する。どうしても不明のまま急ぐ場合は社内フォーマルで仮作成し、宛先確定後にトーンを再調整すると明示する |
| 実名・金額・取引条件など機密を含む | チャット外部（Drive 以外の外部サービス・SNS・メール送信ツール等）への送信をしない。サンプルとして流用・共有したい場合は「◯◯社→A社、金額→X円」のダミー化を提案する。Drive 保存時も保存先フォルダの共有範囲をユーザーに確認する |
| メールの送信自体を頼まれた | 本スキルは**下書きまで**。送信はユーザーが自分のメーラーで行う（誤送信・宛先ミスのリスクを負わない） |
| 「完了報告を書きたい」 | 本スキルではなく work-approach-playbook の完了報告フォーマットを案内する |

## 完成前のセルフチェック

- [ ] 結論（決定事項/依頼内容/サマリー）が冒頭30秒で読める位置にあるか
- [ ] 読み手のトーン段階（カジュアル/フォーマル/社外）に合っているか
- [ ] 事実と意見が分離されているか。推測で埋めた箇所が「要確認」と明示されているか
- [ ] 日付・数値・固有名詞（特に宛先の社名・氏名の表記）に誤りがないか
- [ ] 依頼・TODO に「誰が・何を・いつまでに」が揃っているか

# 仕事の進め方プレイブック

## 目的

依頼主（上司・クライアント・メンター）がいる仕事を、手戻りなく・信頼を積み上げながら進めるための型を提供する。
特にインターン業務や副業案件のように「依頼主との認識合わせがすべて」の仕事を想定している。

このスキルの中核は**作業前チェックリスト**。着手前の5分の確認が、完成後の数時間の手戻りを防ぐ。

## 発動条件

- ユーザーが新しいタスク・依頼を受けて着手しようとしているとき
- 「このタスクどう進めればいい？」「進め方が不安」といった相談を受けたとき
- 作業中に詰まった・方針転換したいという相談を受けたとき
- 「完了報告を書きたい」「振り返りをしたい」と言われたとき
- 依頼内容が曖昧なままユーザーが作業を始めようとしているとき（着手前チェックを提案する）

## 前提セットアップ

外部依存なし。MCP・APIキー・環境変数は不要。

## ワークフロー

### フェーズ1: 着手前チェックリスト（中核）

タスクに着手する前に、以下6項目を順に確認する。答えられない項目があれば、それは**作業を始める前に依頼主へ質問すべき事項**である。

| # | 項目 | 確認する問い |
|---|------|-------------|
| 1 | 目的の確認 | なぜやるのか。誰のためか。この成果物は何に使われるのか |
| 2 | 完了定義（Done） | 何をもって完了とするか。Doneの条件を具体的に明文化できるか |
| 3 | 制約の確認 | 期限はいつか。使ってよいツール・予算・リソースは何か。やってはいけないことはあるか |
| 4 | 優先度と想定時間 | 他タスクと比べた優先度は。想定作業時間はどのくらいか（見積もりを依頼主と共有する） |
| 5 | アウトプットイメージ | 成果物の形式（ドキュメント/スライド/コード/表）と粒度の認識は合っているか。**最初にラフ（骨子・構成案・モック）を見せて手戻りを防ぐ** |
| 6 | 不明点の洗い出し | 上記1〜5で曖昧な点をリスト化したか。質問はまとめて早いタイミングで投げるか、それとも着手後でよいものか仕分けたか |

チェックの進め方:

1. ユーザーから依頼内容をヒアリングし、6項目を埋める形で整理する。
2. 埋まらない項目は「依頼主への質問リスト」として書き出す。質問は Yes/No か選択肢で答えられる形にする（例:「形式はスライドとドキュメントどちらが良いですか？」）。
3. 完了定義は必ず文章にする。「良い感じにまとめる」ではなく「◯◯を含む3ページ以内の資料で、△△が判断できる状態」まで具体化する。
4. アウトプットイメージのすり合わせとして、本作業の前にラフ（見出しだけの構成案、画面モック、処理の流れ）を作り、依頼主の確認を取ることを推奨する。

着手前チェックの出力例:

```markdown
## 着手前チェック: <タスク名>
- 目的: 〜のため（最終的に◯◯さんが△△に使う）
- 完了定義: 〜が〜の状態になっていること
- 制約: 期限 MM/DD、ツールは◯◯まで、□□は変更不可
- 優先度/想定時間: 高 / 約3時間（本日中に着手）
- アウトプットイメージ: ◯◯形式。まず構成案を出して確認をもらう
- 質問リスト:
  1. （質問A — 着手前に必須）
  2. （質問B — 進行中でも可）
```

### フェーズ2: 進行中の報連相

**詰まったときの15分ルール**
- 15分調べて・試して解決しなければ、抱え込まずに質問する。
- 質問時は「何をしようとして」「何を試して」「どこで詰まっているか」「自分の仮説」をセットで伝える。丸投げの質問にしない。

**方針転換前の確認**
- 当初の想定と違うやり方が良さそうだと気づいたら、**転換してから報告ではなく、転換する前に確認**する。
- 「Aの予定でしたが、〜の理由でBの方が良さそうです。Bで進めてよいですか？」の形で、理由と代替案をセットで示す。

**中間報告のタイミング**
- ラフ完成時（フェーズ1の構成案確認）
- 作業の折り返し地点、または想定時間を超過しそうだと分かった時点
- 期限が近いのに完了が危ういと分かった時点（分かった瞬間に報告。期限当日に言わない）

中間報告フォーマット:

```markdown
## 中間報告: <タスク名>（進捗 ◯◯%）
- 現状: 〜まで完了
- 次にやること: 〜
- 懸念/相談: 〜（なければ「なし」と明記）
- 完了見込み: MM/DD HH:MM ごろ
```

### フェーズ3: 完了時

**セルフレビュー観点**（報告前に自分で確認する）
- 完了定義を満たしているか（フェーズ1で明文化した条件と突き合わせる）
- 依頼主の視点で見たとき、最初の30秒で内容が把握できるか
- 誤字脱字・数値の誤り・リンク切れ・動作確認漏れがないか
- 「やったこと」だけでなく「やらなかったこと・スコープ外にしたこと」も説明できるか

**完了報告フォーマット（結論ファースト）**

```markdown
## 完了報告: <タスク名>
- 結論: 〜が完了しました（成果物: <リンク/場所>）
- 完了定義との対応: 条件◯◯ → 満たした（〜で確認）
- 補足: スコープ外にした点 / 判断に迷って◯◯とした点
- 確認依頼: 〜を見ていただき、問題なければクローズします
```

**振り返り**（タスクごとに軽量に。3項目だけ書く）

```markdown
## 振り返り: <タスク名>
- うまくいった点: 〜
- 改善点: 〜（次はどうするかまで書く）
- 次に活かす学び: 〜（次の類似タスクの着手前チェックに反映する）
```

## 出力フォーマット

このスキルを使う際は、フェーズに応じて上記のテンプレート（着手前チェック / 中間報告 / 完了報告 / 振り返り）を Markdown で出力する。共通ルール:

- 結論・現状を先頭に置く（結論ファースト）
- 相談事項は「質問リスト」として番号付きで分離し、依頼主が答えやすい形（Yes/No・選択肢）にする
- 日時・数値は具体的に書く（「近いうちに」ではなく「MM/DD HH:MM」）
- 空欄をごまかさない。不明な項目は「未確認（質問リスト#1）」のように明示する

## 注意点

- **チェックリストを儀式にしない。** 6項目すべてを毎回依頼主に質問するのではなく、まず依頼内容から自力で埋め、本当に埋まらない項目だけ質問する。質問が多すぎると依頼主の負担になる。
- **小さいタスクは軽量版でよい。** 30分以内のタスクなら「目的・完了定義・期限」の3点確認だけで着手してよい。
- **ラフ確認を省略しない。** 手戻りの大半は「アウトプットイメージのズレ」が原因。成果物が大きいほど、構成案の段階で確認を取る価値が上がる。
- **悪い報告ほど早く。** 遅延・ミス・想定外は、判明した時点で報告するのが最も信頼を守る。報告を遅らせても状況は良くならない。
- **振り返りは蓄積してこそ意味がある。** 学びは次のタスクの着手前チェックに反映する。同じ改善点が2回続いたら、仕組み（テンプレート・手順）の方を直す。

# Pickup Automation — 条件抽出業務の汎用自動化

「情報源から条件に合うものを拾い、決まった形に整形して届ける」ピックアップ業務を、
定義ファイル `pickup-config.md` を核に自動化するスキル。収集→フィルタ→整形→ログ更新→
定期実行設定までを型として提供する。

## v1 の位置づけ（最重要）

- **v1 は汎用フレーム。** 実際のインターン固有業務（対象サイト・条件・書式）はまだ未確定なので、
  **初回は必ずヒアリングモード（Step 0-B）から始める。** いきなり収集に走らない。
- 実業務の情報源と条件が固まったら、固有の URL・クエリ・書式をこの SKILL.md に焼き込み、
  version を上げる（汎用フレーム → 業務特化への育成が前提の設計）。

## 大原則

- **定義ファイルが正。** 毎回の依頼文ではなく `pickup-config.md` の条件に従って動く。
  依頼文と定義が食い違ったら、どちらを正とするか確認し、定義側を更新する。
- **迷ったら勝手に判断しない。** 条件に照らして確信が持てないものは「グレー」として別枠で提示し、
  ユーザーの判断を仰ぐ。
- **条件は実例で育てる。** グレー判定へのユーザーの回答は、その場で定義ファイルの
  「判断実例集」に追記する。これで精度が回を追うごとに上がる。
- 出力済みのものは `pickup-log.md` を参照して再掲しない（重複防止）。

## ファイル構成

作業ディレクトリ直下に `pickup/` を作って管理する（場所の指定があればそちらに従う）:

```
pickup/
├── pickup-config.md   # ピックアップ定義（テンプレ: templates/pickup-config.md）
└── pickup-log.md      # 出力済みログ（重複防止用。初回実行時に自動作成）
```

- `pickup-config.md` は **1ピックアップタスク = 1定義ブロック**。複数タスクを1ファイルに並べてよい。
- `pickup-log.md` の書式（タスクごとに節を分ける）:

```markdown
## <タスク名>
| 日付 | ID | タイトル/名称 | 判定 |
|---|---|---|---|
| 2026-07-04 | https://example.com/a1 | 記事タイトル | 掲載 |
| 2026-07-04 | https://example.com/a2 | 記事タイトル | 除外(広告) |
```

ID は定義ファイルの「重複判定」で決めたもの（URL・企業名・案件ID など）。除外・グレー判定も
記録しておくと、後で条件を見直すときの材料になる。

## 前提セットアップ

基本は外部依存なし（内蔵の WebFetch / WebSearch / ファイル読み込みで動く）。

| 情報源の種類 | 必要なもの | 未接続時の代替 |
|---|---|---|
| 公開 Web ページ・RSS | なし（WebFetch） | — |
| Web 検索ベースの収集 | なし（WebSearch） | — |
| ローカルファイル（CSV/MD/テキスト） | なし（Read） | — |
| Google Drive 上の資料 | Google Drive MCP | ファイルを手動でダウンロードして貼り付け/配置してもらう |
| Slack チャンネル | Slack MCP | 対象メッセージを手動でコピペしてもらう |
| GitHub | GitHub MCP（推奨） | WebFetch で api.github.com（認証なし、60req/時） |

MCP が必要な情報源は、定義ファイルの「情報源」欄にその旨を明記する。実行時に未接続なら
エラーで止まらず、上表の代替手段を案内して続行するかスキップするかを確認する。

## ワークフロー

### Step 0-A: 設定確認

1. `pickup/pickup-config.md` を探して読む。
2. **無ければ → Step 0-B（ヒアリングモード）へ。** これが初回の必須ルート。
3. あれば、依頼がどのタスク定義に対応するか特定する（タスクが1つなら確認不要。複数あって
   曖昧なら「どのピックアップを実行しますか」と一度だけ聞く）。→ Step 1 へ。

### Step 0-B: ヒアリングモード（初回・新規タスク追加時）

`templates/pickup-config.md` をベースに、次の **5つの質問** で定義を一緒に作る。
一度に全部聞かず、1〜2問ずつ会話で埋めていく:

1. **何を・どこから拾いますか?** — 情報源の URL / ファイルパス / MCP 接続先。複数可。
2. **どういうものを含め、どういうものを除外しますか?** — 自然言語の条件に加えて、
   **「これは含める」「これは除外」の具体例を最低1つずつ** 挙げてもらう（条件だけだと必ずブレる）。
3. **どんな形で欲しいですか?** — 表の列（例: タイトル/URL/要約/該当理由）と並び順・件数上限。
4. **どこに届けますか?** — このチャットに表示 / ファイルに追記 / Slack 投稿（MCP 必要）。
5. **どのくらいの頻度で?** — 手動実行のみ / 毎朝 / 週次など。

定義ドラフトを書いたら、**その場でサンプル実行**する（Step 1〜3 を1回、少量で回す）。
結果を見せて「拾いすぎ/拾い漏れ」を指摘してもらい、条件と判断実例集を修正してから
`pickup/pickup-config.md` として保存する。**サンプル実行なしで定義を確定しない。**
定義確定時、サンプル実行で提示済みの項目は `pickup-log.md` に記録しておく
（定常実行の初回に同じものが再掲されるのを防ぐため）。

### Step 1: 収集

定義の「情報源」に応じて手段を選ぶ（前提セットアップの表を参照）:

- URL 指定 → WebFetch。取得時の prompt に「何を一覧で抜き出すか」を明示する
  （例:「このページの記事を、タイトル・URL・日付・冒頭要約の形式で全件リストして」）。
- テーマ・キーワード指定 → WebSearch で候補を集めてから、必要なら個別ページを WebFetch。
- ファイル → Read（大きい場合は Grep で候補行を絞ってから読む）。
- MCP 接続先 → 対応する MCP ツール。未接続なら代替を案内（エッジケース参照）。

収集件数と取得元を必ず控えておく（Step 3 の報告で「N件中M件が条件合致」と示すため）。

### Step 2: フィルタ（含める / 除外 / グレー）

収集した各項目を定義の条件に照らして3分類する:

| 分類 | 基準 | 扱い |
|---|---|---|
| 合致 | 「含める条件」に合い、除外条件・判断実例集に抵触しない | 本枠で出力 |
| 除外 | 「除外する条件」または判断実例集の除外例に該当 | 出さない（ログには記録） |
| グレー | どちらとも言い切れない | **別枠で理由付き提示** |

- まず `pickup-log.md` と照合し、出力済み ID は除外する（定義で「再掲あり」の指定がある場合を除く。
  ログ未作成なら照合はスキップして全件を判定に回す）。
- グレーは「◯◯という点では合致だが、××が条件に明記されていない」の形で迷った理由を添える。
- **ユーザーがグレーに判定を返したら、その場で定義ファイルの判断実例集に1行追記する。**
  これを省略しない — このスキルの精度向上はこの1行の積み重ねだけで実現される。

### Step 3: 整形

定義の「出力形式」どおりの表にする。勝手に列を増減しない（改善提案は表の後に別枠で書く）。
表の前に必ず1行のサマリを付ける:

> ◯◯（情報源）から N 件取得 → 条件合致 M 件、グレー K 件（前回からの新着のみ）

### Step 4: ログ更新

出力した項目（グレー・除外含む）を `pickup-log.md` の該当タスク節に追記する。
ファイルが無ければテンプレどおりの書式で新規作成する。ログが500行を超えたら、
古い行のアーカイブ（`pickup-log-archive.md` への移動）を提案する。

### Step 5: 届け先へ

定義の「届け先」に従う。チャット表示ならそのまま、ファイルなら指定パスに追記、
Slack なら MCP で投稿（未接続なら投稿用テキストを整形して手動投稿を依頼）。

### Step 6: 定期実行の設定案内（希望があれば）

定義の「実行頻度」が手動以外なら、環境で使える定期実行手段を案内する:

- Claude Code のトリガー/Routine 機能が使える環境 → 「毎朝8時に pickup/pickup-config.md の
  ◯◯タスクを実行して」という趣旨のプロンプトで cron トリガーを設定する。
- 使えない環境 → 実行用の依頼文ワンライナーを渡し、手動で定期的に投げてもらう。

定期実行時も Step 0-A から順に回る（定義が更新されていれば最新の条件が使われる）。

## エッジケース

| 状況 | 挙動 |
|---|---|
| 情報源にアクセスできない（404/タイムアウト/ログイン必須） | エラー内容と対象を報告し、他の情報源があればそれだけで続行。「◯件中◯源が取得失敗」と明記。恒常的なら定義の情報源欄の見直しを提案 |
| MCP が必要だが未接続 | 前提セットアップ表の代替（手動貼り付け等）を案内し、続行/スキップを確認 |
| 条件合致がゼロ | 「該当なし」と収集件数を報告して正常終了。**条件を勝手に緩めない。** グレーが多いなら条件が厳しすぎる可能性として提示 |
| ほぼ全件が合致 | そのまま出さず「条件が緩すぎる可能性」を指摘し、上位のみ提示して絞り込み条件を相談 |
| 条件が曖昧で判定できない項目が多い（グレーが合致を上回る） | フィルタを中断してグレーの代表例を3〜5件見せ、条件の言語化を先に行う（ヒアリングモードに部分的に戻る） |
| 依頼文と定義ファイルの条件が矛盾 | どちらを正とするか確認。今回限りなら定義は変えず、恒久変更なら定義を更新して履歴に記録 |
| ログファイルが壊れている/書式不明 | 読める範囲で重複判定し、その旨を報告。再構築の許可を得てから書式を直す |

## 条件を育てる運用（version up の指針）

- グレー判定へのフィードバックが数回蓄積したら、判断実例集から共通パターンを抽出して
  「含める/除外する条件」本文への昇格を提案する（実例集は残す）。
- 特定の業務（対象サイト・定型書式・固有の判断基準）で運用が安定したら、その手順を
  この SKILL.md に固有セクションとして焼き込み、plugin.json / 定義ファイルの version を上げる。
  汎用フレームのままで運用し続けることは想定しない。

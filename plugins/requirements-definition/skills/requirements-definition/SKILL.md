# Requirements Definition（要件定義整理）

曖昧な依頼やアイデアを、ヒアリングと3つの思考フレームワークを通じて
構造化された要件定義書（Markdown）に落とし込むスキル。

使うフレームワークは次の3つ。

1. **イシュー特定** — 安宅和人『イシューからはじめよ』流。手を動かす前に「本当に解くべき問い」を見極める
2. **MECE分解** — 課題・要件をモレなくダブりなく分解する
3. **ピラミッド構造化** — バーバラ・ミント流。結論→根拠→事実の階層で文書を組み立てる

## 目的

- 「なんとなく作りたいもの」を、合意可能・着手可能な要件定義書に変換する
- 解く価値のない問題に工数を注ぐ前に、イシューの質を検証する
- 抜け漏れ（考慮されていない要件）と重複（同じ話の言い換え）を排除する
- 読み手が結論から理解できる構造の文書を残す

## 発動条件

- ユーザーの依頼が曖昧で、そのまま実装に入ると手戻りが大きそうなとき
  （例:「社内向けのツールを作りたい」「このプロセスを自動化したい」）
- 「要件定義して」「要件をまとめて」「仕様を整理して」と明示的に依頼されたとき
- 新規プロジェクト・新機能の企画段階で、スコープや優先順位が未確定なとき
- 既存の雑多なメモ・議事録・チャットログから要件定義書を起こすよう頼まれたとき

すでに要件が明確で、単に実装だけを求められている場合は発動しない。

## 前提セットアップ

**外部依存なし。** MCPサーバー・APIキー・環境変数は一切不要な、純粋な思考フレームワークスキル。
必要なのはユーザーとの対話（ヒアリング）だけ。

## ワークフロー

### Step 0: ヒアリング

まず以下を確認する。ユーザーの最初の発言で判明している項目は飛ばし、
不明な項目だけをまとめて質問する（一問一答で何往復もさせない）。

| 観点 | 質問例 |
|---|---|
| 背景 | なぜ今これをやりたいのか？ きっかけは？ |
| 現状の課題 | 今、何にどれくらい困っているか？ 誰が困っているか？ |
| ゴール・成功指標 | 何がどうなったら成功か？ 数値で言えるか？ |
| スコープ / 非スコープ | 必ず含めたいこと・今回はやらないと決めていることは？ |
| 制約・期限 | 予算・技術・体制・期限の制約は？ いつまでに必要か？ |
| ステークホルダー | 利用者は誰か？ 承認者・関係部署は？ |

回答が得られない項目は「前提（仮置き）」として文書に明記し、後で検証できるようにする。

### Step 1: イシュー特定

集めた情報から「本当に解くべき問い」を1文で定義する。良いイシューは次の2軸で評価する。

- **解く価値（イシュー度）**: それに答えが出ると意思決定や行動が大きく変わるか。
  誰も困っていない問題、答えが出ても何も変わらない問題は捨てる
- **答えを出せる度合い（解の質を出せるか）**: 今の情報・期間・体制で現実的に答えを出せるか

やること:

1. ユーザーの依頼の裏にある問いの候補を2〜3個挙げる
   （例:「勤怠アプリを作りたい」→ 候補:「打刻の手間を減らすには？」「勤怠データの集計工数を減らすには？」「労務リスクを検知するには？」）
2. 各候補を上の2軸で評価し、最も筋の良い1つを選ぶ
3. 「◯◯という状況において、△△を□□にするには何が必要か」の形で言語化し、ユーザーに確認する

**「作りたいもの」ではなく「解きたい問題」で定義する**のがポイント。
手段（アプリ、ツール）がイシューに紛れ込んでいたら剥がす。

### Step 2: MECE分解

イシューに答えるために必要な課題・要件を、モレなくダブりなく分解する。
切り口の例（対象に合わせて選ぶ。無理に全部使わない）:

- **利用者の行動フロー順**: 登録 → 入力 → 確認 → 出力 → 通知
- **ステークホルダー別**: エンドユーザー / 管理者 / 運用者 / 経営層
- **要件の種類別**: 機能要件 / 非機能要件（性能・セキュリティ・可用性・運用性）
- **時間軸**: 導入前 / 導入時 / 運用中 / 廃止時
- **課題の構造**: 発生頻度 × 影響度、あるいは 原因系 / 対症系

分解したら各要素をチェックする:

- モレ: 「これで全部か？ 例外ケース・異常系・運用は含まれているか？」
- ダブり: 「2つの項目が同じことの言い換えになっていないか？」
- 粒度: 同じ階層の項目の抽象度が揃っているか

### Step 3: ピラミッド構造化

分解結果を、結論を頂点とする階層に組み直す。

```
結論（このプロジェクトで何をどこまでやるか）
├─ 根拠1（なぜそれをやるのか）
│   ├─ 事実・データ
│   └─ 事実・データ
├─ 根拠2
│   └─ 事実・データ
└─ 根拠3
    └─ 事実・データ
```

- 上位は下位の**要約**になっていること（下を読まなくても上だけで意味が通る）
- 同一階層は Step 2 の MECE な切り口で並べること
- 「事実」と「解釈」と「提案」を混ぜないこと

この構造をそのまま要件定義書の章立てに反映し、優先順位は **MoSCoW**
（Must / Should / Could / Won't）で付ける。迷ったら「それがないとリリースできないか？」で
Must と Should を切り分ける。

### Step 4: ドキュメント化とレビュー

下の出力フォーマットで要件定義書を作成し、ユーザーに提示する。
仮置きした前提・未確定事項を明示し、認識のズレがないかレビューを依頼する。
フィードバックを反映して確定版とする。

## 出力フォーマット

```markdown

- 作成日: YYYY-MM-DD / 版: v0.1（ドラフト）
- 作成者・確認者: <名前>

## 1. 背景
<なぜこのプロジェクトが必要か。現状の課題と、放置した場合に何が起きるか>

## 2. イシュー（解くべき問い）

| | | | | |

- 
### 非スコープ（今回やらないこと・理由つき）
- 

## 5. 機能要件

|---|---|---|---|
| F-01 | | | Must |
```

## 注意点

- **ヒアリングを省略しない。** 情報が足りないまま要件定義書を「それらしく」埋めるのが
  最悪のパターン。不明な点は捏造せず、質問するか「前提（仮置き）」として明記する
- **イシューの合意を最優先にする。** Step 1 でユーザーと問いの認識が合っていないと、
  以降の全作業が無駄になる。Step 1 の結果は必ずユーザーに確認してから先に進む
- **手段先行に注意。** ユーザーが「◯◯というツールで」と手段を指定してきても、
  一度イシューに立ち戻る。ただしユーザーの意思として手段が確定しているなら制約として扱う
- **完璧なMECEを追いすぎない。** 分解は意思決定に十分な粒度で止める。
  切り口の美しさより、モレによる手戻りを防ぐことが目的
- **非機能要件とスコープ外を必ず書く。** 曖昧な依頼で後から揉めるのはほぼこの2つ。
  「やらないこと」を理由つきで文書化することが要件定義書の価値の半分を占める
- 要件定義書はドラフト（v0.1）として提示し、確定はユーザーのレビューを経てから行う

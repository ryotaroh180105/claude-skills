# SNS Ops Team

SNSアカウント運用を「企画 → リサーチ → 執筆 → レビュー → キュー出力」の
チーム作業として回すスキル。成果物は投稿キュー（`post-queue.md`）までで、
**実際の投稿はこのスキルでは行わない**。承認済み（approved）の行を
sns-auto-posting スキルが読んで投稿する分担になっている。
承認 = Ryo（ユーザー）が該当行のステータスを `approved` に変更すること。

## 工程マップ（「文章を書く仕事」の第一原理分解との対応）

| 第一原理の工程 | このスキルでの担当 |
|---|---|
| 読者理解 | `sns-strategy.md` のペルソナ・提供価値（Step 0 / 初回セットアップ） |
| テーマ選定 | ② 企画 |
| 一次情報の調査 | ① リサーチ（twitter-intel / agent-reach / hermes-relay 経由） |
| 構成・表現 | ③ 執筆（`references/x-post-quality.md` 準拠） |
| 校正 | ④ レビュー（炎上・法令・トーン・AIっぽさ） |
| 配信 | **sns-auto-posting**（approved 行のみ。このスキルは対象外） |
| 反応分析 | 「配信→反応分析ループ」（下記）。分析結果を戦略・リファレンスへ還流 |

全工程がこの表のどこかに割り当てられていることを崩さない。工程を増減する
改修をするときは、まずこの表を更新してから本文を直す。

## 前提セットアップ

このスキル自体に外部 API・キーは不要。ファイル読み書きとサブエージェントだけで動く。

| 依存 | 必須? | 用途 |
|---|---|---|
| なし（本体） | - | 企画〜レビュー〜キュー出力まではキー不要 |
| agent-reach スキル | 任意 | リサーチ強化（X/Reddit/YouTube等の実データ収集）。無ければ WebSearch と一般知識で縮退 |
| sns-auto-posting スキル | 任意 | approved 行の投稿実行。そちら側で X API キー等が必要 |

## ファイル構成

アカウントごとにディレクトリを分ける（運用代行で複数アカウントを扱うため）。

```
sns/
└── <アカウント名>/
    ├── sns-strategy.md   # アカウント戦略（テンプレ: templates/sns-strategy.md）
    └── post-queue.md     # 投稿キュー（テンプレ: templates/post-queue.md）
```

作業ディレクトリにすでに `sns/` や `sns-strategy.md` があればそれを使う。
どのアカウントの話か不明なら、`sns/` 配下の一覧を見せて選んでもらう。

## ワークフロー全体像

```
戦略確認 ──(無ければ)──> 初回セットアップ（戦略ファイルを一緒に作る）
   │
   ▼
週次バッチ: リサーチ+ネタ出し → 執筆 → レビュー → post-queue.md に draft 追記
   │
   ▼
Ryo が確認し、通す行を approved に変更（このスキルの外の人間作業）
   │
   ▼
sns-auto-posting が approved を投稿し posted に更新（このスキルはやらない）
   │
   ▼
配信→反応分析ループ: 実績数値を取得・分析 → sns-strategy.md と
references/x-post-quality.md へ還流 → 次バッチの企画に反映
```

### Step 0: 戦略ファイルの確認（毎回最初にやる）

1. 対象アカウントの `sns/<アカウント名>/sns-strategy.md` を読む。
2. **無い場合（初回）**: 以下の「初回セットアップ」へ。勝手にデフォルト戦略で
   投稿を作り始めない。
3. **ある場合**: 目的・ペルソナ・トーン・NGリストを把握してから次の工程へ。
   以降の全エージェントへの指示に、戦略ファイルの該当部分を必ず埋め込む。

### 初回セットアップ（戦略ファイルが無いとき）

`templates/sns-strategy.md` を `sns/<アカウント名>/sns-strategy.md` にコピーし、
ユーザーにヒアリングしながら一緒に埋める。一度に全部聞かず、次の順で数問ずつ:

1. アカウントの目的（フォロワー増? 集客? 採用? 収益化?）と対象プラットフォーム
2. ターゲットペルソナ（誰に届けたいか、その人の悩み）
3. 提供価値とトーン&マナー（参考にしたい既存アカウントがあれば聞く）
4. NGリスト（触れない話題・使わない表現・競合言及の可否）
5. 投稿頻度と KPI

埋め終わったら要約を見せて確認をとり、その週のバッチに進むか聞く。
`post-queue.md` が無ければ `templates/post-queue.md` からヘッダ部分をコピーして作る。

### 週次バッチ（2回目以降のメイン運用）

`post-queue.md` が既にある場合は追記する。既存の最大 id と、まだ `draft` /
`approved` のまま残っている行の予定日時を確認し、id は連番を継続、
予定日時は既存行と重複しないように割り付ける。

工程は「役割設計とエージェント指示例」のとおり。1バッチの本数は
戦略ファイルの投稿頻度から決める（例: 週5投稿なら5〜7本作り、没を見込んで多めに）。

### 承認と受け渡し

- 出力した行はすべて `draft`。**このスキルが勝手に approved にしない。**
- Ryo に「post-queue.md を確認して、投稿してよい行の ステータス を approved に
  変更してください。投稿は sns-auto-posting が行います」と案内して終わる。
- 修正指示が来たら該当行の本文を直し、`draft` のままにする。

### 配信→反応分析ループ（投稿後。loop-engineering の6要素で設計）

投稿して終わりにしない。以下のループを**週次バッチの冒頭**で回す
（新しい投稿を作る前に、前週分の振り返りを必ず先にやる）。

- **Trigger**: 週次バッチの依頼が来たとき（自動化するなら Routine/cron で
  「毎週決まった曜日に振り返り→バッチ」を発火させる設計を提案してよい）。
  `posted` 行のうち、投稿から48時間以上経過し数値未記録のものが対象。
- **Doer（数値取得）**: 優先順に試す。
  1. ユーザー提供のアナリティクス数値（インプレッション・いいね・RP・リプライ・
     プロフィールクリック・フォロー増）
  2. hermes-relay で posted 行の投稿 URL の反応を調査（いいね数等の概況）
  3. どちらも不可なら「数値なし」として記録だけ残しスキップ
- **分析**: 投稿ごとに「フックの型 / 狙い（保存・共有・共感・リプ）/ 数値」を並べ、
  アカウント内の中央値と比較して勝ち/負けを判定する（絶対値やよそのアカウントと
  比べない。自分の過去投稿との相対で見る）。
- **Memory（還流先）**: 分析のたびに次の3つへ還流する。
  1. `sns-strategy.md` の「振り返りログ」節に日付・投稿id・数値・学びを追記
  2. **同じ型の勝ちが3回再現したら** `references/x-post-quality.md` の分析ソース表へ
     の追記（自アカウントの実例として）と、該当する型の記述強化を提案する
  3. 負けが続く型・ネタは、NGリストまたは企画方針の修正案として提示
- **Verifier**: 数値の裏付けがない「学び」は書かない。1回だけの結果で戦略や
  リファレンスを変えない（3回ルール）。
- **Stop Rules**: 数値が2週連続で取得できなければループを止めて取得手段を
  ユーザーに相談する。フォロワー急減・炎上の兆候（否定的リプの急増）が出たら
  新規投稿の作成を止め、戦略見直しを先に提案する。

戦略ファイル・リファレンスの書き換えは修正案を提示して**ユーザーの合意を得てから**行う。

**数値の扱い**: エンゲージメント率・インプレッション等はユーザー提供値か agent-reach 等で
実際に取得した値のみを使う。推測・補正で数字を作らない（Epistemia対策。CLAUDE.md 参照）。
取得できない指標は「未取得」と明記し、それらしい数値を埋めない。

**運用ルールの改訂ループ（NGリストの育て方）**: トーン逸脱・過剰な同調・不適切な表現など
「事件」が起きたら、その場しのぎの訂正で終わらせず `sns-strategy.md` の NGリスト・トーン節に
再発防止のルールを1行追記してから次に進む（例:「感嘆符は1投稿2つまで」「全員一律の称賛禁止、
具体的に何が良いか1点言語化してから返信」）。次バッチの執筆・レビュー指示にはこの更新を
必ず反映する。

## 役割設計とエージェント指示例

5つの役割で回す。リサーチと企画の初動は並列可、執筆は企画の後、
レビューは執筆の後、スケジュール管理（キュー出力）は最後。
規模が小さいとき（1〜2本の単発依頼）はサブエージェントを立てず、
同じ役割分担・同じ観点を自分が順番に演じて1人で回してよい。

各プロンプトの `{...}` は戦略ファイル等から実際の値を埋めて渡すこと。

**① リサーチ（並列実行その1）** — Agent tool にそのまま渡す例:

> あなたはSNSリサーチ担当です。テーマ「{アカウントの発信領域}」について、
> 今週投稿に使えるトレンド・話題を調査してください。agent-reach スキルが
> 利用可能なら X と YouTube の実データを収集し、無ければ WebSearch を
> 使ってください。出力: 話題を5件、各件について「概要 / なぜ今話題か /
> {ペルソナ} に刺さる切り口」を3行以内で。出典URLも付けること。

**② 企画（並列実行その2、リサーチ結果が届いたら統合）**:

> あなたはSNS企画担当です。アカウントの目的は「{目的}」、ターゲットは
> 「{ペルソナ}」、提供価値は「{提供価値}」です。添付のリサーチ結果も
> 参考に、今週の投稿ネタを{本数+3}案出してください。各案は「仮タイトル /
> 狙い（保存・共有・共感のどれを取るか）/ 想定プラットフォーム{platform} /
> 投稿候補日」の形式。NGリスト（{NGリスト}）に触れる案は出さないこと。

**③ 執筆（採用したネタごとに。独立なので複数を並列起動してよい）**:

執筆エージェントには `references/x-post-quality.md`（伸びる投稿の構造と
AIっぽさ回避）の**内容をプロンプトに直接貼る**（パス渡しはサブエージェントの
実行環境でパスが解決できないことがあるため、貼り込みを既定とする）。

> あなたはSNS執筆担当です。以下は投稿品質の基準です（フック・言葉遣い・構成・
> 説得力・AIっぽさ回避）: {x-post-quality.md の内容}。
> そのうえで次のネタで {platform} 向けの投稿本文を書いて
> ください: {ネタの内容}。この投稿で取りにいく反応は {保存/共有/共感/リプライ}
> です。トーン&マナー: {戦略ファイルのトーン&マナー節を
> 全文貼る}。文体例: {文体例}。制約: Xなら全角140字以内（長文可の方針なら
> その旨明記）、ハッシュタグは{方針}、NGリスト: {NGリスト}。
> 書き終えたら上記基準のAIっぽさチェックリストで自己検査し、
> 該当があれば直してから出すこと。出力は本文のみ。改行位置まで投稿する形そのままで。

**④ レビュー（執筆結果をまとめて1エージェントに）**:

> あなたはSNS投稿のレビュー担当です。以下の投稿案{n}本を審査してください。
> 観点: (1) 炎上リスク（政治・宗教・ジェンダー・災害・特定個人や企業への
> 攻撃と読める表現、事実と断定できない言い切り） (2) 法令・規制の注意領域
> （健康・美容系なら薬機法的な効能断定、「必ず稼げる」等の景表法・誇大広告
> 表現、案件投稿のPR表記漏れ、他者コンテンツの無断転載）— アフィリエイトリンク
> や計測パラメータ付きURLが含まれるのに #PR 等の表記が無いものは修正必須。
> 表記ルールは affiliate-monetization スキルの funnel-config が正 (3) トーン一貫性
> （このアカウントのトーン: {トーン&マナー}、NGリスト: {NGリスト}）
> (4) 品質・AIっぽさ: 以下の品質基準（{x-post-quality.md の内容}）に照らし、
> 1行目のフックが立っているか・体験/数字/固有名詞が最低1つあるか・
> AIっぽさチェックリストに該当しないかを判定。該当は修正付きOKで修正文を出す。
> 出力: 各投稿に OK / 修正付きOK（修正文を提示）/ NG（理由）の判定。
> 迷ったら NG に倒してください。法律の最終判断はできないので、グレーな
> ものは「要人間確認」と明示すること。

**⑤ スケジュール管理（レビュー通過分をキュー化。自分でやってもよい）**:

> あなたはSNSスケジュール管理担当です。以下のレビュー通過済み投稿{n}本を
> {path}/post-queue.md の表形式（templates/post-queue.md の書式に従う）で
> 追記してください。既存の最大 id は {last_id} なので続きから連番。
> 予定日時は {投稿頻度・推奨時間帯} に従い、既存の未投稿行と重複しないよう
> 配置。ステータスは全行 draft。本文セル内の改行は <br>、縦棒は \| に
> エスケープすること。

## エッジケースの扱い

- **戦略ファイルが無い**: 必ず初回セットアップに分岐。「とりあえず1本だけ」と
  言われた場合も、最低限「目的・ターゲット・トーン・NG」の4点だけ口頭で聞き、
  その回答をそのまま戦略ファイルの初版として保存してから書く。
- **レビューで全没**: そのままキューに書かない。NG理由を要約して企画工程に
  戻し、ネタまたは切り口を差し替えて再実行する。再生成は2周まで。2周やっても
  全没なら、NG理由一覧をユーザーに見せて方針を相談する（戦略とネタ領域が
  噛み合っていない可能性が高い）。
- **プラットフォーム未指定**: 戦略ファイルの対象プラットフォーム欄に従う。
  そこにも複数書かれていれば主要プラットフォーム（先頭記載）を使う。戦略
  ファイル自体が無い/未記入なら「Xでよいですか?」と確認し、勝手に決めない。
- **キューが肥大化**: `posted` の行が30行を超えたら、月別アーカイブ
  （`post-queue-archive-YYYYMM.md`）への移動を提案する。
- **agent-reach 未導入でリサーチ精度が欲しいと言われた**: agent-reach スキルの
  導入を案内する（X等の実データが取れるようになる）。導入までは WebSearch で代替。
- **「投稿して」と頼まれた**: このスキルでは投稿しない。sns-auto-posting の
  利用（と、そちらで必要な API キー設定）を案内する。sns-auto-posting が
  未導入・利用不可の場合は、approved 行をプラットフォーム別のコピペ用テキスト
  （本文+予定日時+メディアパス）に整形して出力し、手動投稿を依頼する。

## やらないことの明確化

- 投稿の実行・予約 API 呼び出し（sns-auto-posting の担当）
- ステータスを `approved` / `posted` に変更すること（approved は Ryo、posted は
  sns-auto-posting が変更する）
- ユーザーの合意なしの戦略ファイル書き換え

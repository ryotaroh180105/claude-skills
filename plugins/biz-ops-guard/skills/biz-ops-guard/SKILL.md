# Biz-Ops Guard（プロダクト成立性の設計）

目的は **「動くもの」を「使われ続けるプロダクト」として成立させる**こと。
その差は技術力ではなく、導入・保守・運用・マーケティング・差別化の設計で決まる。
大原則: **コードを書く前にビジネス運用面を設計する。後付けは10倍高くつく。**

`requirements-definition`（何を作るか）の後、`yagni-guard`（どう小さく作るか）の前に挟む。

## 発動条件

- 他人に使ってもらう前提のアプリ・スキル・ツールを設計する時。
- 要件定義が終わり、実装に入る前。
- リリース・公開・配布の直前。
- 既存プロダクトが「使われない」「保守がつらい」「差別化できてない」と感じた時。
- ユーザーが「ビジネス面」「プロダクトとして」「運用面」と言った時。

## 適用範囲の判定（最初にやる）

| 対象 | 適用 |
|---|---|
| 自分専用ツール（他人が使わない） | **適用しない**。`yagni-guard` だけでよい。 |
| 他人にも使ってほしいスキル・アプリ | **full**。以下すべてを適用。 |
| 学習・実績目的（G3）と割り切るもの | ラダーは通すが、Noの項目を「意図的に無視」と明示して進んでよい。 |

G3 = このリポジトリの目的タグ「就活で話せる実績・学びを作る」（`docs/skill-requirements.md`）。本スキル内では「使われなくても学習・実績目的で作る」の意。

## Go/No-Go ラダー（実装前に、この順で答える）

実装済み・公開直前に初めて適用する場合も、ラダーとシートを遡って埋める。Noが出たら公開を止めるか「意図的に無視」を明記する。

1. **想定ユーザーを固有名詞で3人言えるか？**（自分を含めてよい。言えなければ自分専用ツール → 適用外）
2. **代替手段からの乗り換え理由を1文で言えるか？**（代替には手作業・Excel・ChatGPTに直接聞く、を必ず含める）
3. **導入から最初の価値体験まで5分以内・3ステップ以内の設計か？**
4. **保守に払える上限（週N分）を宣言できるか？**
5. **最初の10ユーザーに届ける経路を1つ言えるか？**

No がある項目は、①設計を直して Yes にする、②「学習目的なので意図的に無視」とシートに明記する、③作らない、のいずれか。**暗黙に無視して実装に進むのが唯一の禁止事項。**

## 5観点の設計原則

### 1. 導入（オンボーディング）

- **Time-to-First-Value ≤ 5分・3ステップ**。初回の価値体験までの手順数を設計段階で数える。
- 前提条件（APIキー・課金・環境・アカウント）は README/SKILL.md の**先頭に表で明示**。
- **デフォルトで動く**（zero-config first）。設定は動いた後に触るもの。
- 前提未設定のまま起動された時の初回体験を設計する（無言で失敗させない。何が足りないか自分で言わせる）。
- **出口も書く**（アンインストール手順・データの持ち出し方）。出口が見えると導入の心理障壁が下がる。

### 2. 保守（メンテナンス）

- **3ヶ月放置テスト**: 自分が3ヶ月触らなくても動くか。壊れる要因（外部API変更・依存更新・鍵の期限）を列挙する。
- 外部依存ごとに「壊れたら何が起きる／どう気づく／代替は何か」を1行ずつ書く。
- **保守予算を宣言**: 週N分まで。2回連続で超過したら縮小・凍結・廃止を判断する（ずるずる続けない）。
- バージョニング（semver）と CHANGELOG。ユーザーがいる以上、無言の破壊的変更をしない。
- フィードバック窓口を**1つだけ**決める（GitHub Issues / DM / フォーム。分散させない）。

### 3. 運用（オペレーション）

- **ランブック**: 定常運用で人間がやる作業を全部列挙する。理想はゼロ。ゼロにできない作業は頻度×分数でコスト化する。
- **静かに壊れない**: 失敗が自分（またはユーザー）に届く経路を1つ用意する。通知のない自動化は事故る。
- **コスト構造**: ユーザー1人・利用1回あたりの限界費用（API課金・ホスティング）を見積もる。ユーザーが増えると赤字になる構造は設計段階で潰す。
- **期待値の宣言**: どこまで保証するかを明示する（「ベストエフォート・個人運営」と書くだけでもよい。書かないのが最悪）。

### 4. マーケティング

- **一文価値提案**を先に固める: 「（誰）が（既存手段）せずに（成果）できる」。これが書けない機能は作らない。
- **README = LP**。最初の10行で「誰の・何が・どう良くなるか」＋デモ（スクショ/GIF/実行例）。インストール手順はその後。
- **検索性**: ユーザーが検索する語を名前と description に入れる（かっこいい造語より検索される平凡な語）。
- **ドッグフーディングログ**: 自分で使った結果・数字（削減時間・件数・収益）を記録する。実績が広報素材と就活エピソード（G3）の原料になる。
- **配布チャネルを実装前に1つ決める**（note / X / GitHub / marketplace）。ローンチは1回のイベントではなく、更新のたびに繰り返す。記事化は `article-writer`、X運用は `sns-ops-team` に委譲。

### 5. 差別化

- **代替の列挙が先**。競合は同種アプリだけでなく「手作業・Excel・既存SaaS・ChatGPTに直接聞く」を必ず含める。
- 乗り換え理由は**1点に絞る**。10%良い10項目より、10倍良い1項目。
- 持続的優位の源泉を1つ特定する: 自分だけのデータ／運用ノウハウ／組み合わせ／ニッチ特化。機能自体は模倣されるものと考える。
- 差別化が1つも無いなら: 作らない、または「学習目的（G3）」とシートに明示して割り切る。

## 設計時のリサーチ（hermes-relay 経由）

シートを埋めるための調査は、Claude 自身の WebSearch ではなく **hermes-relay** で実行する
（CLAUDE.md の方針。手順は `plugins/hermes-x-search/skills/hermes-x-search/SKILL.md` が正）:

- 競合・代替手段・既存ツールの比較、記事/ドキュメント調査 → `engine: notebooklm` + `topic:`
- X 上の需要・不満・「今どう解決しているか」の生の声 → ヘッダなし（x_search）

調べるのは3点だけ。それ以上の市場調査はやりすぎ:

1. **代替手段の実在**: 想定ユーザーが今それを何で解決しているか（手作業・Excel・既存ツール名）。
2. **不満の種**: 既存手段への不満・つまずき（乗り換え理由の候補）。
3. **検索される語**: ユーザーが実際に使う検索キーワード（命名・description に入れる）。

結果はシートの「代替手段と乗り換え理由」「配布チャネル」欄に1〜2行で反映する。調査レポートを別途作らない。
調査は原則1往復（最大2往復）。結果が不十分でも仮置きでシートを埋めて進み、リリース前チェックで見直す。

## 成果物: ビジネス運用面シート

full 適用時は実装前に以下を埋める（プロダクトの `docs/biz-ops.md`、スキルなら SKILL.md 冒頭または同ディレクトリに置く）。**全項目1〜2行。1ページを超えたら書きすぎ。**

```markdown
# <product> ビジネス運用面シート
- 一文価値提案: （誰）が（既存手段）せずに（成果）できる
- 想定ユーザー（固有名詞3人）:
- 代替手段と乗り換え理由（1点）:
- 導入: 手順数 __ / 所要 __分 / 前提条件:
- 保守: 予算 週__分 / 壊れる要因: / 廃止基準:
- 運用: 定常作業: / 失敗通知経路: / 1利用あたりコスト:
- 配布チャネルと最初の10ユーザー:
- 記録する指標（ドッグフーディングログ）:
- 意図的に無視すること:
```

## リリース前チェックリスト

- [ ] 前提条件が README/SKILL.md の先頭に表である
- [ ] クリーン環境で導入手順どおりに入れて5分以内に価値が出る（Claude が新規ディレクトリ等で再現、不可ならユーザーに依頼。未実施ならチェックを空欄のまま残す）
- [ ] README 冒頭10行で価値提案＋デモが伝わる
- [ ] 前提未設定で起動した時のエラーが自己説明的である
- [ ] CHANGELOG / version がある
- [ ] フィードバック窓口が1つ明記されている
- [ ] 失敗の通知経路がある（自動実行系のみ）
- [ ] 期待値（保証範囲）が書いてある
- [ ] ビジネス運用面シートが埋まっている

## 定期レビュー（月1、5分）

シートの指標を見て4択で判断する: **改善 / 現状維持 / 凍結 / 廃止**。

- 保守予算の2回連続超過、またはユーザー0が2ヶ月 → 凍結か廃止を必ず検討する。
- 凍結・廃止は失敗ではなく成果。学び（なぜ使われなかったか）をシートに追記して閉じる（G3の素材になる）。

## やりすぎ防止（yagni-guard との整合）

ビジネス運用面の整備自体も過剰設計しない。

- ユーザー10人未満で監視ダッシュボード・分析基盤・自動リリースパイプラインを作らない。通知はメール/Slack 1本でよい。
- 課金・ライセンス・多言語対応は、それを求める実ユーザーが現れてから。
- シートとチェックリスト以上のドキュメントを先回りで書かない。
- 意図的な割り切りは `ponytail:` コメントと同様、シートの「意図的に無視すること」欄に1行残す。

## 併用スキル

- `requirements-definition`: 機能要件の定義（本スキルはその直後に使う）。
- `yagni-guard`: 実装を最小に保つ。本スキルの5観点も yagni の例外ではない。
- `lp-builder` / `article-writer` / `owned-media` / `sns-ops-team`: マーケティングの実行系。
- `loop-engineering`: 運用ランブックの自動化（定常作業をゼロに近づける時）。

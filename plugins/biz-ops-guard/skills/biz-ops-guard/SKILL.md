# Biz-Ops Guard（プロダクト成立性の設計）

目的は **「動くもの」を「使われ続けるプロダクト」として成立させる**こと。
大原則: **実装は、実在の誰かが欲しがっている証拠（実シグナル）を得てから始める。** 空想のペルソナ・
自己反証だけで通過できる設計プロセスは、精巧な自己満足を作るだけで現実を防げない。

`requirements-definition`（何を作るか）の後、`yagni-guard`（どう小さく作るか）の前に挟む。

## 発動条件

- 他人に使ってもらう前提のアプリ・スキル・ツールを設計する時。
- 要件定義が終わり、実装に入る前。
- リリース・公開・配布の直前。
- 既存プロダクトが「使われない」「保守がつらい」「差別化できてない」と感じた時。
- ユーザーが「ビジネス面」「プロダクトとして」「運用面」と言った時。

## 適用範囲の判定（最初にやる）

| 対象 | 適用 |
|---|---|
| 自分専用ツール（他人が使わない） | **適用しない**。`yagni-guard` だけでよい。 |
| 他人にも使ってほしいスキル・アプリ | **full**。以下すべてを適用。 |
| 学習・実績目的（G3）と割り切るもの | 経路は通すが、実シグナルが無くても「意図的に無視」と明示して進んでよい。 |

G3 = このリポジトリの目的タグ「就活で話せる実績・学びを作る」（`docs/skill-requirements.md`）。本スキル内では「使われなくても学習・実績目的で作る」の意。

## 経路選択（実装前に、この1問で決める）

**コア価値1つだけの動くデモを半日以内に作れるか？**

```
Yes → ファストパス:
  デモを作る → 実在の3人に送る → 反応を実シグナルとして記録
  → シートは事後に埋める（後追い記入を正式に許可する）

No（半日超の建造物）→ 設計先行パス:
  シートを埋める → 悪魔の代弁者（ピッチ磨き）→ 一言ピッチを実在の3人に送る
  → 実シグナルを得てから実装開始
```

**実シグナルの定義**（いずれか1件以上。空想ペルソナやAgentによる自己反証は代替にならない）:

- 実在の人からの「使いたい/試したい」の返信
- 事前登録・予約
- デモの実使用（アクセスログ等で確認できるもの）

**依頼者・開発者本人からの反応は実シグナルに数えない。** 家族・同僚・身内の合意を実シグナルと混同すると
ゲート自体が形骸化する。シートの実シグナル欄には「誰から」に加え、依頼者との関係性
（利害関係なしの第三者か／同僚か／家族か）を1語添える。

シグナルが得られない場合は、①ピッチを変えて再送（最大2回）②「学習目的（G3）」と明記して進む
③作らない、のいずれか。**実シグナルが無いまま暗黙に実装へ進むのが唯一の禁止事項。**

実装済み・公開直前に初めて本スキルを適用する場合は、シートを遡って埋め、実シグナルの有無を
今から確認する（無ければ①〜③のいずれかを選ぶ）。

## 成果物: ビジネス運用面シート

full 適用時はこの1枚を埋める（プロダクトの `docs/biz-ops.md`、スキルなら SKILL.md 冒頭または同ディレクトリに置く）。**全項目1〜2行。1ページを超えたら書きすぎ。**上から順に埋まるかどうかがそのまま Go/No-Go 判定になる。

```markdown
# <product> ビジネス運用面シート
- 価値提案: （誰）が（既存手段）せずに（成果）できる
- 実在ユーザー3人（属性+痛み+使う場面。実名は書かない）:
- 実シグナル（誰から・関係性/何を/日付。依頼者本人は不可）:
- 導入: 手順数 __ / 所要 __分 / 前提条件:
- 保守運用: 週__分 / 壊れる要因: / 失敗通知経路: / 廃止基準:
- 配布: チャネル / 最初の10人 / 到達期限 公開後__週:
- 収益/回収: 誰がいくら払うか。無料なら何で回収するか（実績・リード・学習）
- 指標: 新規 / 7日内再利用 / 紹介
- 意図的に無視すること:
- 悪魔の代弁者: 指摘→処理:
```

記入例: [examples/sheet-example.md](examples/sheet-example.md)（書き味と粒度の基準にする）。

- 実シグナル欄が空のまま実装に進まない（唯一の禁止事項の実体化）。
- 「意図的に無視すること」欄には無視すると決めた項目だけを書く（仮置き中の項目と混ぜない）。
- 公開リポジトリに置くシートと調査クエリ本文には実名を書かない（イニシャル・属性で代替。実名版は手元メモでよい）。relayへの送信・シートのコミット前に、悪魔の代弁者欄・意図的に無視すること欄を含む自由記述欄を一度目視で読み返す（実名・メールアドレス等の機微情報混入はテンプレ欄より自由記述欄で起きやすい）。

### 収益検証（軽量な支払い意思確認）

有料化を検討する場合、決済実装より先に軽量な検証を1つ選ぶ: スモークテスト（先行予約ページのみ作りクリック/登録を計測）／既存コミュニティでの1on1ヒアリング／行動プロキシ（紹介依頼など一手間を課し熱量を測る）。開発者・エンジニア向けツールは「自分で作れてしまう層」が対象になりやすく、有料化が特に難しい点に注意。

## 悪魔の代弁者（ピッチを送る前の5分レビュー）

シートやピッチを書いた本人（Claude含む）は楽観に寄る。ピッチを実在の3人に送る**前**に、
**別コンテキストの Agent 1体**に「想定ユーザーがこれを使わない理由・乗り換えない理由」を3つ挙げさせる。
1文で反論できない指摘は、シートを直すか「意図的に無視すること」に移す。指摘と処理はシートの
「悪魔の代弁者」欄に残す。これは実シグナルの代替ではなく、実シグナルを取りに行く前の研磨工程。
Agent が使えない環境では翌日の自分で代替してよい。

## 3つの観点の設計原則

導入・保守・運用・マーケティング・差別化の5要素を、個人開発で実際に問うべき3つの問いに束ねたもの。元の語彙は検索性のため description に残している。

### ①選ばれる理由（差別化＋価値提案）

- **代替の列挙が先**。競合は同種アプリだけでなく「手作業・Excel・既存SaaS・ChatGPTに直接聞く」を必ず含める。
- 乗り換え理由は**1点に絞る**。10%良い10項目より、10倍良い1項目。持続的優位の源泉（自分だけのデータ／運用ノウハウ／組み合わせ／ニッチ特化）を1つ特定する。機能自体は模倣されるものと考える。
- **一文価値提案**を先に固める: 「（誰）が（既存手段）せずに（成果）できる」。これが書けない機能は作らない。
- **検索性**: ユーザーが検索する語を名前と description に入れる（かっこいい造語より検索される平凡な語）。
- 差別化が1つも無いなら: 作らない、または「学習目的（G3）」とシートに明示して割り切る。

### ②始めやすさ（導入）

- **Time-to-First-Value ≤ 5分・3ステップ**。初回の価値体験までの手順数を設計段階で数える。
- 前提条件（APIキー・課金・環境・アカウント）は README/SKILL.md の**先頭に表で明示**。
- **デフォルトで動く**（zero-config first）。前提未設定のまま起動された時、無言で失敗させず何が足りないか自分で言わせる。
- **出口も書く**（アンインストール手順・データの持ち出し方）。出口が見えると導入の心理障壁が下がる。

### ③続けられる構造（保守・運用・配布継続）

- **3ヶ月放置テスト**: 自分が3ヶ月触らなくても動くか。外部依存ごとに「壊れたら何が起きる／どう気づく／代替は何か」を1行ずつ書く。
- **保守予算を宣言**: 週N分まで。2回連続で超過したら縮小・凍結・廃止を判断する。バージョニング（semver）と CHANGELOG。フィードバック窓口を1つだけ決める。
- **ランブック**: 定常運用で人間がやる作業を全部列挙する。理想はゼロ。**静かに壊れない**（失敗が届く経路を1つ用意する）。ユーザー1人・利用1回あたりの限界費用を見積もる。期待値（保証範囲）を明示する。
- **配布は継続が前提**。ローンチは1回のイベントではなく更新のたびに繰り返す。数週間反応が無いのを「需要が無い」と早合点しない（尚早な断念は個人開発の典型的な失敗要因。プロダクトの欠陥と配布不足を混同しない）。定期レビューで判断するまでは続ける。記事化は `article-writer`、X運用は `sns-ops-team` に委譲。

## 設計時のリサーチ

シートを埋めるための調査は、CLAUDE.md の調査ルーティングに従い **hermes-relay 経由の Hermes Agent
1本**（x_search + web_search）で実行する（手順は `plugins/hermes-x-search/skills/hermes-x-search/SKILL.md`
が正。NotebookLM は廃止済みで `engine:` ヘッダは書かない）:

- 競合・代替手段・記事調査 → ヘッダなしのまま、プロンプト冒頭で「web_search を使って調べてください。x_search は使わないでください。回答末尾に使用ツール名を列挙してください」と誘導する。
- X 上の需要・不満・「今どう解決しているか」の生の声 → ヘッダなし（デフォルトで x_search）。
- **捏造ガード**: 取得成功したソースの内容だけ書かせ、失敗時は「取得失敗」とだけ書かせる。結果の使用ツール自己申告と本文を突き合わせ、失敗報告なのに引用があれば捏造とみなし破棄する。
- 特定URLの本文抽出（web_extract）は search-only バックエンドのため不可。必要ならユーザーにページ内容の貼り付けを依頼する。

調べるのは3点だけ。それ以上の市場調査はやりすぎ:

1. **代替手段の実在**: 想定ユーザーが今それを何で解決しているか。
2. **不満の種**: 既存手段への不満・つまずき（乗り換え理由の候補）。
3. **検索される語**: ユーザーが実際に使う検索キーワード。

結果はシートの該当欄に1〜2行で反映する。調査レポートを別途作らない。調査は原則1往復（最大2往復）。
結果が不十分でも仮置きでシートを埋めて進み、リリース前チェックで見直す。

relay の watcher が長時間詰まっている・エラーが続く等の障害時は、ユーザーの明示的な許可を得たうえで
一時的に Claude 自身の WebSearch に切り替えてよい（根拠URL必須は同じ）。復旧後は relay に戻す。

## 実シグナル獲得後の最初のアクション

実シグナルを得たら（またはファストパスでデモが動いたら）、その場で **README の冒頭10行**
（一文価値提案・デモ枠・導入3ステップ）をドラフトしてから実装に入る。シートの内容が10行に
変換できないなら、シートの側が曖昧な証拠なので書き直す。

## リリース前チェックリスト

- [ ] 実シグナルを得た（または「意図的に無視すること」に明記した）
- [ ] 前提条件が README/SKILL.md の先頭に表である
- [ ] クリーン環境で導入手順どおりに入れて5分以内に価値が出る（Claude が新規ディレクトリ等で再現、不可ならユーザーに依頼。未実施ならチェックを空欄のまま残す）
- [ ] README 冒頭10行で価値提案＋デモが伝わる
- [ ] 前提未設定で起動した時のエラーが自己説明的である
- [ ] CHANGELOG / version がある
- [ ] フィードバック窓口が1つ明記されている
- [ ] 失敗の通知経路がある（自動実行系のみ）
- [ ] 期待値（保証範囲）が書いてある
- [ ] ビジネス運用面シートが埋まっている
- [ ] 悪魔の代弁者チェックを実施し、指摘を処理した

## 定期レビュー（月1、5分）

見る指標は3つで足りる: **①新規に触った人数 ②7日以内にもう一度使った人数（再利用） ③他人に薦めた・紹介された数**。分析基盤は不要（ホスティング標準ログ・手動カウントでよい）。この3つを見て4択で判断する: **改善 / 現状維持 / 凍結 / 廃止**。

- 保守予算の2回連続超過、またはユーザー0が2ヶ月 → 凍結か廃止を必ず検討する。
- 凍結・廃止は失敗ではなく成果。学び（なぜ使われなかったか）をシートに追記して閉じる（G3の素材になる）。

## やりすぎ防止（yagni-guard との整合）

ビジネス運用面の整備自体も過剰設計しない。

- ユーザー10人未満で監視ダッシュボード・分析基盤・自動リリースパイプラインを作らない。通知はメール/Slack 1本でよい。
- 課金・ライセンス・多言語対応は、それを求める実ユーザーが現れてから。
- シートとチェックリスト以上のドキュメントを先回りで書かない。
- 意図的な割り切りは `ponytail:` コメントと同様、シートの「意図的に無視すること」欄に1行残す。

## 併用スキル

- `requirements-definition`: 機能要件の定義（本スキルはその直後に使う）。
- `yagni-guard`: 実装を最小に保つ。3つの観点も yagni の例外ではない。
- `lp-builder` / `article-writer` / `owned-media` / `sns-ops-team`: マーケティングの実行系。
- `loop-engineering`: 運用ランブックの自動化（定常作業をゼロに近づける時）。
- `product-viability-guard`: 本スキルの英語・依存ゼロ移植版。日本語圏・このリポジトリ固有の運用（G3・hermes-relay）に依存しない相手に薦める時に使う。

## v2.0.0 での破壊的変更（移行メモ）

- Go/No-Go ラダーを廃止し、ビジネス運用面シートに統合した（実シグナル欄が実質的な後継）。
- 実装開始の必須条件が「ラダー通過」から「実在ユーザーの実シグナル1件（依頼者本人は不可）」に変わった。
- 5観点（導入・保守・運用・マーケティング・差別化）を3観点（選ばれる理由・始めやすさ・続けられる構造）に統合した（内容は全て移設、削除なし）。
- 悪魔の代弁者の位置づけが「シート完成後の独立ゲート」から「ピッチ送信前の研磨工程」に変わった。
- 詳細な設計根拠は `docs/biz-ops-guard-v2-design.md` を参照。
- **既存の v1系シート**（旧5観点の見出しで書かれた `biz-ops.md`）は次回そのプロダクトを触るタイミングで
  v2形式（3観点・実シグナル欄）に書き直す。リリース時点でリポジトリ内に存在する v1系シートは
  `plugins/biz-ops-guard/docs/biz-ops.md`（本スキル自身、今回同時に v2 形式で新規作成）のみ確認済み。

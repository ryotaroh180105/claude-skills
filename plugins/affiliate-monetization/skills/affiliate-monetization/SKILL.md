# Affiliate Monetization — 収益化ファネルの設計と週次運用

目的タグは **G2（副業で稼ぐ）**。sns-ops-team（企画・執筆）・sns-auto-posting（X投稿）・
article-writer（note記事）は「作る」「投稿する」を担うが、**収益にする**部分（ジャンル選定・
リンク管理・PR表記・計測・撤退判断）を持たない。本スキルがその構造を担う。

事業構造:

```
[集客] X ポスト（sns-ops-team 制作 → sns-auto-posting 投稿）
   │  プロフィール固定リンク + ポスト内 note リンク
   ▼
[受け皿] note 無料記事（article-writer 制作。冒頭に PR 表記）
   │  記事内アフィリエイトリンク（link-registry で採番）
   ▼
[収益点] ASP 成果報酬（Amazon アソシエイト / A8.net / もしもアフィリエイト から審査が通ったもの1社）
   ▼
[計測] 週次で kpi-log.md に転記 → 判断表で継続/調整/縮小/撤退
```

Phase 1（現在の唯一の対象）は **X × AI/IT ツール紹介ジャンル × note無料記事 × ASP1社** に固定する。
理由: X は sns-auto-posting で投稿実装済み・note は article-writer が制作可能・AI/ITツールは
「①自分が一次体験を書ける ②購買行動につながる検索・比較需要が既知 ③YMYL（医療・金融・法律）でない」
の3条件を満たす。Phase 2（有料記事・ASP2社目・Threads）は Phase 1 で確定件数が1以上になってから、
Phase 3（TikTok動画）は Phase 2 の月間確定額が制作コストを正当化すると判断されてから着手する。
それ以前にジャンルやプラットフォームを増やさない（§8 失敗シナリオ2の対策）。

## いつ発動するか / しないか

- 発動: 収益化構造の初回セットアップ、週次KPIレビュー、記事へのアフィリンク挿入相談、
  PR表記の要否確認、撤退判断の相談。
- **発動しない**: アフィリエイトリンクを含まない通常のnote記事の依頼 → article-writerに委譲する。
  「この記事にはアフィリエイトリンクを入れる予定ですか」と一言確認し、Noならarticle-writerの
  通常フローに戻す。

## Step 0: 初回セットアップのヒアリング（5問）

`monetization/<ジャンル>/` 配下にファイルがまだ無い場合、funnel-config.md を生成する前に
次の5問を確認する（未回答のまま生成しない）。

1. どのジャンルで発信するか。選定根拠（自分が一次体験を書けるか／検索・購買需要があるか／
   YMYL領域でないか）を一緒に確認する。Phase 1では1ジャンルのみ。
2. 集客に使うXアカウントはどれか（既存 `sns/<アカウント名>/` のいずれか、または新規）。
3. note受け皿の有無（アカウント開設済みか。未開設ならユーザーが開設する必要がある旨を伝える）。
4. 収益点となるASP（Amazon アソシエイト / A8.net / もしもアフィリエイト）と審査状況
   （申請済み・審査中・未申請・通過日）。未通過の場合は§7「ASP審査に落ちた/未申請」の挙動に従う。
5. 週次作業予算と撤退基準の初期値（120分・12週・24週）をそのまま使うか、変更するか。

回答が揃ったら `funnel-config.md`（templates/funnel-config.md をコピー）を
`monetization/<ジャンル>/funnel-config.md` として生成し、PR表記文言を確定記入する
（削除は拒否。変更のみ可 — 法令面の必須要素のため）。

## データ契約（3ファイル）

運用データはリポジトリ外の作業ディレクトリ `monetization/<ジャンル>/` に、
`templates/` の3ファイルをコピーして作る（sns-ops-team の `sns/<アカウント名>/` と同じ方式）。
リポジトリには実リンク・実収益を置かない（公開リポジトリのため）。

### funnel-config.md（ジャンルごとに1枚）

ジャンル・Phase・集客/受け皿/収益点・PR表記文言（2種）・週次作業予算・撤退基準（KPI判断表を転記）
を保持する。テンプレート: `templates/funnel-config.md`。

### link-registry.md（リンク台帳。1リンク1行）

列: `link_id`（L+3桁連番） / `ASP` / `商品・サービス名` / `リンクURL` / `貼付先`
（note記事URL/投稿id） / `登録日` / `状態`。状態は `active` / `broken`（リンク切れ検知） /
`retired`（案件終了）の3値のみ。テンプレート: `templates/link-registry.md`。
ASP審査が未通過の間は `pending` 行を作らない（通過後に登録する。§7）。

### kpi-log.md（週次1行。数値はユーザーが転記）

列: `週` / `投稿数` / `note誘導クリック` / `note PV` / `リンククリック` / `発生件数` /
`確定件数` / `確定額(円)` / `作業分` / `判断`。テンプレート: `templates/kpi-log.md`。

- note誘導クリック = Xアナリティクスのリンククリック数。note PV = noteダッシュボード。
- リンククリック / 発生 / 確定 = ASP管理画面。判断 = 下記KPI判断表の結果。

## 週次バッチ（Phase 1 の定常運用）

1. **入力**: funnel-config.md + `sns/<アカウント>/sns-strategy.md` → **処理**: 今週のnote記事1本の
   テーマとX誘導ポスト案をsns-ops-teamの週次バッチに乗せる（企画指示に「note記事URLへの誘導を
   CTAにする」を追加するだけ。sns-ops-teamの工程は変更しない）→ **出力**: post-queue.mdのdraft行
2. **入力**: 記事テーマ + link-registry.md → **処理**: article-writerでnote記事を制作。本スキルは
   (a) 冒頭PR表記文言（funnel-configの確定文）(b) 挿入するリンク（link_id指定）
   (c) リンク挿入位置=「商品の評価を述べたセクションの直後」を article-writer への指示に含める
   → **出力**: 完成原稿（noteへは手動投稿。article-writerの契約どおり）
3. **入力**: 公開済みnote記事URL → **処理**: link-registry.mdの貼付先列を更新。post-queue.mdの
   該当draftをユーザーがapprove → sns-auto-postingが投稿 → **出力**: 投稿完了
4. **入力**: ユーザーが転記する実績数値（Xアナリティクス/noteダッシュボード/ASP管理画面）
   → **処理**: kpi-log.mdに1行追記し下記KPI判断表を適用 → **出力**: 判断（継続/調整/縮小/撤退検討/撤退）と根拠1〜3行

## KPI判断表（確定。数値は初期値であり、4週ごとのレビューで改訂可 — 改訂はkpi-log.md末尾に日付つきで記録）

週次で見るのはkpi-log.mdの9列。判断は**上から順に最初に該当した行**を適用する。

| 条件 | 判断 |
|---|---|
| 作業分が2週連続で 120 を超過 | **縮小**（投稿数を減らす。それでも超過なら撤退検討） |
| 直近4週の note誘導クリック合計 < 10 | **調整**（集客側の問題。ポストのCTA・テーマをsns-ops-teamの振り返りで変更） |
| 直近4週の note誘導クリック合計 ≥ 10 かつ リンククリック合計 = 0 | **調整**（記事側の問題。リンク位置・商品選定を変更） |
| 開始から12週経過で 発生件数累計 = 0 | **撤退検討**（ジャンルまたは受け皿を変えて再スタートするか、凍結するかをユーザーに提示。惰性で13週目に入らない） |
| 開始から24週経過で 確定額累計 = 0円 | **撤退**（Phase 1構造を凍結し、学びをbiz-ops-guardの定期レビュー形式でシートに追記して閉じる） |
| 上記いずれにも該当しない | **継続** |

数値（10クリック/12週/24週/120分）は実装判断としては固定値。実装時に変えず、
運用4週ごとのレビューでユーザーが改訂する場合のみ変更し、改訂記録はkpi-log.md末尾に残す。

## 既存スキルとの役割分担（契約。重複実装禁止）

| 工程 | 担当 | 本スキルとのインターフェース |
|---|---|---|
| 投稿の企画・執筆・レビュー | sns-ops-team | 企画指示に「note誘導CTA」を追加。post-queue.mdの書式は変更しない |
| Xへの投稿実行 | sns-auto-posting | approved行の投稿。本スキルはステータスを触らない |
| note記事の制作 | article-writer | PR表記文言・link_id・挿入位置を指示として渡す |
| SEO記事（検索流入） | owned-media | Phase 1では使わない（noteはSNS流入前提）。Phase 2以降の検討事項 |
| 成立性の定期レビュー | biz-ops-guard | 月1レビューの3指標はkpi-log.mdの列で代替（下記biz-ops節） |
| 本スキル | affiliate-monetization | ジャンル選定・ファネル定義・リンク台帳・PR表記の強制・週次判断 |

しないこと（既存スキルの書式変更禁止）: sns-ops-team / article-writer のSKILL.mdは修正しない。
接続は必ず「指示に文言を追加する」側（本スキル側）で吸収する。投稿実行機能・記事執筆機能の
再実装もしない（それぞれsns-auto-posting / article-writerの担当）。

## エッジケース

| ケース | 期待挙動 |
|---|---|
| ASP審査に落ちた/未申請 | 収益点なしでは開始しない。別ASPの申請を案内し、それまでは記事制作のみ先行してよい（リンクは後挿入。link-registryに`pending`行は作らない — 通過後に登録） |
| PR表記のないアフィリエイトリンク入り記事・投稿 | 公開NG。funnel-configの確定文言を挿入した修正版を提示。景表法ステマ規制（2023-10施行）対応。規制運用の最新状況は断定せず、判断に迷うグレー事例は「要人間確認」と明示する（sns-ops-teamレビュー工程④と同じ倒し方） |
| Xにアフィリエイトリンクを直貼りしたいと言われた | Phase 1の構造（Xはnote誘導のみ）から外れる旨と、Xのアフィリエイトリンク・外部リンクの規約は変動が大きく「実装時に最新規約を確認（hermes-relay）」が必要な旨を伝え、直貼りする場合は先頭【PR】表記を必須にする |
| link-registryのリンク切れ（週次レビューの目視確認で発見） | 状態を`broken`に変更し、該当note記事の修正（リンク差し替えまたは削除）を最優先タスクとして提示 |
| KPI数値が転記されない週 | 該当列を`-`で記録し判断は「保留」。2週連続で`-`なら、計測なしの運用は撤退基準を無効化するため、運用継続の意思をユーザーに確認する |
| note側のアフィリエイトリンク可否 | 実装時にnoteの最新規約をhermes-relayで確認してからfunnel-configを確定する（可否を断定しない） |
| YMYL領域（金融・医療・健康）の高報酬案件を勧められた/やりたいと言われた | ジャンル選定基準③（YMYLでない）に反するためPhase 1では扱わない。理由（E-E-A-T要求と法規制リスク）を伝える |
| 収益見込み・報酬率を聞かれた | 断定しない。「要調査」とし hermes-relay（engine: notebooklm + topic）で調査するクエリ案を提示する |
| 巨大化したkpi-log.md | 52行（1年）を超えたら年別アーカイブ（kpi-log-YYYY.md）を提案 |

## 実装時判断ルール（数値・規約を扱うときの原則）

- 数値（報酬率・料率・審査日数）を書きたくなったら: 断定せず「要調査」と書き、
  hermes-relayのクエリ案（engine: notebooklm + topic付き）を提示する。調査結果にも「調査日」を併記する。
- 規約の記述: 「X/note/ASPの規約では〜」と断定形で書かない。「YYYY-MM時点の調査では〜。
  運用開始時に再確認」の形式に統一する。
- 判断表の数値（10クリック/12週/24週/120分）を変えたくなったら: 実装時は変えない。
  運用4週ごとのレビューでユーザーが改訂する（改訂記録はkpi-log.md末尾）。
- sns-ops-team / article-writerのSKILL.mdを修正したくなったら: しない。接続はすべて
  「指示に文言を追加する」側（本スキル側）で吸収する。
- PR表記の文言: funnel-configの2文言を初期値とする。ユーザーが変更を求めたら変更してよいが、
  削除は拒否する（法令面の必須要素）。
- 実リンク・実収益データの置き場に迷ったら: リポジトリ外の作業ディレクトリ。リポジトリにコミットしない。
- 書かれていない判断はユーザーに確認する。

## biz-ops-guard 適用（Go/No-Goラダー・ビジネス運用面シート）

対象は「発信者本人の収益化構造」で、直接のユーザーは本人1人。ただしbiz-ops-guardの趣旨に従い、
**プロダクト＝発信コンテンツ、ユーザー＝読者**と読み替えて適用する。

**Go/No-Goラダー回答:**

1. 想定ユーザー3人: ①AIツールを業務導入したい非エンジニアの会社員 ②副業目的でAIツール比較を
   検索する20代 ③発信者自身（過去に欲しかった記事を書く）。→ Yes
2. 乗り換え理由1文: 「公式ドキュメントや企業メディアを読み比べずに、実務で使った当事者の選定理由と
   失敗込みの評価が1記事で分かる」。代替＝公式Doc・企業比較メディア・ChatGPTに直接聞く。→ Yes
3. 導入5分・3ステップ: 読者側はXで見てnoteを読むだけ（0ステップ）。運用者側は
   ①スキル導入②ヒアリング5問③funnel-config生成、で15分。運用者側は5分超だが初回のみと割り切り
   「意図的に無視」。
4. 保守上限: 週120分（コンテンツ制作込み。funnel-configに宣言）。→ Yes
5. 最初の10ユーザーへの経路: 既存Xアカウント（sns-ops-team運用中）からの誘導。→ Yes

**ビジネス運用面シート:**

| 観点 | 内容 |
|---|---|
| 一文価値提案 | AI/ITツール導入検討者が、比較メディアの読み比べをせずに、実務者の本音評価1記事で選定できる |
| 想定ユーザー（3人） | 上記ラダー1のとおり |
| 代替手段と乗り換え理由 | 企業比較メディア → 実務の一次体験（失敗込み）があること |
| 導入 | 読者0ステップ / 運用者3ステップ・15分 / 前提条件: ASP審査通過・X/noteアカウント |
| 保守 | 予算 週120分 / 壊れる要因: ASP案件終了によるリンク切れ・Xの外部リンク仕様変更・ステマ規制の運用強化 / 廃止基準: 上記KPI判断表の撤退基準 |
| 運用 | 定常作業: 週次バッチ（制作〜転記〜判断）120分 / 失敗通知経路: 週次レビュー時にlink-registryのURLを目視確認（自動監視は作らない） / 1利用あたりコスト: 0円（API課金なし） |
| 配布チャネルと最初の10ユーザー | 既存Xアカウント（到達期限: 公開後2週） |
| 収益/回収 | 読者は無料。ASP成果報酬で回収。報酬水準は断定しない（要調査: hermes-relay） |
| 記録する指標 | kpi-log.mdの9列（新規=note誘導クリック、再利用=note PV、紹介=発生件数に対応） |
| 意図的に無視すること | 運用者側導入の5分超過（初回のみ）／Instagram・Threads・TikTok（Phase 1では対象外）／ASP API連携 |

**悪魔の代弁者（実装時再実施）:**

1. 「読者0ステップ」は言い過ぎではないか — Xのリーチ抑制が実際に強い場合、noteに辿り着く前に
   離脱する読者が大半になり、想定ユーザー3人への到達自体が成立しない可能性がある。
   → 対策: X→note誘導クリック数を最初の4週で最重要指標として扱い（KPI判断表の2番目の行）、
   ここが弱ければジャンルより先に導線・CTA自体を疑う。
2. 「週120分」は制作コストの見積もりが甘く、実際はレビュー・PR表記チェック・リンク切れ確認まで
   含めると超過しやすいのではないか。→ 対策: 作業分の超過を2週連続で検知したら即座に
   「縮小」を最優先の判断（判断表の1番目の行）にし、継続判断より先に発動するよう順序を固定した。
3. 発生件数・確定額が0のまま「継続」判定が続くリスクは撤退基準（12週/24週）で対処済みだが、
   基準到達前に本人が飽きて更新頻度が落ちる「静かな撤退」を判断表は検知できない。
   → 対策: 週次バッチの出力に必ず判断（継続/調整/縮小/撤退検討/撤退）を含めることを完成条件化し
   （§週次バッチ4番目の工程）、kpi-log.mdへの記入自体が途絶えた場合は「KPI数値が転記されない週」
   のエッジケース（2週連続`-`で継続意思確認）で拾う。

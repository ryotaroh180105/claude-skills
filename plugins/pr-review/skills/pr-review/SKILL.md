# PR Review

GitHub の Pull Request をレビューする実行スキル。PR 情報の取得、コンテキストを踏まえた
レビュー、下書きの提示、ユーザー承認後のコメント投稿までを一連のワークフローで行う。

**役割分担**: 「何を見るか（観点チェックリスト・ADR 判断）」は `code-review-adr` スキルが持つ。
本スキルは「GitHub の PR をどう取得し、どうレビュー結果を届けるか」の手順に特化する。
`code-review-adr` が利用可能ならその観点リストを必ず読み込んで使い、なければ本スキル末尾の
最小観点セットで代替する。

## このスキルを使う場面

- PR の URL / 番号を渡されて「レビューして」と依頼されたとき
- 自分が作った PR を投稿前にセルフレビューしたいとき
- CI が落ちている PR について、失敗原因の調査込みでレビューしたいとき
- レビュー結果を GitHub 上にコメントとして投稿したいとき

ローカルの未コミット差分やコミット済みブランチのレビュー（PR がまだ無い場合）は
`code-review-adr` を直接使う。

## 前提セットアップ

| 依存 | 必須/任意 | 未設定時の挙動 |
|---|---|---|
| GitHub MCP サーバー | 必須（推奨） | 接続を案内し、代替として下記「MCP なしの縮退手順」を使う |
| 対象リポジトリへの読み取り権限 | 必須 | 取得エラーになったらユーザーに権限/URL を確認する |
| コメント投稿権限 | 投稿時のみ | 投稿に失敗したら下書きを Markdown で渡して手動投稿してもらう |

GitHub MCP が未接続の場合は、まず「GitHub MCP サーバーを接続すると PR への直接コメント
投稿までできます」と案内したうえで、縮退手順（後述）でレビュー自体は続行する。

## ワークフロー

### Step 1: PR 情報の取得

`mcp__github__pull_request_read` を method を変えて呼び、以下を揃える。

| 取得内容 | 呼び出し |
|---|---|
| 概要（タイトル/本文/state/draft/mergeable/base/head） | `method: "get"` |
| diff 全体 | `method: "get_diff"` |
| 変更ファイル一覧（追加/削除行数つき） | `method: "get_files"` |
| CI・チェックの状態 | `method: "get_status"` |
| 既存のレビュー（approve/request changes 履歴） | `method: "get_reviews"` |
| 既存の行コメント | `method: "get_review_comments"` |

- **取得順序**: 最初に `get` と `get_files` を見る。変更ファイルが 20 を超える場合は
  `get_diff`（全体 diff）を呼ばず、後述「巨大 PR の扱い」に従ってファイル単位で読む。
- URL を渡されたら owner / repo / pullNumber に分解する。番号だけ渡されて
  リポジトリが不明なら、カレントリポジトリの `git remote get-url origin` から推定し、
  推定結果をユーザーに一言確認する。
- CI が失敗していたら `mcp__github__get_job_logs`（`failed_only: true`）で失敗ログを取得し、
  失敗原因が PR の変更に起因するかを判断材料に含める。

### Step 2: コンテキストの取得（diff だけでレビューしない）

diff は変更の断片でしかない。指摘の精度はここで決まるので省略しない。

- 変更された関数・クラスの**呼び出し元/呼び出し先**、変更されたインターフェースの実装側など、
  diff に現れない関連ファイルを読む。ローカルに同じリポジトリがあれば直接 Read し、
  なければ `mcp__github__get_file_contents`（`ref` に head ブランチを指定）で取得する。
- 変更に対応するテストの有無を確認する（テストが変更されていない挙動変更は指摘候補）。
- PR 本文・リンクされた Issue を読み、「この PR が解こうとしている問題」を把握してから
  コードを読む。

### Step 3: レビュー実施

`code-review-adr` スキルの観点チェックリスト（正しさ/可読性/セキュリティ/性能）に沿って
レビューする。指摘には必ず重要度ラベルを付ける。

| ラベル | 意味 | 判定への影響 |
|---|---|---|
| `[must]` | バグ・セキュリティ・データ破壊など、マージ前に修正必須 | 1件でもあれば request changes 推奨 |
| `[should]` | 修正を強く推奨するが、判断は作者に委ねる | comment 推奨（内容次第で request changes） |
| `[nits]` | 好みの範囲・軽微な改善。対応任意 | 判定に影響しない |

各指摘は「該当ファイル:行 + 問題点 + 根拠 + 修正案（可能なら具体的なコード）」の形にする。
良い点も最低1つ拾う（何も見つからないときは無理に書かない）。

### Step 4: 下書き提示 → 承認 → 投稿

**レビュー結果をいきなり GitHub に投稿しない。** まず下書き（後述のサマリーフォーマット +
行コメント案の一覧）をユーザーに提示し、次のどれにするか確認する:

1. **このまま投稿**（判定: approve / request changes / comment も確認）
2. **修正してから投稿**（修正内容を聞いて下書きを直す）
3. **投稿せず下書きのまま受け取る**（セルフレビューや、口頭で伝えたい場合）

承認を得たら次の 3 ステップで投稿する:

```
1. mcp__github__pull_request_review_write  (method: "create")
   → pending review を作成
2. mcp__github__add_comment_to_pending_review
   → 行コメントを1件ずつ追加（path, line, side を diff から正確に指定）
3. mcp__github__pull_request_review_write  (method: "submit_pending",
   event: "APPROVE" | "REQUEST_CHANGES" | "COMMENT", body: サマリー)
   → レビューを確定
```

- 自分自身の PR には GitHub 仕様上 APPROVE / REQUEST_CHANGES できないため、
  セルフレビュー投稿時は `event: "COMMENT"` を使う。
- 途中で失敗したら pending review が残ることがある。同じ pending に追記して submit すれば
  よく、作り直す場合はその旨をユーザーに伝える。

## サマリーフォーマット

```markdown
## レビューサマリー: <PRタイトル> (#<番号>)

**総評**: <1〜3行。PR の目的に対して変更が妥当かの結論>
**推奨判定**: approve / request changes / comment（理由を1行）
**CI**: <passed / failed（失敗時は原因の要約） / 実行中>

### 指摘一覧（重要度順）
1. [must] <ファイル>:<行> — <指摘>（修正案: ...）
2. [should] ...
3. [nits] ...

### 良い点
- <設計・テスト・命名などで評価できる点>
```

## 巨大 PR の扱い（変更ファイル 20 超）

1. `get_files` の一覧を、①ロジック変更・新規追加 ②設定/依存関係の変更 ③自動生成・
   lockfile・フォーマットのみ、の順に優先度分けする。
2. ①②を精読対象とし、③は「機械的変更として斜め読みのみ」と扱う。
3. サマリー冒頭に **「精読したファイル」と「省略した範囲とその理由」を必ず明記**する。
   全体を見たかのような総評を書かない。
4. 可能なら「PR 分割の提案」自体を [should] 指摘として含める。

## エッジケースの扱い

| 状況 | 挙動 |
|---|---|
| Draft PR | 方向性・設計へのフィードバック中心。判定は原則 comment とし、REQUEST_CHANGES は付けない（nits の細かい指摘は控えめに） |
| コンフリクト中（mergeable: false） | レビューは通常どおり行うが、サマリー冒頭で「base とコンフリクトしており、解消後に diff が変わる可能性がある」と明記する |
| レビュー済み PR への再依頼 | `get_reviews` / `get_review_comments` で既存指摘を読み、①既存指摘が解決されたかの確認 ②前回レビュー以降の新規コミットの差分、の2点に絞る。解決済みの指摘を蒸し返さない |
| CI 失敗中 | 失敗ログを調査し、PR 起因なら [must] 指摘に含める。PR と無関係な flaky / インフラ起因ならその旨を書き、判定の理由から除外する |
| すでにマージ/クローズ済み | レビューの目的（振り返り? 学習?）を確認してから進める。投稿は原則しない |

## MCP なしの縮退手順（git fetch + ローカル diff）

GitHub MCP が使えない環境では、ローカル clone 上で以下を行う:

```bash
git fetch origin pull/<N>/head:pr-<N>     # PR の head を取得
git fetch origin <base-branch>            # base を最新化
git diff origin/<base-branch>...pr-<N>    # 三点差分で PR 相当の diff を得る
git diff --stat origin/<base-branch>...pr-<N>   # 変更ファイル一覧
```

- コンテキスト取得は `git switch pr-<N>`（または worktree）でチェックアウトして行う。
- CI 状態・既存レビューコメントは取得できないため、「CI と既存レビューは未確認」と
  サマリーに明記する。`gh` CLI が使えるなら `gh pr view <N>` / `gh pr checks <N>` で補完する。
- コメント投稿はできないので、出力は常に Markdown 下書き（`gh` があれば
  `gh pr review` での投稿をユーザーに提案してもよい）。

## 最小観点セット（code-review-adr が無い場合のみ）

- **正しさ**: 境界値・null/空・エラーパス、変更に対するテストの有無
- **設計**: 変更が既存の責務分割に沿っているか、不要な複雑化がないか
- **セキュリティ**: 入力検証、認可チェック、秘密情報のハードコード
- **性能**: N+1、ループ内 I/O、不要な全件取得

## 注意事項

- **勝手に投稿しない**が最重要ルール。承認前に許されるのは読み取り系ツールのみ。
- 指摘は断定できる根拠があるものだけ [must] にする。確信が持てないものは
  「〜に見えるが意図があれば教えてほしい」と質問形にして [should]/[nits] に落とす。
- レビュー対象リポジトリの CLAUDE.md やコーディング規約があれば、観点より優先して従う。

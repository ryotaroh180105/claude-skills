# structured-task-execution — 完了条件先固定・観測駆動の4フェーズ実行

## 適用範囲

**収束的な問題**（実装すべきものがある程度定まっていて、完了を客観的に検証できるタスク）向け。
バグ修正・機能実装・設定変更・リファクタリング・移行作業など。

**発散的な問題**（何を作るべきかがまだ定まっていない、正解が一つでない企画・アイデア出し）
には不向き。その場合は `requirements-definition` でイシューを固めてから戻ってくる。

## 発動条件

- 「手戻りが多いタスクを整理して進めたい」
- 「完了条件を先に決めてから着手して」
- 明確な仕様変更・バグ修正・移行タスクに着手する直前

## 前提セットアップ

外部依存なし。対象コード/リポジトリへのアクセスがあれば動く。

## 4フェーズ

### Phase 0: 完了条件を先に固定する

着手前に、**検証可能な受け入れ条件**をユーザーと合意する。
「良い感じにする」ではなく「このテストが通る」「このコマンドがエラーなく終わる」
「この画面でこの操作をするとこう表示される」まで具体化する。

曖昧なまま Phase 1 に進まない。合意できない場合は `requirements-definition` の
イシュー特定に戻る。

### Phase 1: 観測する

推測で進めない。実際のコード・ログ・テスト結果・エラーメッセージを読む。
「たぶんこうなっているはず」で設計しない。関連ファイルを Read/Grep で確認してから
次に進む。

### Phase 2: 最もリスクが高い箇所から着手する

タスクを分解したうち、**最も不確実性が高い・失敗したら手戻りが最大の箇所**を
最初に検証する。簡単なところから手をつけて後で難所に驚く、という順序を避ける。
難所が解けなければ、その時点で Phase 0 の完了条件自体を見直す。

### Phase 3: 実装し、Phase 0 と照合して検証する

Phase 2 で検証済みの方針に沿って残りを実装する。完了したら Phase 0 で固定した
受け入れ条件と実際に照合する。照合できない「たぶんできた」は完了と扱わない。

## 出力フォーマット（着手前の合意メモ）

```markdown
## 実行計画: <タスク名>

- 完了条件（Phase 0）: <検証可能な受け入れ条件>
- 観測結果（Phase 1）: <実際に確認した現状。ファイル/ログ/エラーの要点>
- 最初に着手する箇所（Phase 2）: <最も不確実性が高い部分とその理由>
- 実装順序（Phase 3）: <残りの作業を着手順に>
```

## 注意点

- Phase 0 を省略して手を動かし始めるのが最大の手戻り要因。急ぎのタスクでも
  完了条件の一言確認だけは省略しない。
- 完了条件が途中で変わった場合は、その場で Phase 0 に立ち返って再固定する。
  古い完了条件のまま実装を続けない。
- このメソッド自体は特定モデルに依存しない。どのモデルを使うかは `model-switcher` に委譲する。

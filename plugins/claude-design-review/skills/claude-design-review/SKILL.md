# Claude Design Review（AIっぽさ・アクセシビリティ・仕上げの品質ゲート）

目的は **生成したHTML/UIが「いかにもAI生成」に見えないか、使えるか、意図的に見えるか**を
出荷前にチェックすること。本家
[Trystan-SA/claude-design-system-prompt](https://github.com/Trystan-SA/claude-design-system-prompt)
の20章system promptと14個のDesign Skill（accessibility-audit / ai-slop-check /
hierarchy-rhythm-review / polish-pass 他）の要点を、このリポジトリ用に1スキルへ再構成したもの。

## 発動条件

- HTML/CSS/Reactコンポーネント・Artifact・LPなど見た目のあるUIを生成した直後。
- 「デザインをレビューして」「AIっぽくないか見て」「アクセシビリティを確認して」
  「仕上げをチェックして」「polish pass」と言われた時。
- `dataviz` スキルでチャートを作った後の全体UIレビューにも併用可（チャート単体の色・形は
  dataviz 側の判断を優先する）。

## 対象外

- チャート/グラフの配色・形状そのものの設計 → `dataviz` を使う。
- LP制作の企画・構成・見積もりフロー全体 → `lp-builder` を使う。
本スキルは「できあがったUIの品質チェック」専用。

## ワークフロー

1. **対象ファイルを特定する**（HTML/CSS/JSX等）。実際にコードを読む。
2. 下記4観点を**すべて**チェックする（順不同、まとめて1回で見てよい）。
3. 検出した問題を **ブロッカー（アクセシビリティ違反）/ 品質課題（AIっぽさ・崩れた階層）/
   仕上げ提案（軽微）** の3バケットに分類する。
4. ブロッカーと品質課題は直接修正する。仕上げ提案はユーザー判断に委ねてよい。
5. 出力形式（1指摘=1行厳守、`code-review-adr`と同じ重要度タグ方式を踏襲）:
   ```
   [must] <観点タグ> L<行/箇所>: <指摘>。<修正案>。
   [should] ...
   [nits] ...
   ```
   観点タグ: `slop` / `a11y` / `hierarchy` / `rhythm` / `polish`。
   指摘ゼロなら `Clean. Ship.` とだけ出す。

## 観点1: AIっぽさ検査（AI slop）

以下のパターンは「デフォルトAIテンプレート」に見えるため、意図的な理由がない限り避ける。

| パターン | NG例 | 代わりに |
|---|---|---|
| グラデーション | 虹色・3色以上・ネオン同士のグラデ | 同色相内の低コントラスト2ストップ、または単色フラット |
| 絵文字 | 見出し・ボタン・リストに🚀📈✅を装飾で乱用 | ブランドが使う場合か機能的に必要な場合のみ |
| カード | `border-radius:12px; border-left:4px solid #...` を既定カードにする | 薄いシャドウ・全周の細ボーダー・背景コントラストで区別する |
| 色 | 純粋な `#FFFFFF` 背景 + `#000000` 文字 | トーンを落とした白黒（例 `#FAFAFA` / `#1A1A1A`） |
| フォント | Inter/Roboto/Arial/Fraunces等をシステムデフォルトのまま無自覚に使う | ブランド・文脈に合わせて選定したことを明言できるか自問する |
| 余白 | `padding: 7px 15px; margin: 18px; gap: 13px` のような半端な値 | 4px/8pxの倍数スケールに統一する |
| 「エディトリアル風」 | クリーム背景＋セリフ見出し＋斜体アクセント＋テラコッタ/アンバー配色の組み合わせを無自覚に採用 | これも「紫グラデ以前のデフォルト」化しつつある型。使うなら意図を明言する |
| 画像 | 意味のないストック風グラデ背景・アイコンの乱用 | 本物の写真・プロのイラスト、または縞模様+monospaceラベルの正直なプレースホルダー |

## 観点2: アクセシビリティ監査（WCAG AA基準）

- **コントラスト**: 通常文字（18px未満）は4.5:1以上、大きい文字（18px以上太字 or 24px以上）は3:1以上。
- **フォーカスリング**: `outline: none` を代替なしで使わない。キーボードのTab順が論理的で、
  フォーカスリングがコントラスト3:1以上で視認できることを確認する。
- **セマンティックHTML**: ボタンは`<button>`（divで代用しない）、見出し階層を飛ばさない、
  画像に意味のあるalt、フォームは`<label for="">`で紐付ける。ARIAはセマンティックHTMLで
  表現できない場合のみのパッチとして使う。
- **色だけに頼らない**: エラー/成功を色だけで示さない（赤緑の組み合わせに注意）。
- **モーション**: `prefers-reduced-motion` を尊重する。1秒に3回以上の点滅を避ける。
- **フォーム**: エラーメッセージは具体的でフィールドに紐付く。必須表示はテキスト/アイコン+属性の両方。
- **タッチターゲット**: 最低44×44pxを確保する。

## 観点3: 階層・余白・リズムのレビュー

- **階層の3シグナル**: サイズ（大=重要）、色（彩度高=主要、彩度低=補助）、太さ（見出し太字、
  本文レギュラー）。5秒テスト＝「パッと見て何が一番重要かすぐ分かるか」を自問する。
- **余白スケール**: 4pxまたは8pxの倍数のみを使う。ランダムな余白（`margin-bottom:7px`等）は
  「意図のなさ」として即NG。
- **パレット規律**: 使用色が8色を超えていないか確認する（多すぎると散漫に見える）。
- **リズム**: パターンを繰り返してから戦略的に崩す。全セクションが同一構成（単調）でも、
  全セクションがバラバラ（カオス）でもいけない。
- **グリッド整列**: 要素の端が揃っているか、余白の広さが場所によって不揃いでないか確認する。

## 観点4: Polish Pass（出荷前の最終ゲート）

上記3観点に加え、以下も出荷直前に確認する。

- **インタラクション状態**: default / hover / active / disabled / focus / loading の6状態が
  一通り定義されているか。トランジションが唐突でないか。
- **CTA**: 1画面につき明確なプライマリCTAが1つに絞られているか（複数の同格CTAで迷わせない）。
- **文脈の再確認**: 対象の媒体（スライド/ページ/モバイル/ダッシュボード）・配信環境・制約を
  踏まえた上で、まだ未完成の箇所がないか最終確認する。
- 最終サマリーは「検出して直した数」「ユーザー判断が必要な箇所」「対象外にした項目」の
  3点をセットで報告する。

## 出力ポリシー

- 指摘は確信度・重要度が低いものも省略せず報告する（`polish-pass`の方針を踏襲）。ただし
  出力自体は1指摘=1行に凝縮し、水増しした説明文をつけない。
- ブロッカー（アクセシビリティ違反）は説明を省略せず通常の明瞭さで報告する
  （token-saver の Auto-Clarity 例外に準拠）。
- 意図的にNGパターンを採用する場合（例: ブランドがすでに紫グラデを採用している）は
  「意図的採用」と明記してよい。黙って踏襲するのがNG。

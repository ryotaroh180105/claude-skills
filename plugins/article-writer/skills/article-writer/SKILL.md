# Article Writer — note記事の企画・執筆・推敲

note記事を「切り口設計 → タイトル案 → 構成 → 執筆 → 推敲 → 公開設定 → 反応分析」の
7工程で仕上げるスキル。
目的は **G2（副業・発信で稼ぐ）** と **G3（就活で話せる実績づくり）**。

## 工程マップ（「文章を書く仕事」の第一原理分解との対応）

| 第一原理の工程 | このスキルでの担当 |
|---|---|
| 読者理解 | 工程1（想定読者を1人に絞る） |
| テーマ選定 | 工程1（＋テーマ未定時はネタ出し4観点） |
| 一次情報の調査 | 工程1の素材棚卸し（自分の体験・数字・固有名詞を最低3つ列挙） |
| 構成 | 工程3 |
| 表現 | 工程4（文体メモ＋`references/note-quality.md`） |
| 校正 | 工程5（推敲＋AIっぽさチェック） |
| 配信 | 工程6（公開設定・ハッシュタグ・告知文。**投稿自体は手動＝ユーザー担当**） |
| 反応分析 | 工程7（ダッシュボード数値→文体メモ・ネタ帳・リファレンスへ還流） |
記事を書くたびに Ryo の文体を「文体メモ」に蓄積し、回を重ねるほど本人らしい文章になる運用を前提とする。

**品質リファレンス**: `references/note-quality.md`（noteで伸びる記事のタイトル・冒頭・構成・
画像・AIっぽさ回避の基準）を、工程2以降の各工程に入る前に該当節を読んで適用する。
文体メモと衝突したら文体メモが優先。

**投稿は手動**。note への API 投稿は行わず、コピー&ペーストで貼れる完成原稿と公開設定の提案までがこのスキルの守備範囲。

## いつ使うか

- note に記事を書きたい（ネタの有無を問わず）
- ネタはあるが切り口・まとめ方が決まらない
- タイトル案だけ複数欲しい
- 自分で書いた下書きの推敲・ブラッシュアップだけしてほしい
- ハッシュタグ・公開設定・他記事への導線を提案してほしい
- 有料記事の無料公開部分の切り方を相談したい

## 最初にやること: 文体メモの確認（必須の分岐）

どの工程から入る場合でも、執筆・推敲に入る前に必ず文体メモの有無を確認する。

**保存場所**: 記事を管理しているディレクトリ直下の `style-memo.md`（見つからなければ Ryo に保存場所を確認する）。

### 分岐A: 文体メモが無い（初回）

1. `templates/style-memo.md` をコピーして文体メモを新規作成する。
2. 過去に書いた文章サンプル（note下書き・ブログ・長めのSNS投稿・レポート等、何でもよい）の提供を依頼する。
   - サンプルが**複数本（目安20本以上）**あれば、口調・語尾の癖・一文の長さ・改行のリズム・
     よく使う言い回しと絶対に使わない表現・読者との距離感（先生口調か、隣の同僚口調か）の
     6項目を軸に分析し、`style-memo.md` の該当項目へ落とし込む。
   - 分析後、そのプロファイルに沿った**見本文を100字程度**その場で書いて提示し、
     「これは自分の文章だと感じるか」を確認する。違和感があれば該当項目を Ryo と一緒に直してから確定する。
   - サンプルが少数（1〜2本）の場合はこの精査は行わず、一人称・文末表現・漢字とひらがなの
     開き方・段落の長さなど基本項目だけを分析してメモに記入する。
3. サンプルが無い場合は、次の質問で好みを把握してメモを埋める:
   - 一人称は「僕 / 私 / 俺」のどれか
   - 文末は「です・ます」か「だ・である」か、混ぜるか
   - 絵文字・記号（！、…、（笑）等）を使いたいか
   - 硬め / 柔らかめ、どちらの印象にしたいか
   - 使いたくない表現・言い回し（NG表現）はあるか
4. 埋めきれない項目は `【仮】` を付けて仮置きし、初回記事のフィードバックで確定させる。

**例外（推敲のみの依頼）**: 文体メモが無い状態で「下書きの推敲だけ」を頼まれた場合は、追加ヒアリングをせず、**その下書き自体を文章サンプルとして分析**してメモを初期化する（全項目 `【仮】` でよい）。推敲を優先し、メモ確定は次回に回す。

### 分岐B: 文体メモが有る（2回目以降）

1. 文体メモを読み込み、内容を1〜2行で要約して Ryo に提示する（「この文体で書きます」の確認）。
2. `【仮】` 付きの項目が残っていれば、今回の執筆で検証したい旨を伝える。
3. 執筆完了後、Ryo のフィードバック（「もっと短い文がいい」等）を文体メモに反映し、更新履歴に日付と変更点を追記する。

## 工程1: ネタ → 切り口設計

同じネタでも切り口で価値が変わる。次の3点で切り口を絞る。

| 観点 | 問い | 例（ネタ: 長期インターン） |
|---|---|---|
| 想定読者 | 誰が読むか。1人に絞れるほどよい | 長期インターンを探している大学2〜3年生 |
| 読後の変化 | 読み終えた読者は何ができる/どう変わるか | 応募前に確認すべき3点が分かり、ミスマッチを避けられる |
| 自分が書く理由 | なぜ他の誰でもなく自分がこれを書けるのか | 実際に未経験からコンサル系インターンに入った当事者だから |

- 3点が埋まらない切り口は弱い。埋まるまで切り口を変えるか、ネタを分割する。
- 切り口は2〜3案並べて Ryo に選んでもらう。1案だけ出して進めない。
- **一次情報の棚卸し（工程2に進む前に必須）**: この記事に入れられる自分の体験・
  数字・固有名詞を**最低3つ**列挙して Ryo に確認する。3つ挙がらないテーマは
  一般論記事になる（＝AIっぽくなり、noteでは読まれない）ため、切り口の変更か
  体験談型への転換を提案する。
- **G3視点の確認**: この記事は就活で「発信実績」として語れるか（学び・行動・結果が入っているか）も一言添える。

## 工程2: タイトル案を5本以上

切り口が決まったら、次の5つの型を使ってタイトル案を最低5本出す（型ごとに1本以上）。

| 型 | 特徴 | 例 |
|---|---|---|
| 数字型 | 具体的な数字で信頼と読みやすさを予告 | 「未経験からインターンに受かるまでにやった3つのこと」 |
| 逆説型 | 常識の逆を突いて引っかかりを作る | 「ガクチカは『盛らない』ほうが通る」 |
| 体験談型 | 一人称の実体験でリアリティを出す | 「大学2年の僕がコンサルインターンに落ち続けた話」 |
| How-to型 | 手順・方法を約束する | 「note初投稿を1日で公開するまでの手順」 |
| 問いかけ型 | 読者への質問で自分ごと化させる | 「そのポートフォリオ、誰に見せるために作ってる？」 |

- 各案に「狙い」を一言添える（どの読者のどの感情を突くか）。
- note はタイトルがタイムライン・検索の第一接点。**タイトルだけで内容と得が伝わるか**を基準に絞る。
- `references/note-quality.md` 1節（変化の物語・感情語・具体的な数字）を加点要素として使い、抽象的なポエム型は出さない。
- Ryo が選んだ1本を採用。組み合わせ・修正の要望があれば反映する。

## 工程3: 構成

採用タイトルに沿って見出しレベルの構成案を作り、執筆前に Ryo の確認を取る。

```
リード文（冒頭2〜4文）: 誰向けか + 読むと何が得られるか + 結論の先出し
├─ 見出し1: 本文（主張 → 根拠・体験 → 具体例）
├─ 見出し2: 〃
├─ 見出し3: 〃
└─ まとめ: 要点の再掲 + 読者の次のアクション（1つに絞る）
```

- **リード文は「読む理由の約束」**。結論やベネフィットを隠さず先に出す（note は冒頭で離脱されやすい）。エッセイ系はいきなり場面・感情から入る型でもよい（`references/note-quality.md` 2節）。どちらでも「今日は〜について書きます」型の前置きから始めない。
- 見出しは3〜5個が目安。note は見出しから目次が自動生成されるため、見出しだけ読んでも流れが分かる文言にする。
- まとめの「次のアクション」は、フォロー・関連記事・スキ・コメントなど1つに絞って具体的に書く。

## 工程4: 執筆

- **文体メモに従って書く**。一人称・文末・開き方・段落長・NG表現をすべて反映する。
- 文字数の目安: 指定が無ければ **1,500〜3,000字** をデフォルト提案して確認する（note で最後まで読まれやすい長さ）。指定があればそれに従う。
- 1段落は2〜4文・スマホ表示で4〜6行以内を目安に、こまめに改行する（note読者の大半はスマホ）。
- 体験談は「状況 → 行動 → 結果 → 学び」の順で書くと G3（就活エピソード）にもそのまま転用できる。
- **画像の挿入位置を本文に埋め込む**: `references/note-quality.md` 4節の表に従い、本文中に `【画像: 内容の指示】` を書き込む（アイキャッチ必須、スマホ2〜3スクロールに1枚目安、装飾だけのフリー素材は入れない）。完成原稿とセットで「用意する画像リスト」を提示する。
- 執筆後、文体メモとの差分が出た箇所（迷った表現など)があれば Ryo に確認し、回答をメモに反映する。

## 工程5: 推敲チェックリスト

初稿完成後、次のチェックリストで自己レビューし、修正点を修正案付きで提示する。

- [ ] **一文の長さ**: 60字を超える文は分割候補。1文1メッセージになっているか
- [ ] **重複表現**: 同じ語尾の3連続、同じ接続詞・単語の近接反復がないか
- [ ] **主張と根拠の対応**: すべての主張に根拠（体験・データ・理由）が紐づいているか。根拠のない断定は体験ベースの表現に直す
- [ ] **誤字脱字**: 固有名詞・数字・敬語の誤りを含めて全文チェック
- [ ] **リード文の結論先出し**: 冒頭2〜4文で「誰向けか・何が得られるか」を約束できているか。もったいぶっていないか
- [ ] **文体メモとの一致**: 一人称・文末・NG表現がメモ通りか
- [ ] **AIっぽさ**: `references/note-quality.md` 6節のチェックリスト（定型句・金太郎飴構成・一般論率・感情の欠如・両論併記逃げ・音読テスト）を全項目通す。該当箇所は内容と文字数を変えずに直す: 文の長さに強弱をつける／教科書的な説明を削る／単調な繰り返しをなくす／自信を持った実在の人物が語っているトーンに寄せる
- [ ] **画像**: 挿入位置が適切か（文字だけの長い区間がないか）、各`【画像:】`指示が具体的か

推敲は最大2往復を目安にし、細部の好みの調整は文体メモに書き溜めて次回に活かす。

## 工程6: ハッシュタグ・公開設定・導線

完成原稿とセットで以下を提案する。

- **ハッシュタグ**: 4〜6個。「大きいタグ（#エッセイ #就活 など読者母数が多いもの）2〜3個 + 記事固有のタグ（#長期インターン など）2〜3個」の構成。note公式のお題タグ（#〇〇 の企画）に合えば優先的に入れる。
- **公開設定**: 無料/有料の提案と理由。実績づくり期（フォロワー・スキが少ない段階）は無料公開を基本とする。
- **導線**: 過去記事への内部リンク（あれば）、まとめ末尾のフォロー誘導文、プロフィール記事への接続を提案。連載なら前後の記事リンクを必ず入れる。
- **初速の設計**: 公開直後のスキ・ビューが「注目」タブ掲載に効くため、公開告知用のX投稿文（記事の核を1つ抜き出したもの）もセットで提案する。公式お題タグに合えば優先して入れる（`references/note-quality.md` 5節）。

## note特有の知識（執筆・提案時に前提とすること)

- **冒頭数行が一覧に露出する**: タイムラインや検索結果ではタイトル + 冒頭のテキストが表示される。リード文の1〜2文目は「一覧で見えるコピー」として書く。
- **目次は見出しから自動生成**: 見出し（大見出し・小見出し）を付ければ目次が自動で入る。見出し文言はそのまま目次として読まれる前提で書く。
- **有料記事の無料部分の切り方**: 有料ラインより上が無料公開される。無料部分には「問題提起 + 結論の方向性 + 有料部分で得られるものの明示」まで含め、ノウハウの核心（具体的な手順・数値）の直前で切る。無料部分だけでも1つ学びがある状態にすると信頼を損なわない。

## 工程7: 公開後の反応分析（配信→反応分析ループ）

公開して終わりにしない。公開から3日〜1週間後を目安に、次を回す。

1. **数値の取得**: note ダッシュボードの数値（ビュー・スキ・コメント・フォロー増）を
   Ryo からもらう。もらえなければ「数値なし」として記録だけ残しスキップ
   （このループは任意。ただし連載・G2目的の記事では強く推奨）。
2. **分析**: スキ率（スキ÷ビュー）を過去記事の中央値と比較し、
   「タイトルの型 / テーマ / 切り口」のどれが効いたかを1〜3行で言語化する。
   1記事だけの結果で断定しない（3記事たまってから傾向として扱う）。
3. **還流**: 学びを次の3箇所に反映する。
   - **ネタ帳・次のテーマ選定**: 伸びたテーマの隣接ネタを次回の工程1で優先提案
   - **文体メモ**: 表現・トーン起因の反応（コメントで褒められた言い回し等）を追記
   - **`references/note-quality.md`**: 同じ型の勝ちが3回再現したら、タイトルの型などに
     自分の実績として追記を提案（ユーザーの合意を得てから書き換える）

## 途中の工程から入る場合（エントリポイント）

| 依頼 | 開始工程 | 備考 |
|---|---|---|
| ネタはあるが切り口が決まらない | 工程1 | フルコース |
| タイトル案だけ欲しい | 工程2 | 切り口3点（読者/変化/書く理由）だけ先に口頭確認する |
| 下書きの推敲だけ | 工程5 | 文体メモがあれば読み込んでから推敲。推敲結果から文体メモの更新候補も拾う |
| ハッシュタグ・導線だけ | 工程6 | 記事本文を読んでから提案する |
| 公開済み記事の数値を報告された | 工程7 | 分析→ネタ帳・文体メモ・リファレンスへの還流まで行う |
| 連載の2本目以降 | 工程1 | 分岐B（文体メモ読み込み）+ 前記事への導線を工程6で必ず入れる + 前記事の工程7（反応分析）が未実施なら先に促す |

途中から入る場合でも「文体メモの確認」だけはスキップしない（推敲・執筆の基準になるため）。

## エッジケースの扱い

- **テーマが未定（「何か書きたい」だけ)**: 工程1の前にネタ出しを行う。「最近時間を使ったこと / 人に聞かれたこと / 失敗したこと / 就活で話したい経験」の4観点で棚卸しし、G2/G3 につながるネタを3〜5個提案して選んでもらう。
- **文字数の指定が無い**: 勝手に決めず、デフォルト（1,500〜3,000字)を目安として提示し、確認してから書く。連載や有料記事は例外になり得るため必ず一言確認する。
- **専門外のテーマ（Ryo に実体験・知見が無い領域)**: 工程1の「自分が書く理由」が埋まらないため、そのまま解説記事にするのは非推奨と伝える。①「初心者として学んだ過程」の体験談型に切り口を変える、②テーマ自体を変える、の2択を提案する。書く場合、事実確認が必要な記述には印を付けて Ryo の確認を求め、裏取りできない断定は書かない。

## 前提セットアップ

外部依存なし。MCP・APIキー・環境変数は不要。文体メモ（`style-memo.md`）は初回実行時にこのスキルが作成する。
